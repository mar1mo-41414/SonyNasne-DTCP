# 09 XCode ファームウェア DRM モジュール解析 第3段 — レジストリの実読とディスパッチ機械の切り分け

## 要約

[docs/08](08_xcode_fw_drm_module_phase2.md)(第2段)の残件 — 0x2ED500 レジストリの実読、H2M コマンドディスパッチ機械の同定、DRM 実行コードの所在切り分け — に取り組んだ回の記録。実機には触れていない。

到達点:

- **0x2ED500 レジストリの構造を確定し、第2段の読みを訂正した**。実体は「20 バイト周期 × 4 グループ {キー/フラグ 1 ワード、コードポインタ 2 件、ゼロ 2 ワード}」であり、第2段の「16 バイトレコード」読みは境界の取り違いだった(§2.1)。8 件のコードポインタは**いずれも関数入口を指していない**(関数内部の基本ブロック途中 5 件、データ様の列の内部 1 件、現行デコーダで読めない位置 2 件)。ポインタ対を {開始, 終了} の区間とみる読みは、値の逆転するグループがあるため不成立(§2.2)。この表は静的なコマンドハンドラ表ではなく、ホストコマンド処理系への接続は確認できなかった。
- **H2M コマンド配送の構造は、GPL 側の一次資料(SDK ヘッダとドライバソース)で確定した**。配送単位はリンクリストのパケット `MIPSHOSTCOMPACKET`(コマンド番号フィールド `FunctionNumber`、配送先プロセッサ指定 `procIdx` を持つ)で、イメージ先頭の通信構造体領域を経由する。コマンド番号体系は [docs/02](02_dat_encryption_model.md) の実測番号と完全一致した(SCRAMBLER 0x108、SET_KEYSTORE_KEY 0x113、RESERVE_KEYSTORE_SLOT 0x114、READ_FROM_OTP 0x116)(§4.1)。ただし **FW 側の受信→ディスパッチのコード本体は本段でも未同定**で、ハンドラ本体は読めていない(§4.2)。
- **文脈オブジェクト 0x3DCD7C の利用元は、3 方式の参照探索でも表以外に見つからなかった**(文字列参照、値としての全域検索、到達コード内の即値。いずれも範囲明記、§4.3)。
- **DRM 実行コードの所在切り分け**: 第2 FW と SoC 内蔵カーネルイメージには、文字列の面で DRM 制御の所在を示す証拠が無い(§5.2、§5.3)。実行時にホストから追加モジュールを供給する経路は、ドライバの FW ロード処理には存在しない(ロード対象は主・第2 の 2 イメージのみ、§5.4)。主 FW 内では、DRM 文字列の近傍が実行コードである証拠は得られていない。残る可能性は「主 FW のコード密領域内に、文字列・表を経由しない形で存在する」か「SoC 内の専用セキュリティ処理系(FW イメージ群の外)」であり、いずれも未判定(§5.5)。
- 焦点の (a)/(b) の境界と READ_FROM_OTP の index 境界は、ハンドラ未到達のため**未判定のまま**であり、その理由を §6 に明記する。

## 1. 対象と方法

- 対象: 平文の主 FW イメージ(6,216,324 バイト、SHA-256 は [docs/05](05_xcode_firmware_images.md) §2 と照合済み)、第2 FW イメージ、SoC 内蔵カーネルイメージ、GPL ソースツリー側の SDK ヘッダ(commsdk)と AV ドライバソース。
- 方法は第2段と同じく、表構造はバイト列の直接解読、コードの読みは capstone 6.0.0 + 自作スクリプトで、デコードの正しさが検証できた範囲でのみ主張する。これに加え本段では、命令ワードと limm の格納規約をベクタ表の実バイトから確定させ、デコーダ非依存のバイトパターン走査を併用した(§4.3)。
- 実機には触れていない。手元の解析環境上のファイル解析のみ。

## 2. 0x2ED500 レジストリの実読

### 2.1 構造の確定と第2段の訂正

0x2ED500〜0x2ED54F のワード列は、**20 バイト周期**で次の形を 4 回繰り返す:

| グループ | 位置 | キー/フラグ | ポインタ 1 | ポインタ 2 | 残り |
|---|---|---|---|---|---|
| G0 | 0x2ED500 | 0x01000000 | 0x156830 | 0x156AD0 | 0, 0 |
| G1 | 0x2ED514 | 0x00010000 | 0x26EE7C | 0x26EE04 | 0, 0 |
| G2 | 0x2ED528 | 0x00020000 | 0x228C90 | 0x166B7C | 0, 0 |
| G3 | 0x2ED53C | 0x00000200 | 0x2653F0 | 0x16BBE8 | 0, 0 |

0x2ED550 以降はゼロが続き、表はここで終端する。

- 第2段は「16 バイトレコード {フラグ, コードポインタ, コードポインタ, 0} の列」と読んだが、16 バイト境界で切ると G1 以降でフィールドの対応が崩れる(キー位置に 0 やコードポインタが来る)。20 バイト周期では全 20 ワードが例外なくパターンに一致する。**第2段のレコード境界は誤りであり、本書の読みが実測である**。
- 先頭ワード(キー/フラグ)の意味は未確定である。値 0x01000000 / 0x00010000 / 0x00020000 / 0x00000200 をバイト単位で見ると、各グループで 1 バイトだけが 1 または 2 になり、その位置がグループごとにずれる。半語ペアの ID とも、ビットマスクとも決め打ちできないため、本書では「キー/フラグ」とだけ呼ぶ。

### 2.2 コードポインタ 8 件の実読

各ポインタの指す位置から capstone で読み、入口性を検証した。結果は全件「関数入口ではない」:

| ポインタ | 読みの結果 |
|---|---|
| 0x156830 | 大きな関数の内部。ベースレジスタを合成し、カウンタで 16 バイト刻みの表を辿る処理の途中(第2段 §3.5 の所見と同一箇所) |
| 0x156AD0 | 同じ関数の内部とみられる基本ブロック(定数の格納と分岐のみ) |
| 0x26EE7C | バイト書き込みループの末尾部分(格納、加算、比較、分岐) |
| 0x26EE04 | 1 命令読めたのみで後続はデコード不能。関数入口の形ではない |
| 0x228C90 | コードではなくデータ様の列の内部(マジック様の定数列を含む領域の途中。直前から読み直しても数命令で崩壊する) |
| 0x166B7C | 構造体フィールドの初期化列の途中(ゼロ代入と 64 ビット減算の並び) |
| 0x2653F0 | capstone で 1 命令もデコードできなかった |
| 0x16BBE8 | 同上(直前は 64 ビット減算の途中として読める) |

解釈と切り分け:

- 静的な関数ポインタ表(ハンドラ表)であれば、ポインタは関数入口(プロローグ)を指すのが通常の形だが、ここでは 8 件とも入口を指していない。**この表がコマンドハンドラのディスパッチ表であるという読みは、この実測と整合しない**。
- ポインタ対を {開始アドレス, 終了アドレス} の区間指定とみる読みは、G1 で大小が逆転する(0x26EE7C > 0x26EE04)ため**不成立**。
- 残る性格の候補は、状態機械の再開点(継続点)の列、あるいは実行時に書き換えられる作業表の初期値などであり、本段では決め打ちしない。**この表が何をキーに何を引く表かは未確定**、というのが本段の結論である。
- 外部からの参照: 8 件のポインタ値と表のベースアドレスは、イメージ全域の値検索(リトルエンディアン形式)で**表の中にしか現れない**。表を利用するコードは、ベースを合成して相対アクセスする形とみられ、到達コード内でも表近傍への即値参照は検出されなかった(検証範囲は §4.3)。

## 3. 0x2ED458 の初期化/登録リスト様テーブルの再読

第2段 §3.6 の表について、本段の精密ダンプで次の読みが得られた:

- 8 バイトペアの列で、第 2 要素は 0x3D2EF8 から +0xC 刻みで増える(ゼロ初期化領域の記述子スロット列)。
- 第 1 要素は 0x00680B50、0x00680BDC、… のように **0x68〜0x6B 万台のアドレス帯**に分布し、ファイル範囲外を指す。後半のレコードでは第 3・第 4 の値(0x4EB3E4 から +4 刻みで増える列など)も現れる。
- 傍証: ベクタ [2] の跳躍先から辿れる関数(0x123584)の中に、この帯域の値 0x69017C を即値として参照する命令が実在した。すなわちこの帯域は実在するアドレス空間(フレームバッファ等の作業メモリ帯とみられる)である。
- 解釈(推測と明記する): この表は {作業メモリ上のバッファアドレス, 記述子スロット} の初期化リストであり、メディア処理のバッファ管理用である可能性が高い。DRM 制御との接続は本段でも確認できていない。
- 表の末尾側(0x2ED4C8〜)にはコードポインタ 0x15D00C / 0x15D06C / 0x15D0AC と値 0x3D3070 の組がある。0x15D00C を読むと時刻・カウンタ系の処理(64 ビット加算とループカウンタ)であり、DRM との関係は見出せなかった。

なお 0x2ED5B0〜約 0x2EDCFF には半語値の密な列(値が所在と緩やかに連動して増減する並び)が続き、0x2EDD00 以降はゼロ領域になる。表群(0x2ED458〜0x2EDCFF)はひとかたまりのデータ領域であり、その性格(16 ビット命令列か、補間係数等のデータ列か)は本段では未確定である。

## 4. H2M コマンドディスパッチ機械

### 4.1 配送構造の確定(一次資料による)

ホスト→FW のコマンド配送は、GPL 側の SDK ヘッダ(commsdk の `mipshost.h`、`drv_if.h`、`xcodecmd.h`)とドライバソースから、次の形に確定した:

- 配送単位は **`MIPSHOSTCOMPACKET`**(リンクリストのパケット)。フィールドは `Next` / `Prev`、`Direction`(HOST2MIPS=1 / MIPS2HOST=2)、**`FunctionNumber`(コマンド番号)**、`PacketProcessed`、`Input`(入力データへの参照)、`NextPacket`、`CallerPrivate1/2`、**`procIdx`(配送先プロセッサの指定: 0, 1, 2, 4)**、`reserved`。
- 通信構造体は FW イメージ先頭の領域に置かれる(`MIPS_FB_CODE_OFFSET` = 0、通信オフセット 0x100〜)。主 FW イメージの 0x100〜0x4000 がファイル上でゼロなのは、この領域が実行時の通信・作業用 RAM であることと整合する。
- ホスト→プロセッサの通知は MMIO レジスタ経由のドアベルで行われる(`XC_SOC_HOST_TO_PROC0_CMD_REG` 等の定義が SDK にある)。
- コマンド番号体系は SDK の列挙で一意に定まる。**[docs/02](02_dat_encryption_model.md) の実測番号と完全一致**した: CMD_INIT = 0x100 から始まり、CMD2_SDEV_RSA = 0x106、CMD2_SDEV_SCRAMBLER = 0x108、CMD2_SDEV_SET_KEYSTORE_KEY = 0x113、CMD2_SDEV_RESERVE_KEYSTORE_SLOT = 0x114、CMD2_SDEV_XC4_RSA_REQUEST = 0x115、**CMD2_SDEV_READ_FROM_OTP = 0x116**、CMD2_SDEV_NVMDATA = 0x11A まで。すなわち本書で追うコマンド群(OPEN 系、SCRAMBLER、READ_FROM_OTP、SECUREDTS を含むストリーム開始)は、全てこの FunctionNumber 体系で FW 側に届く。
- 暗号制御のパラメータ形式(SDK の `crypto.h`)にも、鍵そのものではなくインデックスで指定する設計が確認できる: TS デスクランブル制御パケット `scramble_ctrl` は `vector_index` / `cw_01_index` / `cw_10_index` / `cw_11_index` / `syskey_index` を持ち、`CRYPTOCTRL2` には「システム鍵を使う」(`CRYPTO_CTRL2_USE_SYSTEM_KEY`)「CW が暗号化されて渡る」(`CRYPTO_CTRL2_ENCRYPTED_CW`)のフラグがある。これは [docs/02](02_dat_encryption_model.md) §10 の「実効鍵は FW 側解決」というモデルの前提(ホストが触るのはスロット番号とトークンまで)と整合する傍証である。ただしこれは SDK の一般形であり、この製品の録画経路がどのフラグ・形式を使っているかは未確定である。

### 4.2 FW 側の受信・ディスパッチコード — 未同定

- FW 側でパケットリストを受けて FunctionNumber で振り分けるコード本体は、本段でも同定できなかった。到達できたコード(ベクタ跳躍先、既知の表に載る関数、レジストリのポインタ群など 33 関数)の中に、通信構造体領域やコマンド番号らしき値への言及は見つからなかった。
- ベクタ [0] 0x113C20・[1] 0x113C00・[2] 0x113D5C のうち、[1] は現行デコーダでコードとして読めず(生バイトは 16 ビット命令の密な列様で、マジック様の定数列も混在する)、割り込み入口の実読は進まなかった。
- 配送先が `procIdx` で複数プロセッサに分かれる設計であるため、主 FW(ARC イメージ)側のコードは「プロセッサ間メッセージの受け手」として振る舞い、H2M の一次受け手は SoC メインプロセッサ側の処理である可能性が残る。一次受け手のコードの所在は、§5 の切り分けの範囲では確定していない。

### 4.3 文脈オブジェクト 0x3DCD7C の利用元 — 3 方式の陰性(範囲明記)

0x2ED578 の表(ID 0x1101〜0x1106 → 同一ポインタ 0x3DCD7C)について、利用元を 3 方式で探索した。いずれも**表の中以外に現れなかった**:

1. 値としての全域検索: 値 0x003DCD7C はイメージ全域で表の 6 件のみ(リトルエンディアン形式)。半語スワップ形式は 0 件。
2. limm 形式命令のバイトパターン走査: 命令ワード 0x0F8020XX + 半語スワップ limm の形式(ベクタ表とサンクの実バイトから規約を確定)をコード領域全域で走査し、この形式で 0x3DCD7C・レジストリ(0x2ED500)・初期化リスト(0x2ED458)・対応表(0x2ED578)を指す命令は **0 件**だった。なお同形式のベクタ表エントリ(ジャンプ 6 件)とサンクの呼び出しは正しく検出できており、走査方法自体の有効性は確認している。ただしこの形式以外の limm 持ち命令は走査対象外である。
3. 到達コード内の即値: 種エントリ群(ベクタ跳躍先、サンク先、レジストリのポインタ群、初期化リストに載る関数など)から再帰辿りで読めた 33 関数について、表近傍(0x2EC000〜0x2EF000)、文脈オブジェクト近傍(0x3DC000〜0x3DD000)、記述子帯(0x3D2000〜0x3D4000)への即値参照は **0 件**だった。到達範囲がコード領域全体のごく一部であるという限界はそのまま残る。

したがって文脈オブジェクトの利用元は未同定であり、この表の意味付け(ID 0x11xx 群とランタイムオブジェクトの対応)も未確定のままである。

## 5. DRM 実行コードの所在切り分け

### 5.1 主 FW 内の別領域

- DRM 文字列ブロック(0x2D3070〜0x2E7178)の近傍が実行コードである証拠は得られていない。最も近いベクタ跳躍先 0x2D0144 の周辺は 16 ビット命令の密な列で現行デコーダでは意味が取れず、その性格は未確定である。
- イメージ後半(約 0x3C0000〜0x564000)にはオーディオ系ライブラリの文字列(Dolby の著作権表示やライブラリ版数)が含まれ、複合イメージの後半はメディアライブラリ群の領域である。DRM 制御の文字列はここには無い(第1段の文字列走査の範囲)。

### 5.2 第2 FW イメージ

- 先頭は主 FW と異なる形式(ベクタ表形式ではなく、16 ビット命令列様の開始)で、コード密領域は約 0x0〜0x1C0000、中程度の領域が約 0x240000 まで、以降はゼロ。
- キーワード文字列の走査(DRM/DTCP/OTP/鍵/証明書/RSA 等の語彙、5 文字以上の可読文字列)では、DRM 制御に関わる文字列は **「DTCP」の断片 1 件と AAC スクランブラのログ 1 件のみ** で、drmctrl 級の制御文字列は存在しない。
- 判定: 第2 FW はオーディオ/ビデオ処理側プロセッサのイメージであり、DRM 制御の主所在とは考えにくい。ただしこれは文字列の面での切り分けであり、コードの実読はしていない(ログを出さない実装の可能性までは否定しない)。

### 5.3 SoC 内蔵カーネルイメージ

- MIPS Linux カーネル(uImage)の文字列・シンボル名を走査した範囲では、DTCP / keystore / kauth に関わる文字列は **0 件** で、現れるのは Linux 標準の暗号フレームワークのシンボル群のみだった。「vixs」「xcode」の語は汎用ドライバ名等に現れる範囲に留まる。
- 判定: DRM 実行コードの所在はこのイメージではない(文字列・シンボルの面)。[docs/05](05_xcode_firmware_images.md) §5 の通り、このイメージ自体が製品で使われているかも未確定である。

### 5.4 実行時に供給されるロード可能モジュール

- ドライバ(製品版と同一系統の GPL ソース)の FW ロード処理(`INIT_LOAD_FIRMWARE`)が設定するコードイメージは、**主 FW と第2 FW の 2 つだけ**である(ビルドにより平文版/暗号化版が差し替わる。一次資料: ドライバソースの初期化処理で `fm_ptr` / `second_fm_ptr` に設定されるのはこの 2 系統のみだった)。
- ロード後に追加モジュールをホストから供給する経路は、このロード処理の範囲には存在しない。
- 主 FW 側でも、モジュールの登録構造(名前とポインタの組の表)は §2・§3 で読んだ表群以外には確認できていない(確認した範囲は 0x2ED000 台の表領域と、その周辺)。
- 判定: 「DRM 実行コードが実行時に供給される別モジュールにある」という仮説は、**ホスト側からの供給という形では支持されない**。残る変形は「主 FW イメージ内に埋め込まれた別プロセッサ用コード資産」だが、その存在を示すヘッダ様構造は本段の確認範囲では見つかっていない。

### 5.5 切り分けのまとめと残る可能性

| 所在候補 | 判定 | 根拠(範囲) |
|---|---|---|
| 主 FW の DRM 文字列近傍 | 証拠なし | 文字列参照の陰性(第2段)、近傍ベクタ先の実読不能 |
| 主 FW のコード密領域のどこか | 未判定 | ディスパッチ形式が数値→表/分岐以外の可能性を排除できていない |
| 第2 FW | 考えにくい | DRM 制御文字列が走査範囲でほぼ皆無(§5.2) |
| SoC カーネルイメージ | 棄却寄り(文字列の面) | 関連文字列・シンボル 0 件(§5.3) |
| 実行時供給モジュール | 棄却寄り(ホスト供給の形) | ドライバのロードは 2 イメージのみ(§5.4) |
| SoC 内の専用セキュリティ処理系(イメージ群の外) | 未判定 | 本段の材料では検証手段が無い |

## 6. 焦点への回答状況 — (a)/(b) の境界と OTP の index 境界

- **(a)/(b) の境界: 未判定**。理由: FW 側でホストコマンド(SCRAMBLER 0x108 等)を処理するハンドラ本体を本段でも同定できず、トークンが通過する ARC コードを読めていない。§4.1 の SDK 資料は「インデックス指定とシステム鍵の設計が存在する」ことまでは示すが、この製品の録画経路でトークンがどう扱われるかは示さない。
- **READ_FROM_OTP の index 境界(0x82 付近): 未読**。[docs/07](07_otp_value_level_stability.md) のホスト側実測(0x00–0x81 と 0xFF は値レベルで固定、0x82–0xFE は読み出しごとに変動)に対応する FW 側の境界処理は、READ_FROM_OTP(0x116)ハンドラ未同定のため読めていない。
- どちらも「ハンドラの同定」が前提であり、本段の到達点(配送構造の確定)はその入口までである。

## 7. 残件と次の打ち手

1. **逆アセンブラの強化**(第2段から継続): 現行 capstone の ARCompact デコードの弱さが全ての実読の天井になっている。Ghidra 向け ARC SLEIGH の自作、または出所を監査できた定義の導入が、ハンドラ同定の前提条件である。
2. **ベクタ [1](0x113C00)と [5](0x2D0144)の実読**: 16 ビット命令列のデコードが安定すれば、割り込み入口と DRM 文字列近傍のコードの性格が分かる。
3. **プロセッサ間メッセージの追跡**: `procIdx` による配送の先、ARC 側タスクがメッセージを受ける構造(タスク登録・メッセージ ID の表)を主 FW 内で探す。§2 のレジストリと §4.3 の対応表(ID 0x11xx)は、その過程で意味が付く可能性がある。
4. **通信構造体領域を参照するコードの探索**: FW イメージ先頭(0x100〜)の通信領域は小さいアドレスのため静的検索が効きにくい。デコーダ強化後に、初期化コード(ベクタ [0] の初期化経路)から順に実読するのが現実的である。
5. ハンドラ同定後: (a)/(b) の境界と READ_FROM_OTP の index 境界処理を読む。
