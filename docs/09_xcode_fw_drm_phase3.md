# 09 XCode ファームウェア DRM モジュール解析 第3段 — レジストリの実読とディスパッチ機械の切り分け

## 要約

[docs/08](08_xcode_fw_drm_module_phase2.md)(第2段)の残件 — 0x2ED500 レジストリの実読、H2M コマンドディスパッチ機械の同定、DRM 実行コードの所在切り分け — に取り組んだ回の記録。実機には触れていない。

到達点:

- **0x2ED500 レジストリの構造を確定し、第2段の読みを訂正した**。実体は「20 バイト周期 × 4 グループ {キー/フラグ 1 ワード、コードポインタ 2 件、ゼロ 2 ワード}」であり、第2段の「16 バイトレコード」読みは境界の取り違いだった(§2.1)。8 件のコードポインタは**いずれも関数入口を指していない**(関数内部の基本ブロック途中 5 件、データ様の列の内部 1 件、現行デコーダで読めない位置 2 件)。ポインタ対を {開始, 終了} の区間とみる読みは、値の逆転するグループがあるため不成立(§2.2)。この表は静的なコマンドハンドラ表ではなく、ホストコマンド処理系への接続は確認できなかった。
- **H2M コマンド配送の構造は、GPL 側の一次資料(SDK ヘッダとドライバソース)で確定した**。配送単位はリンクリストのパケット `MIPSHOSTCOMPACKET`(コマンド番号フィールド `FunctionNumber`、配送先プロセッサ指定 `procIdx` を持つ)で、イメージ先頭の通信構造体領域を経由する。コマンド番号体系は [docs/02](02_dat_encryption_model.md) の実測番号と完全一致した(SCRAMBLER 0x108、SET_KEYSTORE_KEY 0x113、RESERVE_KEYSTORE_SLOT 0x114、READ_FROM_OTP 0x116)(§4.1)。ただし **FW 側の受信→ディスパッチのコード本体は本段でも未同定**で、ハンドラ本体は読めていない(§4.2)。
- **文脈オブジェクト 0x3DCD7C の利用元は、3 方式の参照探索でも表以外に見つからなかった**(文字列参照、値としての全域検索、到達コード内の即値。いずれも範囲明記、§4.3)。
- **DRM 実行コードの所在切り分け**: 第2 FW と SoC 内蔵カーネルイメージには、文字列の面で DRM 制御の所在を示す証拠が無い(§5.2、§5.3)。実行時にホストから追加モジュールを供給する経路は、ドライバの FW ロード処理には存在しない(ロード対象は主・第2 の 2 イメージのみ、§5.4)。主 FW 内では、DRM 文字列の近傍が実行コードである証拠は得られていない。残る可能性は「主 FW のコード密領域内に、文字列・表を経由しない形で存在する」か「SoC 内の専用セキュリティ処理系(FW イメージ群の外)」であり、いずれも未判定(§5.5)。
- 焦点の (a)/(b) の境界と READ_FROM_OTP の index 境界は、ハンドラ未到達のため**未判定のまま**であり、その理由を §6 に明記する。

## 1. 対象と方法

- 対象: 平文の主 FW イメージ(6,216,324 バイト、SHA-256 は [docs/05](05_xcode_firmware_images.md) §2 と照合済み)、第2 FW イメージ、SoC 内蔵カーネルイメージ、GPL ソースツリー側の SDK ヘッダ(commsdk)と AV ドライバソース。
- 方法は第2段と同じく、表構造はバイト列の直接解読、コードの読みは capstone 6.0.0 + 自作スクリプトで、デコードの正しさが検証できた範囲でのみ主張する。これに加え本段では、命令ワードと limm の格納規約をベクタ表の実バイトから確定させ、デコーダ非依存のバイトパターン走査を併用した(§4.3)。
- 実機には触れていない。手元の解析環境上のファイル解析のみ。

## 2. 0x2ED500 レジストリの実読

### 2.1 構造の確定と第2段の訂正

0x2ED500〜0x2ED54F のワード列は、**20 バイト周期**で次の形を 4 回繰り返す:

| グループ | 位置 | キー/フラグ | ポインタ 1 | ポインタ 2 | 残り |
|---|---|---|---|---|---|
| G0 | 0x2ED500 | 0x01000000 | 0x156830 | 0x156AD0 | 0, 0 |
| G1 | 0x2ED514 | 0x00010000 | 0x26EE7C | 0x26EE04 | 0, 0 |
| G2 | 0x2ED528 | 0x00020000 | 0x228C90 | 0x166B7C | 0, 0 |
| G3 | 0x2ED53C | 0x00000200 | 0x2653F0 | 0x16BBE8 | 0, 0 |

0x2ED550 以降はゼロが続き、表はここで終端する。

- 第2段は「16 バイトレコード {フラグ, コードポインタ, コードポインタ, 0} の列」と読んだが、16 バイト境界で切ると G1 以降でフィールドの対応が崩れる(キー位置に 0 やコードポインタが来る)。20 バイト周期では全 20 ワードが例外なくパターンに一致する。**第2段のレコード境界は誤りであり、本書の読みが実測である**。
- 先頭ワード(キー/フラグ)の意味は未確定である。値 0x01000000 / 0x00010000 / 0x00020000 / 0x00000200 をバイト単位で見ると、各グループで 1 バイトだけが 1 または 2 になり、その位置がグループごとにずれる。半語ペアの ID とも、ビットマスクとも決め打ちできないため、本書では「キー/フラグ」とだけ呼ぶ。

### 2.2 コードポインタ 8 件の実読

各ポインタの指す位置から capstone で読み、入口性を検証した。結果は全件「関数入口ではない」:

| ポインタ | 読みの結果 |
|---|---|
| 0x156830 | 大きな関数の内部。ベースレジスタを合成し、カウンタで 16 バイト刻みの表を辿る処理の途中(第2段 §3.5 の所見と同一箇所) |
| 0x156AD0 | 同じ関数の内部とみられる基本ブロック(定数の格納と分岐のみ) |
| 0x26EE7C | バイト書き込みループの末尾部分(格納、加算、比較、分岐) |
| 0x26EE04 | 1 命令読めたのみで後続はデコード不能。関数入口の形ではない |
| 0x228C90 | コードではなくデータ様の列の内部(マジック様の定数列を含む領域の途中。直前から読み直しても数命令で崩壊する) |
| 0x166B7C | 構造体フィールドの初期化列の途中(ゼロ代入と 64 ビット減算の並び) |
| 0x2653F0 | capstone で 1 命令もデコードできなかった |
| 0x16BBE8 | 同上(直前は 64 ビット減算の途中として読める) |

解釈と切り分け:

- 静的な関数ポインタ表(ハンドラ表)であれば、ポインタは関数入口(プロローグ)を指すのが通常の形だが、ここでは 8 件とも入口を指していない。**この表がコマンドハンドラのディスパッチ表であるという読みは、この実測と整合しない**。
- ポインタ対を {開始アドレス, 終了アドレス} の区間指定とみる読みは、G1 で大小が逆転する(0x26EE7C > 0x26EE04)ため**不成立**。
- 残る性格の候補は、状態機械の再開点(継続点)の列、あるいは実行時に書き換えられる作業表の初期値などであり、本段では決め打ちしない。**この表が何をキーに何を引く表かは未確定**、というのが本段の結論である。
- 外部からの参照: 8 件のポインタ値と表のベースアドレスは、イメージ全域の値検索(リトルエンディアン形式)で**表の中にしか現れない**。表を利用するコードは、ベースを合成して相対アクセスする形とみられ、到達コード内でも表近傍への即値参照は検出されなかった(検証範囲は §4.3)。

## 3. 0x2ED458 の初期化/登録リスト様テーブルの再読

第2段 §3.6 の表について、本段の精密ダンプで次の読みが得られた:

- 8 バイトペアの列で、第 2 要素は 0x3D2EF8 から +0xC 刻みで増える(ゼロ初期化領域の記述子スロット列)。
- 第 1 要素は 0x00680B50、0x00680BDC、… のように **0x68〜0x6B 万台のアドレス帯**に分布し、ファイル範囲外を指す。後半のレコードでは第 3・第 4 の値(0x4EB3E4 から +4 刻みで増える列など)も現れる。
- 傍証: ベクタ [2] の跳躍先から辿れる関数(0x123584)の中に、この帯域の値 0x69017C を即値として参照する命令が実在した。すなわちこの帯域は実在するアドレス空間(フレームバッファ等の作業メモリ帯とみられる)である。
- 解釈(推測と明記する): この表は {作業メモリ上のバッファアドレス, 記述子スロット} の初期化リストであり、メディア処理のバッファ管理用である可能性が高い。DRM 制御との接続は本段でも確認できていない。
- 表の末尾側(0x2ED4C8〜)にはコードポインタ 0x15D00C / 0x15D06C / 0x15D0AC と値 0x3D3070 の組がある。0x15D00C を読むと時刻・カウンタ系の処理(64 ビット加算とループカウンタ)であり、DRM との関係は見出せなかった。

なお 0x2ED5B0〜約 0x2EDCFF には半語値の密な列(値が所在と緩やかに連動して増減する並び)が続き、0x2EDD00 以降はゼロ領域になる。表群(0x2ED458〜0x2EDCFF)はひとかたまりのデータ領域であり、その性格(16 ビット命令列か、補間係数等のデータ列か)は本段では未確定である。
