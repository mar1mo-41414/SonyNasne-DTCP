# 10 XCode 主 FW 平文イメージの全域監査 — 暗号化されたままの領域はあるか

[docs/05](05_xcode_firmware_images.md)(第1段)の証明 —「平文版と製品版は同一内容で、相違は 16 バイトブロック単位の暗号化(ECB 型)だけ」— を前提に、その射程の外にある問いを監査した回。実機には触れておらず、手元のファイル解析のみで実施した。

**問い**: 平文版の全域が本当に平文か。暗号化出力との全単射が成り立っていても、平文版の一部領域が「チップ側で別途復号される前提で暗号化されたまま」含まれている可能性は論理的に残る。nasne の SPI ROM では先頭部分が暗号化されていた前例があり、同世代の設計で同じことが FW イメージ内に起きていてもおかしくない。これは「普通はそんな設計をしない」式の常識では潰せず、実測で潰すべき対象である。

**結論(要約)**:

- **暗号化されたままの領域の存在を示す統計的様相は、イメージ全域のどこにも無い**。4KB 窓・512B 窓の両粒度で「ランダム様」の窓を全列挙し、その全てについて平文の構造化データとしての積極的な同定が付いた(§3)。
- 高エントロピーの正体は、音声コーデックの係数/Huffman 表データ(ライセンス表示・エラー文字列が平文で混在)、CPRM/DTCP のパラメータデータ、DSP 係数表、0xFF 埋めの疎なレコード類であり、いずれも暗号化域ではない。
- 第1〜3段の結論に修正は不要。むしろ本監査は、第2段・第3段の所在切り分けにおける代替仮説「DRM 実行コードがこのイメージ内の暗号化サブ領域に隠れている」を統計的に除去する(§6)。
- 判定の限界(512B 未満の断片)は §7 に明記する。

## 1. 判定基準 — 暗号化域なら何が見えるはずか

暗号化(または圧縮+暗号化)された領域は、次の統計的署名を同時に持つはずである:

1. バイト分布が均一(カイ二乗統計量/自由度 ≈ 1)。
2. 窓エントロピーが 8 近傍(4KB 窓で 7.9 以上)。
3. 短ラグ(1〜32 バイト)の自己相関がランダム水準(バイト一致率 ≈ 0.0039)。
4. 可読文字列が偶然水準しか生じない。
5. 16 バイトブロックの重複は、平文側に反復構造があれば現れるが、構造の無い平文ではほぼ全て相異なる。**この 5 は単独では証拠にならない**(係数表でも全て相異なり得る)。判定は 1〜4 の複合で行う。

対照(本物の暗号化形): 製品版イメージのコード域の窓は、カイ二乗/自由度が 1.18〜1.29、4KB 窓エントロピーは 7.93〜7.99 を示す(本監査で実測)。平文版のコード域の同じ窓は、カイ二乗/自由度 155〜340、エントロピー 6.5〜7.0 であり、両者は統計的にはっきり別の様相である。

## 2. 方法とカバレッジ

- 対象: 平文の主 FW イメージ(6,216,324 バイト、SHA-256 が [docs/05](05_xcode_firmware_images.md) §2 の記録と一致することを確認して使用)と、製品版(暗号化出力、同 6,216,336 バイト)。
- 全域を次の 4 手法で覆った:
  1. **4KB 窓エントロピーマップ**: 全 1,518 窓(平文版・製品版の両方)。エントロピー ≥7.5 の窓を全列挙した。
  2. **512B 窓エントロピーマップ**: 全 12,141 窓。≥7.5 を全列挙した(4KB 未満の埋め込みサブ領域を検出するための細粒度側)。
  3. **非ゼロランの全数調査**: ゼロ間隔 256 バイト未満を連結し、全 373 ランについてエントロピー、16 バイトブロックの相異率と最頻ブロック占有率、文字列被覆率、ポインタ様ワードの密度、ゼロ率を測定した。サイズ ≥64 バイトかつエントロピー ≥6.9 のランを全列挙した。
  4. **個別精査**: 疑わしいラン/スポットごとに、カイ二乗均一性、ラグ 1〜32 の自己相関、ワード頻度、文字列の実読を行った。最有力候補については既知圧縮形式(zlib / raw deflate / gzip / lzma / bzip2)の展開試行も行った。
  5. **製品版との全単射の再検証**: 16 バイトブロック対応の全単射を 64KB チャンク単位で取り直し、先頭・末尾を含む全 95 チャンクで整合を確認した([docs/05](05_xcode_firmware_images.md) §3.4 の再現)。
- バイト被覆: 非ゼロバイトは全体の 49.7%(3,089,936 バイト)で、残りは全ゼロである。ゼロ域はそれ自体が平文であり、非ゼロ部分は手法 3 のラン調査が全域を覆う。「高エントロピーでないから見ていない」領域は存在しない — 全ての窓と全てのランが測定対象である。

## 3. 高エントロピー域の列挙と同定

### 3.1 4KB 窓で ≥7.5 は 10 窓、全て音声コーデックのデータ域内

該当窓は 0x3E8000、0x43A000〜0x43D000、0x444000、0x453000、0x482000、0x484000〜0x487000 で、**全て 0x3B0000〜0x48C000 のデータ域の中**にある。コード密領域(0x8000〜0x2D3070)の窓最大は 6.976、末尾(0x564000〜末尾)の最大は 1.034 である。

このデータ域が何であるかは、平文で読める文字列が積極的に示す: AAC 系デコーダのエラー文(「Invalid huffman codebook」「Negative scalefactor found, should be impossible」「Pulse coding not allowed in short blocks」等)、MPEG 音声系デコーダのエラー文(「Invalid bitrate」「Invalid sampling frequency」「MPEG1 not supported」等)、ソースファイル名 `../refDecoder.c`、識別子 `ViXS AAC encode`、デコーダの版数表示 `LBRDEC version 3.01.01.20`、Dolby Laboratories の著作権表示(2003–2006)とライセンス文、MLP デコーダのアサート文。すなわちこの域は、ライセンス供与された音声コーデック群(AAC / MPEG 音声 / Dolby 系)の表データと文字列が平文で格納された場所であり、高エントロピー部分はその係数/Huffman 表にあたる。

### 3.2 最有力候補セグメントの精査(0x439CDC〜0x43D890、15,284 バイト)

イメージ内で最もランダムに近いセグメント(全体エントロピー 7.89、16 バイトブロックは全て相異なる)を個別に精査した:

- バイト分布は均一から大きく外れる(カイ二乗/自由度 = 14.4。暗号化形の対照は §1 の通り ≈1.0〜1.3)。
- ラグ 4 のバイト一致率は 0.141 で、ランダム水準(0.0039)の 36 倍。ワード単位の構造がある。
- AAC デコーダのエラー文字列が平文で混在する。暗号化された領域の中に平文の文字列は存在し得ない。
- 既知圧縮形式の展開試行はいずれも不成立で、圧縮域としての証拠も無い。

判定: Huffman 表/係数表のデータ(平文)。ブロックが全て相異なることは、この種の表でも普通に起こり、暗号化の証拠にはならない(§1 の基準 5)。
