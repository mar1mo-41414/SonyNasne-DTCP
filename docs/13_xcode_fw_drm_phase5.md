# 13. XCode ファームウェア DRM モジュール解析 第5段: +0x100000 ビューでの再解析

対象は主 FW 平文イメージ([05](05_xcode_firmware_images.md) で製品版と同一内容と確定した 6,216,324 バイト)。本段のアドレス表記は、特に断らない限り**ファイルオフセット**とする(ビュー2の Ghidra プログラム上のアドレスは +0x100000)。実機には触れていない。解析は手元のイメージと GPL 一次資料のみ。

## 0. 要約

- 第4段([12](12_xcode_fw_drm_phase4.md))で発見された **+0x100000 ずれたアドレスビュー**を前提に、イメージを +0x100000 へマッピングした第2の Ghidra プログラム(以下 ghp5)を構築して自動解析した。ビューの担当範囲は**連続した領域ではなく、ライブラリ単位でベース0ビューと混在**する(§3.2)。
- アンカーである通信記述子初期化のジャンプ表をバイトレベルで検証し、このモジュールでは命令埋め込みの表アドレスと格納ジャンプ先の双方が「ファイルオフセット + 0x100000」であることを確定した(§3.1)。
- 通信記述子初期化(ファイル 0x1ADC38)をビュー2で完全に実読した: 記述子ストライド 0xF4、プロセッサ 7 個、各プロセッサに要素 0x2C(= `MIPSHOSTCOMPACKET` のサイズ)のパケットスロット配列 3 本(§4)。
- **DRM 文字列への参照がビュー2で解決し、DRMCTRL モジュールの実行コードに到達した**(§5)。[08](08_xcode_fw_drm_module_phase2.md) の「文字列 xref では実行コードに到達できない」は、ベース0ビューで復号した命令列の範囲でのみ正しい結論へ範囲を訂正する。到達したのは `drmctrl_open` 本体相当、OPEN_STREAM のペイロード変換と診断出力、"ScamScramble" の名前ベース呼び出し、AKE ラッパ(`gen_kauth` / `setexchgkey`)。
- 伝送層コマンド番号による中央ディスパッチ(スイッチ/静的ハンドラ表)は、両ビューで発見できなかった(探索範囲は §6)。到達した操作呼び出しは**操作名をキーとする名前ベース**の形を取る(§5.2)。
- SCRAMBLER ハンドラ本体と `control_words[24]` の処理、READ_FROM_OTP ハンドラには未到達。**(a)/(b) の境界と OTP の index 境界は未判定のまま**(理由は §7)。

## 1. 前提と注記(docs/12 の本文について)

- docs/12 のコミット済み本文は §4.1 の途中で終わっており(文の途中で切断)、§5 以降(ディスパッチ探索の詳細と +0x100000 ビューの実証節)はリポジトリ内の文書には残っていない。本段が前提とする「+0x100000 ビューの存在」は、docs/12 冒頭の要約記述と第4段の作業ログ、および本段 §3.1 のバイトレベル再検証に基づく。docs/12 本文の欠落自体は本段の判定に影響しないが、記録の欠落として明記する。
- コマンド番号の2層性・procIdx の配送先など第4段の確定事項は、GPL 一次資料(commsdk ヘッダとドライバソース)で本段でも再確認した: 伝送層番号は SCRAMBLER=37、SET_KEYSTORE_KEY=42、RESERVE=44、READ_FROM_OTP=45、OPEN_STREAM=8。SCRAMBLER のパケットは `control_words[24]` をペイロード先頭 +0x34 にインラインで含む(`cmd2_stream_scrambler`)。SCRAMBLER は CUST4 ビルド時に procIdx=6、それ以外は 0。SET_KEYSTORE_KEY(鍵 32 バイトをインライン複写)と READ_FROM_OTP(KeyIndex のみ)は procIdx の明示代入が無く既定の 0。

## 2. 方法

- ghp5: Ghidra 12.1.3 + ARCompact SLEIGH([11](11_xcode_fw_arc_tooling.md))。BinaryLoader で baseAddr 0x100000 にインポートし、シードとしてベクタ 5 件(+0x100000)、サンク表、記述子初期化(0x2ADC38)とそのジャンプ表ケース群、0x2ED500 レジストリ([09](09_xcode_fw_drm_phase3.md))のポインタ群(+0x100000)を置いてから自動解析した。
- 対照としてベース0のプログラム(第4段の ghp4)にも同一の探索スクリプト群を適用した。
- バイトレベル調査: 全域の u32 走査(2 バイト刻み・4 バイト整列の両方)によるポインタ候補の分布、整列ポインタの連続ラン、(番号, ポインタ)ペア表の走査。
- Ghidra スクリプトによる探索: 関数エントリが 10 個以上連続する表の走査(両プログラム、格納形式は両ビュー)、コマンド値比較とパケット +0x0C ロードのクラスタリング、個別のスカラ・参照照会、対象関数のダンプとデコンパイル。

## 3. ビューの切り分け

### 3.1 アンカー: 記述子初期化ジャンプ表のバイト検証(確定)

- 通信記述子初期化ループ(ファイル 0x1ADD80〜)は `ld.as r1,[0x2ade4c,r4]`(r4 はプロセッサ番号 0〜6)の後に `j_s r1` で分岐する。
- 表の実体はファイル **0x1ADE4C** にあり、7 エントリ `{0x2ADC7A, 0x2ADE68, 0x2ADDE8, 0x2ADFCA, 0x2AE138, 0x2ADDE8, 0x2AE29C}`。各値は「ファイル内ターゲット + 0x100000」である。裏付け: ターゲット 0x1ADDE8 はループのインクリメント命令そのもの(本文を持たない継続ケース)で、0x1ADC7A はループ頭の直前に位置する。一方、リテラル値が指すファイル 0x2ADE4C の内容は無関係な 16 ビットデータであり表ではない。
- よってこのモジュールでは、**命令に埋め込まれた表アドレスと、表に格納されたジャンプ先の双方**が +0x100000 ずれており、イメージ内絶対参照がビューでずれることがバイトレベルで確定した。第4段の「ジャンプ表で実証」という要約記述は正しい。

### 3.2 ビューの担当範囲: 連続範囲ではなくライブラリ単位の混在(確定)

- ビュー2で新たに参照が解決した関数は、ファイル 0x6772C・0x683B8(AKE ラッパ)、0xB6344(OPEN_STREAM 変換)、0xDC374(OPEN_STREAM 診断出力)、0x161520(`drmctrl_open`)、0x188A50・0x1F483C(ScamScramble 呼出)、0x1ADC38(記述子初期化)、0x22FC54・0x23FFC8・0x24A7E4(ストリーム管理)など、コード領域(0x8000〜0x2D3070)の全域に散在する。
- 一方、ベクタ表・サンク表・番号付き報告 API(ファイル 0x2B7E20)などはベース0ビューで整合する。両ビューのコードは PC 相対分岐(ビューに依らない)で相互に呼び合うため、**関数・ライブラリ単位でビューが混在する**のが実態であり、「ベース0の範囲 / +0x100000 の範囲」という単一境界線を引く仮説は棄却する。
- 規模の参考値: 関数の同定数は ghp4 で 1,881 件、ghp5 で 2,801 件。ただし復号できた命令バイト数や関数外(孤児)バイト数は両者で単調な優劣にならない(誤ったビューでも命令列自体は復号できてしまうため)。ビュー判定の根拠は規模ではなく、3.1 や §5 の個別の参照解決に置く。

### 3.3 RAM・ハードウェアアドレスはビュー不変(確定)

- 通信記述子配列の基底 **0xAFE000** は両ビューのコードが同じ値で参照する(命令スカラの出現は ghp4 で 251 件、ghp5 で 483 件。件数の差は復号できた命令列の差による)。0xBFE000(= 0xAFE000 + 0x100000)への参照は、u32 生値・命令スカラとも両プログラムで **0 件**。
- MMR の値(0xA0E8 等の補助レジスタアドレス)も両ビューで同値である。ずれるのはイメージ内(コード/データ)への絶対参照だけである。

## 4. 通信記述子初期化の実読(ビュー2で到達)

対象はファイル 0x1ADC38 の関数。ベース0では関数として同定されず孤児コードだったものが、ghp5 では本体 [0x1ADC38〜0x1ADE49] + [0x1ADE68〜0x1AE41D](間の 0x1ADE4C〜 は 3.1 のジャンプ表)として成立した。デコンパイルによる実読:

- 冒頭で共有 RAM のヘッダ部に 3 本のポインタを書く: 0xAFEB64 ← 0xAFE6B4、0xAFF940 ← 0xAFE7E8、0xAFF944 ← 0xAFE91C。
- ループ(i = 0〜6): 記述子[i] は基底 0xAFE000 + i × **0xF4**(ストライド 244 バイト)。フィールドは +0x08 = i、+0xF0 = 0xAFE6B4 + i × 0x2C、+0xF4 = 0xAFE7E8 + i × 0x2C、+0xF8 = 0xAFE91C + i × 0x2C、+0x10 = 0xFE3。要素サイズ 0x2C は `MIPSHOSTCOMPACKET` のサイズと一致する([09](09_xcode_fw_drm_phase3.md) §4)。すなわち各プロセッサに 3 本のパケットスロット配列が割り当てられる構造である。
- プロセッサ番号で分岐するジャンプ表(3.1)が、プロセッサごとの MMR マップを書く。ケース 0(proc0)は +0x0C = 0xA0E8、+0x14 = 0xA0EC、+0x18 = 0x423、+0x1C = 0x348、+0x24 = 0x800 など 0xA0xx / 0xB4xx 帯。ケース 1 は 0xA4xx 帯(+0x18 = 0x443、+0x1C = 0x3A0)。ケース 2 と 5 は本文を持たず、表の重複エントリ 0x2ADDE8(インクリメントへの合流)を共有する。
- 呼び出し元: ファイル 0x10AE86 の初期化シーケンス片からの呼び出しがビュー2で解決した(ベース0では呼び出し先が文字列領域を指すため追跡不能だった)。同片は続けて初期化 2 件(ファイル 0x18CA38、0x122E8)を呼び、記述子[0] の +0x04(値 0)を基底として MMR 0xA0E8 と 0xA0EC に値 8 を書く。

## 5. DRM 文字列参照の解決と到達した実行コード

[08](08_xcode_fw_drm_module_phase2.md) §4 の中核的な陰性(DRM 文字列のアドレスが 32 ビット値としてイメージ内のどこにも現れない)は、**格納値としての走査では今も正しい**(本段でも再確認: 文字列アドレスの u32 生値出現は 0)。しかし命令の即値(limm)としてエンコードされた参照は +0x100000 ずれた形で存在し、ghp5 では参照として解決した。したがって [08](08_xcode_fw_drm_module_phase2.md) の結論「文字列 xref では実行コードに到達できない」は、**ベース0ビューで復号した命令列の範囲でのみ正しい**ものへ範囲を訂正する。

### 5.1 OPEN_STREAM ペイロードの暗号関連フィールド(確定)

診断関数 0xDC374 の出力項目から、OPEN_STREAM ペイロード(先頭からのバイトオフセット)に次の暗号関連フィールドがあることが確定した:

- +0x884: `xcode_key_index`
- +0x888 / +0x88C: ENCRYPT 項目(input_encrypt_mode / output)
- +0x8A0: `securedts_mode`
- +0xD10: `numOfDecrypter`
- +0xD14: `decrypt_key_slot_id`
- +0xD24: `encrypt_key_slot_id`

これは第4段の「SECUREDTS は専用の伝送層番号を持たず、OPEN_STREAM のペイロード内の種別で表現される」という一次資料側の結論と、実読側で整合する。ペイロードが運ぶのは全てスロット番号・モードの類であり、鍵そのものは含まれない(ホスト側一次資料で `scramble_ctrl` が index 指定であることとも整合)。

### 5.2 名前ベースの操作呼び出し(ScamScramble の実読)

- 0x1F483C と 0x188A50 は、操作名 "ScamScramble"(24 バイトの名前欄)と引数ポインタ・フラグからなる局所記述子をスタックに構築し、対象範囲のキャッシュフラッシュ(ファイル 0x6D478 が 0x20 バイト境界ごとに 0x71238 を呼ぶ)を挟んで、名前キーで操作を引くヘルパ(ファイル 0xA19A4 / 0xA0744。ともに極小でデコンパイルは不成立)に渡す。
- 呼び出し元 0x19E550 は、2 つの大域変数を引数にこのラッパを呼び、クリアした後、16 エントリのイベントリングにコード 0x3AE を記録する。すなわちこの "ScamScramble" 呼び出しは、ホストコマンドの直接のハンドラではなく、ストリーム処理の内部状態機械から操作名で呼ばれる形を取る。
- 解釈(事実と分けて明記): 少なくとも DRM / スクランブル系の操作の一部は、静的な関数ポインタではなく「操作名 → 実装」の名前引きで結合されている。これが第2段以来、文字列・表のどちらの静的 xref からも実行コードへ到達できなかった構造的な理由の候補である。名前引きの対応表の実体([09](09_xcode_fw_drm_phase3.md) の 0x2ED500 レジストリとの対応を含む)は未同定。

### 5.3 未解決の表: ファイル 0x2D34E0 の {ポインタ, 0} × 16

- DRM 文字列群の近傍(ファイル 0x2D34E0)に、コードポインタと 0 のペアが 16 件並ぶ表がある。ポインタはファイル 0x156F90〜0x157C2C の関数群(0x156F24 を入口とするバッファ / ストリーム操作の一群)を指し、先頭の 0x156F90 が 3 回繰り返される(デフォルトハンドラ様のパターン)。
- この表への参照は、両プログラムの全復号命令に対する参照照会・両形式のスカラ照会のいずれでも発見できなかった(範囲: ghp4 / ghp5 の自動解析と個別シードで復号された命令列)。基底ポインタ経由(構造体のフィールドとして保持される等)の可能性が残り、表の性格は未確定。

## 6. 伝送層ディスパッチの再探索(陰性、範囲明記)

- 静的ハンドラ表: 両プログラムで「関数エントリが 10 個以上連続する u32 ラン」を全域走査し、ベース形式・+0x100000 形式とも **0 件**。52 エントリ級の静的ジャンプ表は、少なくとも Ghidra が関数と同定した入口への表としては存在しない。
- 比較分岐: パケット +0x0C(FunctionNumber のオフセット)のロードと、境界値(51 / 52)比較または computed jump が併存する関数は、両プログラムで発見できなかった(パターン探索の範囲)。コマンド値(8 / 37 / 40 / 42 / 44 / 45 等)との単独比較はイメージ全域に散在するが、実読で文脈を確認したものはいずれも別用途だった(代表例: ファイル 0x364DC の `cmp 0x2d` は文字 '-' の比較、ファイル 0x85AFC 付近の一群は書式値の判定)。
- 結果として、伝送層コマンド番号で振り分ける中央ディスパッチ本体は本段でも未同定。ただし第4段までと違い、今回は「ビューが原因で見えない」という説明は使えない(ビュー2で復号した範囲でも見つからなかった)。残る可能性は、(i) パケットはプロセッサ別に配送され、受信側はコマンドごとの登録 / ポーリングで処理する(静的表が実行時に構築される)、(ii) ディスパッチは本イメージの外(proc6 等)で行われる、(iii) 両プログラムでまだ関数外にあるコード領域の中に残る、のいずれかであり、未判定。

## 7. (a)/(b) 境界・OTP index 境界は未判定(理由)

- (a)/(b): SCRAMBLER ハンドラ本体に到達できず、`control_words[24]` が FW コードでどう処理されるかは本段でも実読できていない。よって「トークンの加工は FW コードか、そのまま HW / 他プロセッサか」は未判定のままである。本段で新たに分かったのは周辺構造までで、OPEN_STREAM ペイロードが運ぶのはスロット番号とモードのみ(§5.1)、スクランブル操作の呼出は名前ベース(§5.2)、一次資料では SCRAMBLER の配送先は procIdx=6(CUST4 ビルド時、[12](12_xcode_fw_drm_phase4.md))、という点に留まる。これらはいずれも (a)/(b) の判定材料としては間接的であり、判定には使わない。
- OTP の index 境界: READ_FROM_OTP ハンドラは未到達。イメージ内に "otp" / "OTP" を含む文字列は **0 件**で、文字列アンカーも使えない。[07](07_otp_value_level_stability.md) の実測(0x00–0x81 と 0xFF は値レベルで固定、0x82–0xFE は読み出しごとに揮発)に対応する FW 側の境界処理は未同定のままである。

## 8. 残件

- 名前引きの実体: 操作名 → 実装の対応表(実行時構築なら、その構築コード)の同定。0x2ED500 レジストリ([09](09_xcode_fw_drm_phase3.md))と 0x2D34E0 の表(§5.3)が候補として残る。
- proc6 側に SCRAMBLER の実処理があるか(本イメージが proc0 側であるという前提の検証を含む)。
- READ_FROM_OTP / SET_KEYSTORE_KEY の受信側処理が、名前引き・キュー登録のどちらで実装されているかの切り分け。
- 両ビュー混在を前提にした関数同定の継続(関数外コードは両プログラムとも残っており、特に ghp5 側は誤ビュー由来の復号も混ざるため、領域ごとの切り分けが要る)。

作業物(Ghidra プロジェクト ghp5、探索スクリプト群、census / 表走査 / ダンプの各ログ)は、開発側の作業領域 `2026-11-13-fw-drm/phase5/` に保存した。
