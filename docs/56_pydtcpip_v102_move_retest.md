- 資格情報の扱いは docs/48・50 の作法どおり (鍵は本人が `credentials.env` にだけ配置し、検証側のプログラムは値を見ない。消費は pydtcpip 本体のみで、当該ファイルはパスでのみ参照)。本書にも鍵の値・個体を特定できる値 (IP・MAC・シリアル等) は書かない。

## 2. 検証方法

- pydtcpip はチェックアウトを現行 master `66ff262` (v1.0.2) に切り替えて使用した。マージ `d71b5aff` と follow-up `9800e5b` が master に含まれることを祖先判定で確認済み。実行はチェックアウト同梱 venv (Python 3.15.2、作業ツリーを直接参照する editable 構成)。
- `discover` で機体がプロファイル `nasne` として自動選択されることを確認。録画一覧は救出ツールの列挙スクリプト (資格情報なし) で取得し、**最も小さいタイトルを1件** を検証対象に選んだ (HDD-B の 204 件はキャンペーン録画で、検証用の犠牲にできるもの)。
- move は公式 CLI を **作者指定の `--server` 経路** (デバイス記述 URL を指定し、プロファイル選択を効かせる形) で1回実行した。`--credentials` には既存の env ファイルをパスで指定し、`--verbose` の通信ログを保存した。
- move 後、列挙を再実行して対象タイトルのコピー数を独立に確認した。

## 4. follow-up 経路 (未認証再接続) の確認

本検証の主眼である「recorder 選択で Sony nasne が選ばれた場合に未認証の再接続を使う」経路について、コードと実走ログの両面で確認した。

- **コード経路**: CLI の move は `--server` で得た MediaServer を operations 層へ渡し、`reconnect_without_authentication` は `profile.uses_move_reconnect_without_authentication(description)` で決まる。`nasne` プロファイルはこれを `model_name == 'nasne'` のときに True と定義しており、本機 (modelName: nasne) では True になる。
- **動作の仕組み**: finalize / complete の送信前、MoveTransaction は保持している認証済み制御接続の EOF を確認する。nasne は AKE 完了直後に当該接続を閉じる (docs/51 §4 で実測確定) ため、閉じた接続は送信前に破棄され、コネクタ経由で張り直される。ポリシーが True の場合、コネクタは **AKE を行わず新規 TCP 接続だけを開く**。finalize はその未認証接続で送られ、保存済みの Move 鍵と同一 nonce で検証される。
- **実走ログの裏付け**: `--verbose` ログに現れる AKE シーケンスは冒頭の Move 認証の **1回だけ** で、finalize の前に2回目の AKE は現れない。また「応答なし→再接続」のログ行も無く、EOF の事前判定で再接続が送信前に済み、finalize は **1回の送信で受理** された。complete も同じ接続で受理された。
- **docs/51 §12 との対比**: PR ブランチ最終形の実走 (2026-11-21) では、最初の finalize が閉じかけの認証済み接続へ送られて無応答となり、「応答なし→再接続」の再試行が発動して未認証接続で受理された。今回は EOF が送信前に検出でき、再試行を経ずに未認証接続での送信が直接受理された。どちらの分岐でも最終的に finalize が未認証の新規接続で受理される点は同一で、接続の閉鎖タイミングの差による分岐の違いである。
- 結論: follow-up の制限 (未認証再接続は Sony nasne 選択時) は実機でも設計どおりに効き、PR #25 の欠陥 (finalize 無応答) は v1.0.2 では再現しない。

## 5. 消費したタイトルと件数変動の記録
