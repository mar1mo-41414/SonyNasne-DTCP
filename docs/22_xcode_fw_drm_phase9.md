# 22. XCode ファームウェア DRM モジュール解析 第9段 — proc4 要求処理ループの実読と proc6 設定初期化の追跡着手

第2 FW(メディア処理側イメージ)について、[docs/16](16_xcode_fw_drm_phase8.md) §7 の残件 1・2 を実施した記録(2026-11-14 実施)。残件 1 = `proc4_incoming_request_process` の要求処理ループ本体の実読(前提: スケジューラ呼び出し後段の関数境界復元)、残件 2 = proc6 のプロセッサ別設定セルへの書込み主体の追跡([docs/19](19_resumption_plan.md) トラック B の第 1・第 2 候補)。

**現在の到達点**:

- **proc4 の要求処理ループ本体を実読し、全体構造を同定した(残件 1 は完了)**。ループは共有メモリ上のリングキュー(要素 = {選択子, 要求記述子ポインタ} の 8 バイト)を読み、選択子 1–4 で 4 件の処理ブロックへ計算済み間接ジャンプで振り分け、各ブロックが「ワーカー(記述子の実処理)→ 転送器(結果の転送)」の対で構成される。Ghidra の関数範囲から漏れた原因は、OS プリミティブ `0xB04A28` への呼出しが CALL_TERMINATOR(noreturn 扱い)と誤判定され、後続ブロックが関数体に取り込まれなかったためと同定した(§3.1)。
- **このループは mhcmd のディスパッチではない**。proc4 の内部要求キューであり、転送器が使う転送番号 10 / 12 / 14 / 16 と mhcmd 番号体系との関係は未確定(§3.10)。ループとワーカーの実読範囲に DRM 系の文字列・処理は無かった(メディア処理という第8段の同定と整合)。
- **proc6 の設定セルの書込み主体を同定した(残件 2 は着手し、書込み主体まで到達)**。書込みはホストでも他プロセッサでもなく、**各プロセッサ自身がブート時に実行する初期化関数 `0xB0791C`** が、補助レジスタのプロセッサ識別子に応じて自分のセル(`0xCF0080` / `0xCF00A0` / `0xCF00C0`)へ自分用に確保した設定ブロックのポインタを書く(§4.3)。proc6 のタスク集合が proc4 と異なるかは、初期化へ渡るブート記述子の出所(唯一の呼び出し元 `0xB8BDE0`)の実読が次段の入口になる(§4.5)。

## 1. 対象と方法

### 1.1 対象

- 第2 FW 平文イメージ(ファイルサイズ 2,771,804 バイト、SHA-256 `a4ff86b2d7287356519d9955da2f26a4e886b79be7ae3aa212c9e2f0298a9c3a`、ISA = ARC 系、ロードベース `0xB00000`。[docs/05](05_xcode_firmware_images.md) / [docs/16](16_xcode_fw_drm_phase8.md) §3.1 で確定済みのものと同一ファイルであることを本段でも照合した)。
- タスク記述子表([docs/16](16_xcode_fw_drm_phase8.md) §3.7)を再走査して入口を再確認した: 表はファイルオフセット `0x1F1DC4`、6 レコード × `0x20` バイト {+0x00 ID, +0x04 入口, +0x08 スタックサイズ, +0x0C 優先度相当, +0x10 名前ポインタ, +0x14 末尾}。ID 12 = `proc4_incoming_request_process`(入口 `0xBC39A4`、スタック `0xC00`、優先度相当 `0x30`、名前は `0xCD126C`)。このレコード形状の表はイメージ全域走査でこの 1 件のみ。表の基底ポインタはファイルオフセット `0x206388`(アドレス `0xD06388`)に格納されている。

### 1.2 境界復元の手法(本段の実施内容)

Ghidra の既存プロジェクト(第8段の解析結果、2,595 関数 / 325,017 命令)を正とし、不足分を次の手法で補った。

- **M1 既知入口からの領域ダンプ**: タスク表で確定した入口を含む領域 `0xBC3800`–`0xBC4400` の全命令を、所属関数つきでダンプした。310 命令中 **165 命令が孤児(どの関数にも属さない)** で、同領域に交差する Ghidra 関数は 2 件(補助関数 `0xBC390C` と断片化した入口関数 `0xBC39A4`)のみだった。
- **M2 フレッシュインポートでの線形逆アセンブル**: 既存プロジェクトのデータ定義・フロー誤判定に引きずられないよう、イメージを新規プロジェクトへ分析なしでインポートし、指定アドレスから線形に逆アセンブルするスクリプトで、Ghidra がデータとして扱っていた範囲(`0xBC3A60`–`0xBC3A9B`、`0xBC3D84` 等)を命令として読み直した。これで計算済みジャンプとその遷移表が復元できた。
- **M3 プロローグパターンの census**: ARC の関数プロローグ(`st.a fp,[sp,-N]` 系のバイト列)を全イメージ走査し、孤児領域内の関数開始候補を列挙した。ループ直後の `0xBC3E58` に大きなレジスタ退避を伴うプロローグがあり、次候補は `0xBC5162` だった(この間の関数分割は未実施、§5)。
- **M4 同型ブロックの反復パターン認識**: 致命的エラー記録マクロ(定数 `0xDEADC0DE` の書込みを含む定型)とチェックポイント登録の定型を署名として、コード断片の同型性を判定した。
- **M5 組み込みデータと命令の分離**: アラインされたワード列がコード域内アドレスを指す場合に遷移表と判定した(§3.3 の表は間隔・指し先の規則性で検証)。
- **M6 スカラ参照 census**: 特定アドレス(設定セル `0xCF0080` 等)を即値・参照として含む命令を全命令から検索し、読み手と書き手を分離した(§4.2)。基礎プリミティブの実読にはデコンパイルを併用した。

## 2. (前提の再確認)プロセッサ別設定セル

[docs/16](16_xcode_fw_drm_phase8.md) §3.9 のとおり、設定ポインタセル `0xCF0080`(識別子 3)/ `0xCF00A0`(4)/ `0xCF00C0`(6)は静的イメージ内では全て 0 で、指す先の設定構造は実行時初期化である。本段 §4 で書込み主体を同定した。

## 3. proc4 要求処理ループの実読

### 3.1 Ghidra の関数範囲から漏れた原因(事実)

- 入口関数 `0xBC39A4` の Ghidra 関数体は 4 断片 [BC39A4–BC3A5F] / [BC3A9C–BC3B13] / [BC3D88–BC3DDB] / [BC3E1C–BC3E55] で、間の 3 区間が未所属だった。
- 断片の切れ目はいずれも OS プリミティブ `0xB04A28` への `bl` の直後である。同呼出しは Ghidra 上で flow = CALL_TERMINATOR(noreturn 扱い)になっており、復帰後の命令が到達不能として関数体から落とされていた。
- しかし `0xB04A28` 本体のデコンパイルには通常の return 経路が複数存在し(§3.8)、呼出し直後には意味のある命令列(§3.3 の振り分け計算)が続く。**noreturn 扱いは解析上の誤判定であり、ループ本体はこの誤判定で孤児化していた**と判断する(根拠: 本体の復帰経路の実在 + 呼出し直後の命令列が §3.3 の遷移表と整合すること)。

### 3.2 ループ全体構造(事実)

ループは 1 つの関数体(`0xBC39A4` から `0xBC3E55` まで、途中の中断のないマクロ展開を含む)であり、構造は次のとおり。

1. **入口処理**: フレーム構築後、チェックポイント登録(§3.5)、プロセッサ状態ワードの確認(§3.8 の `0xB04940`、非 0 なら致命的エラー経路)。
2. **ループ先頭 `0xBC3A00`**: チェックポイント登録、`0xB0497C`(§3.8)呼出しの後、キュー文脈(アドレス `0x1483840`、共有 RAM 域)の 2 ワードを読む: +`0x100`(書込み側ポインタ)と +`0x104`(読み側ポインタ)。
   - **一致(キュー空)**: 登録・譲渡経路 `0xBC3D88` へ。現行タスク制御ブロック(§3.8 の `0xB05710` で取得)へマジック `0xABCD00F1` を +`0x8` に書き、スケジューラプリミティブ `0xB04B00` を呼び、復帰後にチェックポイント登録と状態確認を経て合流点 `0xBC3DDC` へ。
   - **不一致(要素あり)**: チェックポイント登録、状態確認の後、`0xB04A28` を呼び、振り分け(§3.3)へ。
3. **合流点 `0xBC3DDC`**: チェックポイント登録、状態確認(非 0 なら致命的エラー記録ブロック `0xBC3A9C`)、問題なければループ先頭 `0xBC3A00` へ戻る。

### 3.3 キューと振り分け(事実)

- デキュー関数 `0xC4E450`(第 1 引数 = キュー文脈、第 2 引数 = 出力先 2 ワード)の実読: 読み側ポインタ(+`0x104`)と書込み側ポインタ(+`0x100`)が一致すれば -1 を返す。一致しなければ読み側の指す 2 ワードを出力先へ複写し、読み側を +8 進める。基底ポインタは文脈 +`0x108`、リング容量は `0x100` バイトで回り込む。すなわち**要素は 8 バイト × 最大 32 個のリングキュー**で、要素 = {第 1 ワード: 選択子, 第 2 ワード: 要求記述子へのポインタ}。
- 振り分け計算(`0xBC3A60`–`0xBC3A88`、M2 で復元): 選択子から 1 を引き、3 以下でなければ(選択子が 1–4 の範囲外なら)合流点へ直接分岐(`0xBC3D84` → `0xBC3DDC`)。範囲内なら遷移表 `0xBC3A8C` から `表[選択子-1]` を読み `j r8`(計算済み間接ジャンプ)する。
- 遷移表(アドレス `0xBC3A8C`、4 ワード): `0xBC3B14` / `0xBC3BB0` / `0xBC3C4C` / `0xBC3CE8`。間隔は全て `0x9C` で、§3.4 の同型ブロックの開始点と一致する(M5 による検証)。

### 3.4 4 件の処理ブロック(事実)

各ブロック(`0x9C` バイト)は同型で、次の定型からなる。

1. **ワーカー呼出し**: 記述子ポインタを引数に、ブロック固有のワーカーを呼ぶ。
2. チェックポイント登録(§3.5)。
3. 状態確認 `0xB04940`: 非 0 ならブロック内の致命的エラー記録コピーへ(§3.5)。
4. 0 なら第 2 チェックポイント登録、`0xB0497C` 呼出し、記述子の第 1 ワードを読み、**転送器**を呼ぶ。
5. 合流点 `0xBC3DDC` へ分岐。

| 選択子 | ブロック | ワーカー | 転送器 | 転送番号(§3.7) |
|---|---|---|---|---|
| 1 | `0xBC3B14` | `0xC44728` | `0xC45BEC` | 10 |
| 2 | `0xBC3BB0` | `0xBE96E8` | `0xC45C8C` | 12 |
| 3 | `0xBC3C4C` | `0xC6B03C` | `0xC88318` | 14 |
| 4 | `0xBC3CE8` | `0xC6B5AC` | `0xC6D5A8` | 16 |

### 3.5 チェックポイントと致命的エラー記録(事実)

- チェックポイント登録の定型: 現行タスクのスロットインデックス(取得関数 `0xC8B5E0`、§3.8)を `0x50` 倍した位置の表(基底 `0x100608`、副基底 `0x10060C` / `0x100630` / `0x100634`)へ文脈値と現在 PCL を書き、別表(基底 `0x101C20`、ストライド `0x10`)へブロック開始時に捕捉した PCL を書く。タスクごとの実行位置の記録であり、ウォッチドッグ的な死活記録とみられる(解釈)。
- 致命的エラー記録の定型: レコード {`0xDEADC0DE`, PCL, SP, タスクインデックス} を **`0x100530` と `0x530` の両方**へ書く(第2 FW 内でも +`0x100000` の二重ビュー書込みが使われている事実)、致命的エラー処理 `0xB04900` を呼び、無限ループで停止する。この定型のコピーがループ内に少なくとも 6 組存在する(入口、合流点、各ブロック内ほか)。

### 3.6 ワーカー 4 件の実読(事実と解釈の区別つき)

- **ワーカー 1 `0xC44728`**: 記述子のバイトフィールド(+`0x14` モード、+`0x15`–+`0x1A`)とバッファポインタ(+`0x4` / +`0x8` / +`0xC` / +`0x10`)を読む。モード値 0 / 1 / 2 で分岐し、サイズを バイト積 × `0x10` および × 4 で計算してバッファ登録関数 `0xB049D8` へ渡し、HW 設定関数 `0xC93DD0`(引数 `0xB1B0`, `0x10052006`)/ `0xC93D78` を呼ぶ。実読した範囲ではフレームバッファの形状設定(マクロブロック単位の幾何)と解釈できる。
- **ワーカー 2 `0xBE96E8`**: 記述子 +`0x3C` のフラグで分岐。0 なら幾何の和(+`0x1C`+`0x24`、+`0x24`+`0x20` 等)を引数に処理関数 `0xB91A3C` を呼ぶ。非 0 なら記述子フィールドを局所構造体へ詰め替えて `0xBD52D0` へ渡し、負の戻り値ならエラー報告 `0xB8EA08`(コード `0xCC`)を呼ぶ。
- **ワーカー 3 `0xC6B03C`**: 記述子のポインタ・オフセット対(+`0x4`–+`0x30` の 6 対)と寸法(+`0x34` / +`0x38`、後半の対では 1/2 にして使用)を引数に、領域設定関数 `0xBCE0DC` を 6 回呼ぶ。複数プレーン/領域の一括設定と解釈できる。
- **ワーカー 4 `0xC6B5AC`**: 本体約 `0x1A20` バイトの大きな処理で、バイト/ハーフワード単位のデータ操作が主体。画素形式変換類の処理とみられるが、本段では先頭部の性格確認までで詳細は未読(§5)。

いずれのワーカーの実読範囲にも、DRM・鍵・OTP に関する文字列参照や処理は無かった(第8段 §3.4 の「メディア処理専用」の所見と整合する範囲の観測であり、ワーカー 4 の未読部分については断定しない)。

### 3.7 転送器 4 件の同型性(事実)

4 件の転送器は定数だけが異なる同一テンプレートである。

- カウンタ `0xCF88E0` を +1 し、直近の記述子ポインタを `0xCF88DC` へ保存する。
- パケット取得関数 `0xBF6E00`(転送番号 N, `0x40003`)でパケットを得て、パケット +`0x14` のポインタ先へ記述子の第 1 ワードを書く。
- 送信関数 `0xC5C8A4`(記述子第 1 ワード, N, パケット, 0, 0, `0x40003`)を呼ぶ。成功(0)ならカウンタ `0xCF88E4` を +1 して 0 を返し、失敗なら 2 を返す。
- 転送番号 N は選択子 1–4 に対して **10 / 12 / 14 / 16**(偶数、刻み 2)。定数 `0x40003` は取得・送信の双方で共通。

### 3.8 OS プリミティブの同定(事実)

ループが使う基礎関数の実読結果。

- `0xB04940`: 現行プロセッサの設定構造(後述の識別子ディスパッチで取得)の +`0x18` ワード(状態/エラー相当)を返す。ループでは「非 0 = 異常」として致命的エラー経路のゲートになっている。
- `0xB0497C`: 設定構造 +`0x1C`(現行タスク制御ブロックへのポインタ)経由でタスク +`0x68` のカウンタを +1 する(0 の場合は補助レジスタへ設定 +`0x16` の値を書いてから)。タスクの tick/ハートビート相当(解釈)。
- `0xB04A28`: タスク +`0x68` のカウンタを -1 し、0 に達したら設定 +`0x18` の状態に応じ補助レジスタへ設定 +`0x1A` または別タスク経由の値を書く。**通常の return 経路を持つ**(§3.1 の根拠)。スケジューラのタイマ再装填・譲渡側のプリミティブ(解釈)。
- `0xB04B00`: スケジューラ/文脈切替プリミティブ(第8段 §3.8 で実読済みの範囲に、設定セル切替とタスクリスト操作を確認)。
- `0xB05710`: 現行タスク制御ブロックの取得(設定 +`0x1C` の指す先を辿る)。制御ブロックのフィールド: +`0x8` 初期化マジック(`0xABCD00F1`)、+`0x14` スタックポインタ保存、+`0x68` カウンタ。
- `0xC8B5E0`: 戻り値が per-task 表のインデックスとして使われる取得関数(現行タスクのスロットインデックス、解釈)。
- 設定構造の取得は全プリミティブ共通で、補助レジスタ(IDENTITY)の識別子(ビット 15–8)でセルを選ぶ: 3 → `0xCF0080`、4 → `0xCF00A0`、6 → `0xCF00C0`(それ以外の識別子では `0xCF00A0` 側に落ちる実装)。設定構造の判明したフィールド: +`0x16` / +`0x1A`(補助レジスタへ書く値)、+`0x18`(状態ワード)、+`0x1C`(現行タスク制御ブロック)、+`0x234`(異常時用タスク相当へのポインタ)。

### 3.9 [docs/16](16_xcode_fw_drm_phase8.md) §3.8 の記述の精密化

第8段 §3.8 は入口の初期化部だけの実読で、カウンタ対について「一致を確認し(不一致なら致命的エラー)」と書いた。本段のループ全体の実読では次のとおりであり、§3.8 の記述はこの範囲で精密化される。

- カウンタ対の実体はリングキューの読み/書込みポインタであり、**不一致は「要素あり」の通常経路**(振り分けへ進む)、**一致は「キュー空」の経路**(タスク登録とスケジューラ譲渡)である。
- 致命的エラー経路のゲートはカウンタ対ではなく、`0xB04940` が返すプロセッサ状態ワード(+`0x18`)の非 0 である。

### 3.10 mhcmd との関係(未確定)

- このループは proc4 のタスク内要求処理であり、ホストとの mhcmd 配送(H2M パケット、procIdx 振り分け、[docs/12](12_xcode_fw_drm_phase4.md) / [docs/16](16_xcode_fw_drm_phase8.md) §3.1)とは別の層である。リングキューへの投入側(書込みポインタを進める主体)は本段では同定していない(共有 RAM 域 `0x1483840` への他タスク/他プロセッサからの書込みが想定されるが未確認)。
- 転送器の転送番号 10 / 12 / 14 / 16 と定数 `0x40003` が mhcmd 番号体系・procIdx とどう対応するかは未確定。転送先の同定には送信関数 `0xC5C8A4` と取得関数 `0xBF6E00` の実読が要る(§5)。

## 4. proc6 設定初期化の追跡(着手結果)

### 4.1 ホスト側の切り分け(事実、範囲つき)

GPL 一次資料のホストドライバで第2 FW のロード関数 `Down_Load_Embedded_Second_Mips_Prog` を実読した。同関数の実体(暗号化版/平文版とも)は「イメージをフレームバッファメモリのオフセット `0xB00000` へコピーし、必要なら復号する」処理のみで、**プロセッサ別設定への書込みはこの関数には無い**。ホスト側の他の初期化経路まで全て否定するものではないが、少なくとも FW ロード経路は設定の書込み主体ではない。

### 4.2 設定セルの参照 census(事実)

M6 でセル 3 件(`0xCF0080` / `0xCF00A0` / `0xCF00C0`)を含む命令を全命令から検索した結果、ヒットは 305 件。大半は §3.8 の識別子ディスパッチによる**読み出し**(`ld`)で、OS プリミティブ群(`0xB04940` / `0xB0497C` / `0xB04A28` / `0xB04B00` / `0xB05710` / `0xB0582C` ほか)に集中する。セルへの**書込み**(`st`)として同定できたのは、基底 `0xCF0060` + オフセット `0x20` / `0x40` / `0x60`(= セル 3 件)への書込みを持つ **関数 `0xB0791C` のみ**だった(この census は即値・参照で辿れる書込みの範囲であり、計算済みアドレッシングの書込みの不在を証明するものではない。ただし §4.3 の実読で同関数の役割が裏付けられた)。

### 4.3 書込み主体 `0xB0791C` の実読(事実)

- 同関数は補助レジスタのプロセッサ識別子で分岐する**各プロセッサ自身のブート時初期化**である。処理の骨格:
  1. ブート記述子(引数。第 1・第 2 ワードの範囲)から設定ブロックのサイズ相当量を計算する(識別子 3 / 4 では ×1 相当、6 では ×2 相当のスケール)。
  2. 確保関数 `0xB87A44`(引数 `0x13A8000`、ヒープ基底相当)で領域を確保し、32 バイト境界に整列したアドレスを得る。
  3. **自分の識別子に対応する設定セルへ、そのアドレスを書く**(3 → `0xCF0080`、4 → `0xCF00A0`、6 → `0xCF00C0`)。
  4. 設定ブロックを初期化する: 初期化関数 `0xB09060`(サイズ `0x494`)、`+0x21C` のビット設定、ブート記述子から `0x30` バイトを +`0x100` へ複写、`+0x104` へ自己ポインタ、`+0x108` のマスク処理、副次確保(`0xB09354`、サイズは最低 `0x134` + `0x20`)と +`0x60` への終端アドレス書込み等。
- すなわち [docs/16](16_xcode_fw_drm_phase8.md) §3.9 の「設定セルは実行時初期化で静的に引けない」の実体は、**第2 FW 自身のブートコードによる自己初期化**であり、書込み主体はホストでもブート側の外部コードでもなく本イメージ内の `0xB0791C` だった。

### 4.4 呼び出し元(事実)

`0xB0791C` への xref は 1 件のみ: 関数 `0xB8BDE0` 内の呼出し(`0xB8BDE2`)。同関数がブートスタブ側の経路(第8段 §3.2 のブートスタブとの関係は未確認)であり、ブート記述子(引数)の出所はここにある。

### 4.5 見通し(次段の入口)

1. `0xB8BDE0` の実読: ブート記述子の出所(静的データか、他プロセッサ/ホストから渡る値か)と、`0xB0791C` へ渡る時点でプロセッサごとに異なる値が含まれるかを確認する。proc6 のタスク集合が proc4 と異なる場合、その分岐はブート記述子か設定ブロック初期化(+`0x100` への `0x30` バイト複写入り)に現れるはずである。
2. 設定ブロックの +`0x1C`(現行タスク)以外のフィールド、特にタスク表ポインタ相当のフィールドの同定: proc ごとのタスク表が設定ブロック経由で切り替わるなら、proc6 用タスク表の静的列挙が可能になる。
3. それでも SCRAMBLER ハンドラ自体は未同定のままである。本段の成果は「proc6 のパーソナリティが本イメージ内にあるなら、その選択は `0xB0791C` + ブート記述子の経路で決まる」という追跡範囲の確定であり、ハンドラの不在を意味しない。
