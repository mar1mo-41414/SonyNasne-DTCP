# 03. 再生経路と復号オラクル

録画の鍵がホストに存在しない([docs/02](02_dat_encryption_model.md))以上、回収の現実的な経路は「**実機のチップ自体を復号オラクルとして使う**」方向になる。本書は、再生経路の静的追跡、オラクル化の可否、実験 E1〜E4 の設計と、E3(Tp 再生中の平文採取)の準備・初回実測を記録する(2026-11-12 実施、2026-11-13 に本リポジトリへ移行・再構成)。

**現在の到達点**: Tp(リモート視聴)経路では平文 TS がホストメモリにステージされる設計であることが静的に確定した。ただし E3 の初回実測では、再生中のヒープ側候補バッファは全て null パケットのままで、平文の常駐は確認されなかった。棄却の範囲は限定されており、次はデバイス共有バッファ(rw-s)側の走査が残件である。

## 1. 再生経路マップ

dtvtuner のストリーム open は単一のディスパッチャに集約される(webapi は同型)。逆コンパイルで確定した構造:

- 引数のストリーム文脈が内部文脈へ複写され、文脈フィールドが 0 でない場合は**ソフトウェア経路**(送受信リングバッファを確保しワーカースレッドを起動する)へ、0 の場合はチップ側 open へ進む。
- チップ側 open はカテゴリで分岐する: **0 = OPEN_LOCAL、2 = OPEN_TS、1 = OPEN_CAPTURE、その他(3)= SECURED 系**。未知カテゴリはエラー。
- OPEN_GENERIC のラッパーのパケットレイアウトも確定した: バイトオフセット 0xAC のワードが `generic_mode`、要求サイズはその直後のワード対、コマンド番号は 0x2E、タイムアウト 2000、戻り値はストリームハンドル。これにより、観測で見ていた「GENERIC 引数 +0xAC に `0x200`」は **`generic_mode = GENERIC_MODE_DTCP`(0x200)の GENERIC open** だったことが静的に確定した。
- GENERIC のモード制限付きヘルパーはモードとして **{0x200(DTCP), 0x2000(IVDR), 0x4000(AES)} のみ受理**し、それ以外を弾く。このヘルパーの呼び出し元を全数追跡した結果、**確定できた直接呼び出しはすべて 0x4000(AES)** であった(8 箇所、要求サイズ 0xFC00 / 0xE100 / 0xF000)。0x200 を渡す呼び出しは静的に同定できていない(ヘルパー自体へのテーブルディスパッチ経由の参照が存在し、そこからの呼び出しは未解決)。
- B-CAS 用途は専用の別経路で、MULTI2 復号クラスが **モード 0x400(GENERIC_MODE_BCAS)、サイズ 0x10000/0x10000、ホスト可視バッファ付き** で GENERIC を開く — **復号結果がホストバッファへ出る構成が製品内に実在する**ことの実例として重要である(MULTI2 は放送側のスクランブルであり保存保護とは別物だが、「チップ復号 → ホスト平文出力」という形自体はファームウェアが受理する)。

経路ごとに、平文がどこへ出るかを整理する:

1. **ライブ視聴・録画入力**: チューナー入力は SECUREDTS(0x30)で復号され、**平文 TS がホストへ出る**。自作の受信ツールが既に利用している実証済みの経路(暗号化されているのは放送のスクランブルであり、保存保護とは無関係)。
2. **録画保存**: `.dat` への書込みは dtvtuner 本体のポンプが行う。保存段の実形態は [docs/02](02_dat_encryption_model.md) §9 のとおり SECUREDTS + GENERIC-AES で確定した。
3. **DTCP-IP 配信(通常再生)**: ホストが `.dat` を読み、**LOCAL ストリーム(0x10)** を SOURCE モード(EMI + MoveLabel 設定、SRM 検証/設定あり)で開いて流し込む。**ホストが受け取るのは PCP 暗号化されたデータのみ**であり、それを HTTP で送る。復号と DTCP 再暗号化はチップの同一ストリーム内で結合されており、**この経路では平文はホストに出ない**([docs/01](01_dtcp_firmware_analysis.md) §4)。
4. **Tp リモート視聴**: §2 のとおり、3 とは構造が異なり、**平文がホストメモリにステージされる設計**である。
5. **webapi / procmng**: webapi は同一 SDK スタックの複製を持ち自前の配信・API 用途に使うが、録画暗号化に固有の役割は見つからなかった。procmng はストリーム open を一切行わない。AV ドライバを開けるのが dtvtuner / webapi / procmng の 3 プロセスだけ([docs/02](02_dat_encryption_model.md) §7.2)で、データプレーンの候補は dtvtuner と webapi に限られる点も変わらない。

## 2. Tp 経路では平文がホストメモリにステージされる(静的確定)

dtvtuner 内の Tp 配信クラスを同定し、その内部構造を確定した。

- ファクトリ関数のシンボル名がプロジェクト内に残存しており、**`TpStreamSource::Create(TpStreamType, TpStreamSource**)`** と同定できた。type=1 のときシングルトンとして、コンストラクタで **0xFCE8 バイト** のオブジェクトを生成する。vtable の直後にある RTTI 名から、実装クラスの実名は **TpStreamSourceImpl** である。
- コンストラクタの所見: (a) オブジェクト内に **0xFC00 バイト(= 192 バイト × 336 パケット)の TS ステージングバッファ** を内蔵し、null パケットのテンプレート(同期バイト 0x47、PID 0x1FFF 相当のヘッダ、残り 0xFF 埋め、192 バイトストライド)で初期化する。(b) サブオブジェクトを介して **GENERIC セッションを AES モード(0x4000)、要求サイズ 0xFC00 で開き**、そのバッファ情報をオブジェクト内に保持する。(c) イベントオブジェクトを 2 つ生成する。
- tpkeydec の開封はこのクラスのメソッドだった: vtable のメソッドが `/dev/tpkeydec` を開き、ioctl(cmd=0)で blob を開封し、得た **16 バイトの鍵をオブジェクト内に格納** する([docs/01](01_dtcp_firmware_analysis.md) §5 の構造と一致を再確認した)。
- 入力設定メソッドは、コンテンツを識別する**文字列**を受け取り、ID 群へ分解してオブジェクト末尾のフィールド群に保持し、内部パス文字列を解決する。すなわち TpStreamSource の入力は「コンテンツ ID 指定」であり、実データの読み出しは後段のストリーミング処理側にある。
- dtvtuner 自身の暗号能力を追加確認した: libcrypto からの import は EVP_sha1 のみで、**バイナリ内に AES のテーブル類も SHA-256 定数も存在しない**。したがって dtvtuner のユーザーランドコードはバルク AES を実行できず、Tp の配信暗号化は上記 (b) の**チップ側 GENERIC-AES セッション**が担う。ホストの役割は、鍵(tpkeydec で開封した 16 バイト)の供給と、データのステージングである。

**判定**: Tp 経路は「**ホストが開封済みの鍵と TS ステージングバッファを持ち、暗号化だけをチップに委ねる**」設計であり、Tp セッション中の TS は暗号化直前の形でホストメモリ上にステージされる構造であることが静的に確定した。DTCP-IP 経路(平文が出ない)とは対照的である。

残る未確定は 1 点: そのステージに載る TS が、録画再生時に「保存暗号化の復号段を出た直後の平文」なのか、それとも復号段と Tp の間に別のチップ内結合があるのかは、TpStreamSource へ TS を供給する上流側の追跡が未完のため静的には決まらなかった。ただし DTCP-IP と違い、Tp にはホスト側に鍵もバッファも実在する以上、**オラクル化の第一候補は Tp 経路**で確定とし、決着は動的観測(実験 E3)に委ねる。

## 3. オラクル化の可否と壁

- **直接の経路は存在しない**: 「保存済み `.dat` を指定して、復号結果をホスト可視の形(バッファ/ファイル/ネットワーク)で受け取る」というホスト API の形をした経路は、Sony ユーザーランドの使用実態の中には存在しなかった。製品の再生経路は、平文を出さない DTCP-IP と、ホスト介在だが目的が Tp 配信に固定された Tp の 2 本である。
- **壁の特定**: (1) 保存鍵はファームウェア管理で、ホストはスロット番号しか触れない。(2) DTCP-IP 経路は PCP 暗号文のみを出力するよう結合されている。(3) 最大の壁は、**「保存復号 → 平文をホストバッファへ出力」というストリーム構成を製品ファームウェアが受理するか否か**であり、これはファームウェア側のポリシーの問題であって、ホスト側コードの解析からは決定できない。
- **可能性の根拠**: SDK の部品は揃っている(LOCAL の出力暗号化モード = NONE と TS のホスト出力、GENERIC のホスト共有バッファ、システムキーのスロット参照)。BCAS 経路は「チップ復号 → ホスト平文出力」の製品実例である(§1)。Tp 経路は平文ステージングの構造実例である(§2)。よって「ファームウェアが保存コンテンツについて平文ホスト出力を拒むかどうか」だけが未測の一点であり、これは実機で構成を試せば直接判定できる。
- **結論**: オラクル化は「製品経路の転用では届かないが、実験で決着する」段階である。

**方針**(プロジェクトとして決定済み):

- **本線**: 実機チップ自体を**復号オラクル**として使う方式(再生経路で平文を取り出す)。
- **副線**: 「鍵だけ抜いて PC で復号」の道も**諦めない**。「到達不能」の判定は現時点の結論として残すが、研究線としては閉じない。分岐点はシステムキーの出自であり、読み取り可能な材料からの導出(KDF)なら副線が復活し、OTP 封印のみなら復活しない([docs/02](02_dat_encryption_model.md) §8)。
- オラクル方式の想定形: **HDD の録画領域(p3)を無傷のまま起動できる環境(embed 方式)で、XCode に `.dat` を復号させ、復号された TS をネットワーク経由で PC へ抜く**。実行環境の候補として embed(Debian ユーザーランド一式が使える)を本命としつつ、公式ユーザーランド上で自前バイナリが root で動く観測ビルド環境を安全側の実験環境として併用する。

## 4. 実機実験の設計(E1〜E4)

**安全条件(全実験共通)**: 入力は必ず `.dat` のコピー(p3 原本には触れない)。sys1 / SPI への書込みなし。版数(カスタム `.dlm` の版フロア)を消費しない。実験前後で対象タイトルの原本ハッシュを照合する。

**E1 — READ_FROM_OTP 走査(副線の分岐判定)**: dtvtuner の発行手続きと同じ手順(ドライバ open → GENERIC を RSA モードで open → コマンド 0x116 を KeyIndex 0..255 で発行 → close)を自前プログラムで実装し、インデクスごとの **成否 / ゼロか非ゼロか / 再起動を跨いだ安定性** のみを記録する。返却値そのものは記録にも作業素材にも残さない(安定性はその場のハッシュ比較で判定し、生値は破棄する)。→ **実施済み**。結果は [docs/02](02_dat_encryption_model.md) §11(全 index が受理され、zero 85 / nonzero 171。再起動間の安定性は未実施)。

**E2 — 直接オラクル試験(ファームウェアの受理ポリシー測定)**: 既知タイトルの `.dat` 先頭セグメント(数 MiB)のコピーを入力に、候補構成を順に試す: (a) OPEN_LOCAL で入力暗号化モード = DTCP、出力 = NONE、復号システムキーのスロット候補群、TS 共有入出力。(b) OPEN_GENERIC をモード 0x200(DTCP)で開き共有バッファで入出力。(c) OPEN_LOCAL の入力 = CUSTOM_DRM 系。各構成について、open の成否、出力の TS 同期構造(0x47 の 192 バイト周期)と PAT/PMT の有無、出力が入力と同一(素通り)か高エントロピー(未復号)かを記録する。1 つでも平文 TS が出ればオラクルは API レベルで成立する。→ **実施済み**(形を変えて、録画時 CW を使う構成で実施)。結果は [docs/02](02_dat_encryption_model.md) §12(器の自己検証は成立、単純ミラーは棄却。未実施の試行も同節に残した)。

**E3 — Tp 経路の動的確認(本線の本命判定)**: 実タイトルの Tp 再生セッションを発生させ、その間、TpStreamSource シングルトンのステージングバッファ(オブジェクト先頭 +0x70 から 0xFC00 バイト)を `/proc/<pid>/mem` で周期サンプリングし、null パケットでない実コンテンツの TS 構造(0x47 周期)が現れるかを見る。併せて、ネットワーク送信直前のペイロードを分類(TS 構造か高エントロピーか)する。平文が確認できれば、回収方式は「Tp セッションを駆動しつつバッファを連続読みする」形で設計できる。→ 準備と初回実測まで実施済み(§5〜§7)。

**E4 — 復号パイプラインの速度(全実験で併せて測る論点)**: 方式の実用性は速度で決まるため、E2/E3 のそれぞれでスループット(MB/s)を必ず実測する。論点は 2 つ: (i) チップの暗号処理は同時多重録画に耐える DMA 級の設計であり、E2 型のバルク構成が通れば**実時間より大幅に速い**可能性がある。(ii) E3 型(再生セッション転用)は原則**実時間(1 倍速)縛り**であり、早送り等のトリックプレイで倍率が上がるか、上がった場合にホスト側のステージング/読み出しが追随するかも測る。見積りの基準として、対象タイトルの `.dat` 実バイト数と録画時間から TS レートを出し、所要時間 = ファイルサイズ / 実測スループット、の形で記録する。

## 5. E3 の準備 — 採取ツール memscan と対照走査

### 5.1 ツール memscan

- 仕様: 対象プロセス/スレッドのメモリマップを読み、書込み可能領域を走査する。既定では perms が private(p)の領域のみが対象で、ヒープ・匿名領域・スタック・ライブラリ data が入り、デバイス backed と共有メモリ(いずれも rw-s)は除外される。各位相(offset mod 192)ごとに同期バイト 0x47 の連続を数え、一定パケット数以上連続した run を候補として報告する。上位候補については統計のためだけに窓を再読し、同期パケット数・相異なる PID 数・null パケット(PID 0x1FFF)数・非 null 数・ペイロード 0xFF 埋めパケット数を数える。**内容バイト列そのものは表示・保存しない**(記録はアドレス・サイズ・統計のみ)。
- 本カーネル(2.6.29)では `/proc/<pid>/mem` はアタッチなしでは読めなかったため、手順は ptrace アタッチ → 停止確認 → 読み取り → デタッチ。**非リーダースレッドの停止確認には waitpid への `__WALL` 指定が必要**だった(無いと停止確認がタイムアウトすることを実測し、修正後に成功した)。停止確認がタイムアウトした場合はデタッチして何も読まずに終了する。
- 検証(偽対象プロセスでの照合): 仕込んだ TS 形状バッファ(336 パケット × 複数面、約 300 マッピング・118〜185MB のプロセス)について、再読統計が仕込んだ値と完全一致し、全ての面を正確に検出した。読み取りスループットは約 26〜31MB/s(/proc 経由の読み出し速度。E4 の基礎値)。

### 5.2 事故と運用ルール(重要)

- 初回の対照走査で、dtvtuner の**リーダースレッド**にアタッチし、全 rw 領域(デバイスの 64MB マッピングを含む)を走査したところ、ツールが走査中に SIGSEGV で死亡した。アタッチは自動解除されリーダーは復帰したが、**約 80 秒後に機体が再起動した**。機序は未確定だが、「リーダーの停止(約 3 秒)が監督側のハートビート/ウォッチドッグを欠落させ、遅延して再起動に至った」が最有力の説明である。ツールの SIGSEGV の原因も未確定(§5.1 のスケールテストでは再現しなかった。残る差分は、稼働中プロセスのメモリ変動と、rw-s / デバイス backed 領域を含めたこと)。
- **運用ルール(本節で確立): dtvtuner のリーダーには二度と ptrace アタッチしない。アタッチは非リーダーのワーカースレッドに限定し、走査対象は rw-p 領域に限定する。** この方式での対照走査は無事故で完了し、その後も機体は安定している。

### 5.3 対照走査(再生なし)の結果

dtvtuner の非リーダースレッドにアタッチし、rw-p のみを走査した(123 領域 / 約 40MB、読みエラー 0、走査約 2 秒で約 20MB/s)。候補は 2 件、いずれも全パケットが null(PID 0x1FFF)の TS 形状だった:

1. ヒープ内、**336 パケット**、sync 336/336、相異なる PID 数 1、null 336、非 null 0
2. ヒープ内、320 パケット、同型の統計

解釈: **アイドル状態の rw-p メモリ内に、コンテンツ PID を持つ TS は存在しなかった**(これが対照ベースライン)。候補 1 は 336 パケットちょうどであり、§2 の TpStreamSource ステージングバッファ(0xFC00 = 192 × 336)とサイズが一致するため、その最有力の実体候補である。ただしペイロードが 0xFF 埋めではなく、コンストラクタ初期化テンプレートのままではない(起動後に何らかの経路で null パケット列として書き換わっている。ペイロードの中身は設計上確認していない)。候補 2(320 パケット)は同形状の別バッファ(リングバッファ等)とみられる。

注意: rw-s 領域(GENERIC セッション共有バッファ等のデバイスマッピング)は本走査の対象外である。§2 のステージングバッファはオブジェクト内蔵(ヒープ側)のため本走査の範囲で足りる設計だが、再生採取で rw-p 側に平文が出ない場合は rw-s 側への拡張が次手になる(§7 で実際にそうなった)。

## 6. E3 実測までの経緯 — 再生が Tp フロントエンドで止まった分離

§5 の手順で再生採取を試みたところ、**リモート再生そのものがアプリ側エラーで開始されなかった**(複数タイトルで同一のエラー。ペアリングは正常)。観測ログの解析では、試行中も dtvtuner にストリーム開始系のコマンド(OPEN_SECUREDTS / OPEN_LOCAL / OPEN_GENERIC / SCRAMBLER)は 1 件も届いておらず、**停止点は dtvtuner より上流(Tp フロントエンド / DTCP AKE 層)**と特定した。この状態での memscan 採取は対照と同一の結果(候補 2 件・全 null)だったが、再生が始まっていないため平文採取の判定材料にはならない。

分離の経緯:

- **到達性は全宛先で正常**。フロントエンドが機体の版数を読む・送る・比較する処理は静的に存在しないことを確認した。
- **対照再生**: 純正の公式ファームウェア環境ではリモート再生が**成功**した。一方、観測ビルドの内容のまま版数表示だけを公式に合わせたビルドでも**同型に失敗**した。→ **版数ゲート説は、アプリ/サーバ側を含めて対照実験で棄却**。原因は観測ビルドの実行時差分と確定した。
- **パイロット環境**(無改造のデーモン + ssh サーバのみ追加し、起動スクリプトは観測ビルドのものをバイト単位で流用)では再生が**成功**した。内容差分はラッパー 2 バイナリ(デーモンの起動ラッパーを公式バイナリへ戻したこと)のみで、ssh サーバと起動スクリプトの追加処理は残したまま再生が通った。
- **判定: Tp 停止の原因はラッパー/観測シム層(ラッパーのプロセス形態、または LD_PRELOAD 観測シムの存在)と確定した。** ラッパー形態とシムのどちらが効いたか(あるいは両方か)の内訳は未分離だが、E3 の前提としては「無改造デーモン + ssh で再生と採取が両立する」ことが確定したのが本質である。観測系が対象の動作を妨げるという一般的な教訓でもある([AGENTS.md](../AGENTS.md) §4)。

## 7. E3 初回実測 — 再生中の候補バッファは全 null

パイロット環境でリモート再生(torne mobile)が成功した状態で、memscan 採取を行った。

### 7.1 実施条件

- 対象は dtvtuner の非リーダー・S 状態のワーカースレッド 1 本(§5.2 の運用ルールを厳守)。D 状態のスレッドは回避した。全採取を通じて機体の再起動・デーモンの異常はなく、同一ブートの継続を uptime で確認した。
- 再生が採取窓を通じて継続していた裏付け(独立指標): 採取中の load average の上昇、dtvtuner の CPU 時間の進行(カーネル時間主体)、クライアント端末との接続の存在、メーカーの Telepathy サーバへの接続維持、採取終了時点でも CPU 時間の進行と接続の継続を確認した。
- 採取パス: 再生中に 14 パス、停止直後に 6 パス。1 パス 1–2 秒(約 22–44MB/s。E4 基礎値の更新)。走査量は 1 パスあたり約 44MB、読みエラー 0。

### 7.2 結果

| 状態 | パス数 | 候補 1(336 パケット) | 候補 2(320 パケット) | その他の候補 |
|---|---|---|---|---|
| 再生中 | 14 | 全パス null=336 / 非 null=0 / 相異なる PID=1 | 全パス null=320 / 非 null=0 / 相異なる PID=1 | 出現せず(検出下限を下げても同じ 2 件のみ) |
| 停止直後 | 6 | 同一アドレスで全 null | 同一アドレスで全 null | 出現せず |
| アイドル対照(§5.3) | 対照走査 | 全 null | 全 null | 出現せず |

候補はどちらもヒープ内だった。候補 1 のアドレスはブートごとに変動し、候補 2 は対照走査と同一アドレスだった。停止直後の所見として、候補に残留コンテンツは無く、再生中と区別がつかなかった(そもそも再生中に平文が載らなかったため、「残留するか即 null に戻るか」の判定材料自体が得られなかった、と整理する)。

### 7.3 判定と解釈

- **E3 の当初仮説(§2: Tp 再生時に TpStreamSource のヒープ内ステージングバッファへ平文 TS が載る)は、本実測では確認されなかった。** 再生中であることを独立指標で裏付けた窓で、サイズ一致の最有力候補を含む dtvtuner の rw-p 全域に、コンテンツ PID を持つ TS は存在しなかった(非 null=0 は全 20 パスで不変)。
- ただし棄却の範囲は限定する:
  - (a) スナップショットの限界: ステージングの保持時間は数十 ms 級と見積もられており、原理的には充填の谷間だけを掴み続けた可能性を完全には排除できない。もっとも最有力候補が再生中・停止直後・アイドルの 3 状態すべてで一貫して全 null だったことは、「再生中は概ね平文で満ちている」形のステージングとは整合しない。
  - (b) rw-s は対象外のまま: dtvtuner の rw-s には、AV ドライバの **64MB 共有マッピング**と 64KB マッピングを含む多数の領域がある。平文(復号直後の TS)が GENERIC セッションの共有バッファ側に載る設計なら、本採取の範囲外に実体があることになる。
  - (c) 経路差の可能性: 本実測の再生(LAN 内からの視聴)が、§2 で静的にモデル化した Tp 経路と完全に同一とは限らない。
- 副産物として、観測シムなしで採取できる観測環境(無改造デーモン + ssh)が得られたため、今後の採取では観測系そのものが再生を妨げる問題は解消した。

## 8. 残件

1. **rw-s(デバイス共有バッファ)側の走査**: 共有マッピングを `/proc/<pid>/mem` で読む挙動の確認(PFNMAP の読み可否)を含め、可能なら同領域での再採取。§5.2 の事故経路(デバイス backed の読み)に直結するため、段階分けして慎重に行う。再開時の第一候補はこの走査である。なお、平文 TS は Linux 側のメモリではなく **XCode 側のメモリ(256MB)に載っている可能性**も仮説として残す。
2. **バッファ追随読み**: 充填を検出して即座に追いかける読み方の設計(スナップショット限界への対処)。
3. **TpStreamSource 上流の静的追跡**: 録画再生時に復号段の出力が TpStreamSource へどう接続されるか(§2 の最後の未確定点)。
4. **平文ファームウェアのイメージ分割と逆アセンブル**: 複合イメージのサブイメージ境界とロードベースの特定、DRM 制御モジュールとシステムキー初期化コードの追跡([docs/02](02_dat_encryption_model.md) の副線側残件と共通)。
5. **GENERIC-DTCP(0x200)open の発行元の同定**: ヘルパーへのテーブルディスパッチ経由呼び出しの解決。
6. ラッパー形態と観測シムのどちらが Tp 停止の原因だったかの内訳分離(E3 の前提としては不要。観測ビルド一般の知見として)。
