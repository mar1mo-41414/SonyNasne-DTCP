# 07. OTP 応答値の値レベル安定性 — ハッシュだけを残す再走査

[docs/06](06_otp_rescan_stability.md) §5 の残件(値レベルの安定性は未測定)への回答として実施した測定の記録(2026-11-13 実施)。E1 系の走査は応答を「ゼロか否か」に分類するだけで、生値を保存しない設計だったため、nonzero の値そのものが再起動や時間の経過で変わるかどうかは測れていなかった。本書では、応答値を保存せずメモリ内で SHA-256 を取って即座に消去するツール変種を作り、値レベル(ダイジェスト単位)で安定性を測った。

**到達点(要約)**:

- 結果は一様ではなかった。**index 0x00–0x81(130 件)と 0xFF は値レベルで固定**で、再起動を挟む 3 回の全走査すべてでダイジェストが完全一致した。E1 の分類とも整合し、zero 85 件は全て「8 バイトゼロ」のダイジェストに一致した。
- **index 0x82–0xFE(125 件)は揮発域**だった。走査ペア間でダイジェストが一致するのは 0x82–0xFF の 126 件中 3〜4 件だけで、同じブート内での再走査でも 123 件が食い違った。つまりこの域の値は再起動で変わるのではなく、**読み出すたびに変わる**。単発の連続読みでも、対象 index は毎回異なる値を返した。
- 固定域については「一度読み出せば使い回せる」ことが値レベルで確定した。揮発域は読み出し時点の値しか意味を持たず、固定した内容物の読み出しとは質的に別物である。揮発の生成機序と各 index の意味論は未確定のまま残る。

## 1. 問い

- [docs/06](06_otp_rescan_stability.md) で、OTP の分類(成否とゼロ/非ゼロ)は公式 FW 環境・Debian 環境・再起動後で完全一致することが確定した。しかし nonzero の 171 件については、値そのものが変わっていても分類が nonzero のままなら検出できない。
- 本書の問いは 1 つ: **応答値そのものは、再起動を跨いでも、また同じブート内で繰り返し読んでも、同じか。**

## 2. ツール変種と「値を残さない」担保

- 変種ツール `otp_scan_hash` は、E1 の `otp_scan` の後処理だけを変えたもの。手順・コマンド列は完全に同一で、index ごとに ドライバ open → OPEN_GENERIC(RSA モード)→ READ_OTP(コマンド `0x116`、KeyIndex は引数、応答 8 バイト)→ CLOSE_GENERIC → close を繰り返す。パケットレイアウトも同一。
- 成功時の後処理: 応答 8 バイトをメモリ内で SHA-256 に通してダイジェストを出力し、その直後にパケットバッファ全体をゼロ消去する。SHA-256 の作業領域(入力のコピーを含むブロック、スケジュール、内部状態)も使用後にゼロ消去する。出力は index・成否・ダイジェスト・集計のみで、分類すら出力しない(ゼロか否かは、ゼロ応答のダイジェストと比較すれば事後に判定できる)。
- SHA-256 は自前実装(FIPS 180-4)。実機投入前に既知ベクタ 5 件で検証した: 空文字列、`abc`、8 バイトゼロ、56 バイトの FIPS 例題、および任意の 100 バイト列(独立実装 `sha256sum` の出力と照合)。全て一致。
- ソース精読による担保: 応答 8 バイトを参照する箇所は SHA-256 への受け渡しの 1 箇所のみ。全ての標準出力は、固定ラベル・index・status・ioctl 戻り値・ダイジェスト・集計のいずれかで、応答値が乗る経路は無い。失敗経路では応答値を読まずにバッファを消去する。使用するシステムコールは open / close / ioctl / write / exit のみで、E1 と同じ読み取り専用の手続きである。
- ゼロ応答のダイジェスト(8 バイトゼロの SHA-256、`af5570f5a1810b7af78caf4bc70a660f0df51e42baf91d4de5b2328de0e83dfc`)を対照値として使う。これは数学的定数であり個体情報ではない。
- ツールのソースとバイナリは作業環境に保管した(ソースとバイナリの SHA-256 はそれぞれ `0e5cfd0a…`、`7ce714e7…`)。走査結果ファイル自体は [docs/06](06_otp_rescan_stability.md) の方針と同様、本リポジトリには含めず作業環境で管理し、ファイルの SHA-256 だけを §4 に記録する。

## 3. 手順

いずれも現在の Debian 環境で、通常サービス(チューナーサービス等)が稼働中の状態で実施した。

1. **アンカー確認**: 0x00(zero 側)、0x0B / 0x40 / 0xFF(nonzero 側)を単発で読み、E1 の分類と整合すること、0x00 が対照ダイジェストと一致することを確認してから全走査に入った。
2. **値ハッシュ走査1**: 全 256 index を走査(ブート 1)。
3. **再起動**: 実機を 1 回再起動(Debian → Debian)し、通常サービスの復帰を確認。
4. **値ハッシュ走査2**: アンカー再確認ののち全走査(ブート 2)。
5. **値ハッシュ走査2b**: 走査2 と同じブートのまま、間を置かずにもう 1 回全走査。「ブートが違うから変わる」のか「読むたびに変わる」のかを分離するために追加した。
6. **単発プローブ**: 0x82 / 0x90 / 0xC0 / 0xFF を各 5 回連続で単発読みし、変化の時間粒度を測った。

## 4. 結果

| 測定 | 条件 | 集計 | ファイル SHA-256 |
|---|---|---|---|
| 値ハッシュ走査1 | Debian 環境・ブート 1 | ok=256、err=0 | `1397502623472f2ffac727505e3dbcf0ca366824637e4991ec7cce57bcd6dfdc` |
| 値ハッシュ走査2 | Debian 環境・ブート 2(再起動後) | ok=256、err=0 | `d3cac4da051c405f92d86600051d4df5e693d9ed9021e576d7ea2fa7e19c102c` |
| 値ハッシュ走査2b | ブート 2 のまま再走査 | ok=256、err=0 | `078d789d1b70fe8ecfbd533fe29a2f3596bfbfc1131ba58e666073c541071d3e` |

### 4.1 E1 分類との整合

- 走査1 の時点で、E1 で zero だった 85 件は全て対照ダイジェスト(8 バイトゼロ)と一致し、nonzero だった index が対照ダイジェストになることは 1 件もなかった。分類の境界は値レベルでもそのまま再現された。

### 4.2 固定域: 0x00–0x81 と 0xFF

- **0x00–0x81 の 130 件は、走査1・走査2・走査2b の 3 者で全件のダイジェストが完全一致**した。再起動を跨いでも、同ーブート内で繰り返しても、値は変わらない。
- **0xFF も固定**だった。3 走査に加え、両ブートのアンカー読みと単発プローブ 5 回、計 10 回の読みで全て同一のダイジェストを返した。

### 4.3 揮発域: 0x82–0xFE

- 0x82–0xFF の 126 件について、走査ペア間でダイジェストが一致した index はごく少数だった:
  - 走査1 × 走査2: 4 件(0x90、0xE2、0xFC、0xFF)
  - 走査2 × 走査2b(**同じブート**): 3 件(0xE8、0xE9、0xFF)
  - 走査1 × 走査2b: 4 件(0x98、0xA0、0xD9、0xFF)
  - 3 ペア全てで一致するのは 0xFF のみで、残りの一致はペアごとに顔ぶれが変わる(偶然の一致の様相)。
- 単発プローブでは、0x82 / 0x90 / 0xC0 は **5 回連続の読みで毎回異なる値**を返した。変化はブート跨ぎではなく読み出し単位で起きている。
- 域内の構造(いずれもダイジェストだけから分かる範囲):
  - 0x83–0x87 の 5 件は、どの走査でも互いに同一の値を返した。ただしその値自体は走査ごとに変わる。「5 つの index が同じ 1 つの動的な値を覗いている」形になっている。
  - プローブでは、異なる index の読み(0x90 の 4 回目と 0xC0 の 1 回目)が同一の値を返した。値は index に固定されていない。
  - 各走査で 0x82–0xFF に現れる相異なるダイジェストは 107 / 111 / 113 種類(126 件中)で、完全に一様な乱数(ほぼ全件相異なるはず)とも違う。重複を含む有限の列・プールから値が引かれている様子がある。
  - 走査間を単純な index ずれ(シフト)で対応付けることはできなかった。

## 5. 事実と解釈

### 5.1 観測事実

- 0x00–0x81(130 件)の応答値は、環境を固定した 3 測定(再起動 1 回を挟む)で完全に不変だった(§4.2)。
- 0x82–0xFE(125 件)の応答値は、同じブート内でも読みのたびに変わる(§4.3)。0xFF だけはこの域にありながら固定だった。
- 変化の粒度は「再起動」ではなく「読み出し」である(走査2 と 2b の比較、単発プローブ)。

### 5.2 解釈

- **固定域(0x00–0x81、0xFF)は OTP 本来の固定ストア**とみるのが素直で、[docs/06](06_otp_rescan_stability.md) の分類安定性はこの範囲では値レベルまで拡張して確定した。
- **揮発域(0x82–0xFE)は、固定された内容物の読み出しとは質的に別物**である。実装された OTP 容量の範囲外の index に対する読みが、ファームウェア側の動的な生成物や作業領域を返している、という解釈が最も素直に合う。重複の出方からは生成物が有限の列である可能性が示唆されるが、生成機序の特定はしていない(推測の域)。
- 0xFF は Sony 自身が使う index として知られている([docs/04](04_open_questions.md) §2.2)ことと合わせ、揮発域の境界にありながら固定値を持つ特別な位置づけと整合する。ただし意味そのものは未確定のまま。
- 副線(鍵だけ抜いて PC で復号)への含意: 「一度読み出せば使い回せる」素材の候補は固定域に限られる。揮発域は読み出し時点の値しか保持しないため、少なくとも生の形では固定鍵素材の置き場とはみなせない。逆に固定域については、値の再現性が確定したことで、意味論が特定できれば読み出し 1 回で足りることが保証される。

### 5.3 本結果が変えないこと

- 各 index の**意味論**は引き続き未確定([docs/04](04_open_questions.md) §2.2)。本書は「値が変わるかどうか」だけを扱った。
- 録画経路と OTP の接続が無いという既存の判定([docs/02](02_dat_encryption_model.md) §10)にも影響しない。

## 6. 残件

- 揮発域の生成機序の特定(何の列を返しているのか)。ファームウェア解析側の問いと接続する。
- 0x83–0x87 が同じ値を覗く構造の意味。
- 固定域(0x00–0x81、0xFF)の意味論の特定。鍵装填経路側の静的追跡との突き合わせが本筋。
- 本測定の範囲は Debian 環境の 2 ブートである。公式 FW 環境での値レベル測定や、電源断を伴うコールドブート跨ぎは未実施。
