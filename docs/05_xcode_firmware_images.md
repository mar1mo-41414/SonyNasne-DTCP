# 05. XCode ファームウェアイメージの取得と形式判定(DRM モジュール解析 第1段)

[docs/04](04_open_questions.md) §2.2 の未判定事項「トークン → 実効鍵の解決規則そのもの」への静的な接近として、XCode SoC ファームウェアの DRM モジュール解析を開始した。本書は第1段(実現可能性の判定まで)の記録である。実機には触れておらず、手元のファイル解析のみで実施した。

**第1段の到達点(要約)**:

- SoC 向けファームウェアイメージは全て、Sony が公開した GPL ソースツリー内から取得できた(§2)。
- 主ファームウェアの平文版は**製品版と同一内容**であることを、ブロック対応の全数照合で証明した。製品版は平文版を 16 バイトブロック単位で暗号化(ECB 型)したものであり、「別ビルド」「製品個体からは静的に読めない」という従来の留保([docs/02](02_dat_encryption_model.md) §8)は本書の結果で解除される(§3.4)。
- 主ファームウェアの ISA は **ARC 系(ARCompact 世代)** と同定した。ドライバ側の命名にある "mips" はベンダの呼称で、ISA とは一致しない。MIPS32 は積極的な証拠をもって棄却した(§3.2)。
- ロードベースは **0** と確定した(§3.3)。
- DRM 制御モジュールの文字列群とディスパッチ表とみられる構造の所在を特定した(§4)。
- 本格的な逆アセンブルに進める状態である。残る障害は ARC 対応の逆アセンブラの整備のみ(§6)。

---

## 1. 目的と範囲

- 目的: 「ファームウェアイメージが入手できるか」「読める形か(圧縮・暗号化・ISA)」「DRM モジュールの切り出しが可能か」「本格的な逆アセンブルに進めるか」の門を閉じること。解決規則そのものの解読は第2段以降。
- 材料は全て公開済み・手元のもの(GPL ソースツリー、公式 rootfs の複製)であり、実機・ネットワークには触れていない。

補足と切り分け:

- ドライバ側の接続: 主 FW の配列はドライバ内部でダウンロード用ポインタに接続され、SoC へそのまま渡される。ドライバ側に展開・復号の処理は無い(サイズ照合のみ)。製品ビルドで選択されるのは暗号化出力の側で、平文の側は非暗号化ビルドでのみ有効になる。
- **製品との照合(確定)**: 公式 rootfs 内の AV ドライバモジュール(製品版)には、暗号化出力の主・第2 両配列が GPL 側の配列とバイト単位で一致して埋め込まれていた(出現位置はモジュール先頭から 434,596 バイト目と 6,650,932 バイト目、全長照合済み)。平文の配列は製品モジュール内に存在しない。すなわち製品が実際に SoC へ送るイメージは、GPL 公開の暗号化出力そのものである。
- `proc6.bin` は、GPL カーネルツリー同梱の文書によれば副プロセッサ(ARC)用 Linux カーネルのメモリイメージを gzip 圧縮し Intel HEX 化したものである。ただし**製品では使われていない**と判定した: 製品カーネルの設定では当該 staging ドライバが無効(`CONFIG_STAGING` 未設定)であり、公式 rootfs には `request_firmware` の供給先である `/lib/firmware` 自体が存在しない(確認した範囲はこの2点)。本書では ISA 同定の対照(§3.2)としてのみ使う。
- `proc6.bin.ihex` の変換では、type-02 拡張セグメントレコードを無視する自前パーサが同長の誤った出力を出した(gzip として読めないことで検出)。`objcopy -I ihex -O binary` による変換が正解であり、上表のハッシュはそちらである。失敗の記録として残す。
- ブート FW 2種は NAND フラッシュのデバイス名文字列を含むブート用で、DRM 関連の文字列は無く、本解析の対象外と判断した。

## 3. 主ファームウェアの形式判定

### 3.1 全体構造

平文版は圧縮も暗号化もされていない素の複合イメージである。領域の内訳(16KiB ブロック単位のエントロピーと内容からの分類): 先頭にベクタ領域、0x4000〜0x8000 は全ゼロ、0x8000〜約 0x2D4000 がコード密領域、約 0x2F0000〜0x3B0000 と約 0x48C000〜0x564000 に大きなゼロ領域(BSS 相当)、その間にデータ表の領域がゼロの隙間を挟んで並ぶ。内部に uImage / ELF / gzip / cpio 等の既知マジックは存在しない(走査したのは各マジックの先頭バイト列。2バイト級の偶然の一致は除く)。

### 3.2 ISA の同定: ARC 系(確定寄り)、MIPS32 は棄却

- **MIPS32 の棄却(積極的証拠)**: イメージ全体の 32 ビットワード 1,554,081 個を走査し、MIPS32 の帰還命令 `jr $ra` に相当するワードは **0 個**だった。約 3MB のコードに帰還命令が皆無ということはあり得ない。また後述のベクタ構造も MIPS の例外ベクタ形式と合わない。したがって主 FW は MIPS32 コードではない(ドライバや文書の "mips" の呼称は、ISA ではなくベンダ側の命名である)。
- **ベクタ領域の形式**: イメージ先頭は 8 バイト対の列であり、各対は「制御命令 + 長い即値(ジャンプ先アドレス)」と読める。対照として、同梱文書で ARC 用と明記された `proc6` カーネルイメージの先頭も全く同じ 8 バイト対構造であり、ARC 対応デコーダ(capstone 6.0.0a7)では両者とも先頭から `j <アドレス>` の連続として読めた(proc6 側はカーネル空間のアドレスへ、主 FW 側はイメージ内アドレスへ跳ぶ)。これは ARC の割り込みベクタ表の形式と一致する。
- **コードの読み**: コード領域の開始点 0x8000 は、同じデコーダで ARC の関数プロローグ(リンクレジスタのスタック退避)として読めた。
- 留保: 手元の ARC デコーダは ARCv2 寄りの実装で、ARCompact 世代のコードでは命令境界の同期がずれ、領域途中からの線形スイープはほぼ成立しなかった(関数先頭からは読める)。「ARC 系」という族の同定は上記の複合証拠によるもので、世代の細部と全面検証は第2段のツール整備後に行う。

### 3.3 ロードベース: 0(確定)

ベクタ表のジャンプ先がイメージ内のオフセットそのもの(例: 0x0 のエントリ → 0x113C20、0x28 のエントリ → 0x2D00C4)に収まること、データ表内のポインタ値がファイル内オフセットの範囲と BSS 相当の範囲(ファイル末尾を超えるアドレス域)に分布することから、イメージはアドレス 0 を基点に配置される。アドレス参照の解決にベース加算は要らない。

### 3.4 製品版(暗号化出力)の形式: 平文版と同一内容のブロック暗号化(確定)

従来、平文版は「製品版とは別ビルドの変種」とされ、アドレスや定数を製品版へ主張できない留保があった([docs/02](02_dat_encryption_model.md) §8)。本段の検証でこの前提は覆った。

- **XOR 仮説の棄却(積極的証拠)**: 暗号化版では、平文版のゼロ領域に対応する部分が単一の 16 バイトブロックの反復になっており(ゼロ領域 約 88 万バイトで反復を確認)、一見 XOR の周期鍵に見える。しかし実際に XOR で復号すると、ゼロ領域は全て 0 に戻る一方、**非ゼロバイトの一致率は全領域で 0.4%(ランダム水準)** に留まり、コード領域のエントロピーは 8.00(均一ランダム)で、文字列は 1 件も復元されなかった。XOR であればビルド差に関係なく平文そのものが得られるはずであり、この結果は XOR を否定する。
- **ECB 型ブロック暗号の確定(積極的証拠)**: 16 バイト境界で切ったブロックについて、平文版・暗号化版の双方で重複構造を全数比較した。相異なるブロック数は両者とも 193,854 で一致し、重複ブロックの出現回数分布と領域別分布も一致した。さらに全 388,520 ブロックについて「平文ブロック → 暗号化ブロック」の対応を取ると**一対一の全単射であり、衝突は 0** だった(逆向きも同様)。第2 FW でも同じ結果である(173,237 ブロック、相異なるブロック数 125,054 で一致、衝突 0)。これは「暗号化版 = 平文版の各 16 バイトブロックを固定の全単射で置換したもの」= ECB 型ブロック暗号の署名そのものである。
- **帰結**: 平文版と製品版は**同一内容**であり、相違はブロック単位の暗号化だけである。ブロック境界が保存されるため、平文版で得たアドレス・コード配置・定数・文字列の所在は、そのまま製品版に主張できる。製品版の静的解析は平文版で行えばよい(製品版自体の復号は不要)。
- 暗号のアルゴリズム名と鍵は未確定(ブロック長 16 バイトのみ確定。AES と決め打ちはしない)。鍵はホスト側の資料には無く、復号はチップ側のロード処理で行われる設計とみられる。標準的なブロック暗号であれば鍵の総当たりは現実的ではなく、本解析では鍵の探索は行わない(平文版が同一内容で入手できる以上、必要もない)。

## 4. DRM モジュールの所在候補

対象は平文の主 FW(= 製品と同一内容)。オフセットはイメージ先頭からの値。

### 4.1 文字列の所在

- DRM 制御のログ書式群が 0x2D3070〜0x2E7178 に密集する。代表例: `drm_dbg`(0x2D3070)、`ScamScramble`(0x2DCA24)、drmctrl の open/close とエラー書式(0x2DEBB4〜0x2DEC8C)、`AESCMAC`(0x2E0F30)、`drmctrl_open_secured_strm ret:%x`(0x2E2F54)、鍵スロット指定の書式 `xcode_key_index:%d` / `decrypt_key_slot_id:%d, encrypt_key_slot_id:%d` / `securedts_mode:%d`(0x2E6BDC〜0x2E6C34)。
- 0x2ED300〜0x2ED458 には、XML 署名の要素名(`<c:Certificate>`、`<KeyInfo>`、`</SignatureValue>` 等)と、`AES_H_eveflag`、`DRMCTRL AACS BUF`、`DRMCTRL CPRM BUF`、**`gen_kauth`(0x2ED438)、`setexchgkey`(0x2ED444)** という名前が 4 バイト境界に詰めて並ぶ。名前の表(シンボル名相当)とみられる。
- 第2 FW 側の DRM 関連文字列は僅少(DTCP の語 1 件、AACS スクランブラのログ 1 件ほか数件)で、DRM 制御の主所在は主 FW 側である。

### 4.2 ディスパッチ表とみられる構造

0x2ED450 以降には、アドレス対や (ID, ハンドラアドレス) 対のレコード列が続く。例: 先頭列が 0xC 刻みで増加するアドレス対の列(0x003D2EF8, 0x003D2F04, …)、ID 0x00110001〜0x00110006 に対して同じハンドラ 0x003DCD7C を指す対の列。コマンドディスパッチ表の実体候補であり、第2段ではこの表と §4.1 の名前表の対応付けからモジュール境界を引く。

### 4.3 暗号定数の走査

イメージ全体を対象に、既知の暗号定数の先頭連続バイト列で照合した: AES の S-box / 逆 S-box、SHA-256 の定数、Blowfish の P 配列、DES の初期転置表は**いずれも存在しない**(列挙した範囲 = 上記の定数群について、イメージ全体)。0x2D41CC には SHA-1 初期値の先頭 2 語と一致する 8 バイトがあるが、前後は SHA-1 初期値の残りとは続かず、これ単独では SHA-1 のソフトウェア実装の証拠にしない。これは従来の所見(バルク暗号は HW エンジンが担い、FW は制御語とスロット指定に徹する。[docs/02](02_dat_encryption_model.md))と整合する。トークン → 実効鍵の解決も、鍵そのものの計算ではなく、チップ内部状態への参照と制御として実装されている可能性を考えるべきである。

### 4.4 切り出し可能性の評価

ロードベース 0 の確定と、ベクタ表・名前表・ディスパッチ表・文字列の所在特定により、モジュール単位の切り出しは「表を起点に参照を辿る」作業として定式化できる。残るのは ARC 対応の逆アセンブラで文字列参照元(コード側)を引く工程であり、イメージ側の不足はない。

## 5. SoC 内蔵カーネルイメージ(参考)

`kernel_image_data` は uImage 形式(マジック 0x27051956、名前 "Mips Linux Kernel"、無圧縮、ロード 0x90000000、エントリ 0xB0040000、ペイロード 4,853,894 バイト)であり、SoC のメインコアは Linux を走らせる。DRM 制御の主対象は §4 の主 FW 側であり、本イメージは第1段ではここまでに留める。切り分けの記録: ペイロード内に現れる cpio / ELF のマジックは、いずれもカーネル内の文字列リテラル(ログ文・シンボル名の一部)であり、埋め込み initramfs や ELF 実体ではないことを後続バイトの形式不一致で確認した。なお製品版ドライバモジュール内には、この配列と同一のものは見つからなかった(製品での搭載形態は未確定。DRM 解析とは別件として残す)。

## 6. 本格解析への判定と次の打ち手

### 6.1 判定: 進める(門は開いた)

- 情報の存在: トークン解決に関わるはずの DRM 制御モジュールは、製品と同一内容の平文イメージの中に、文字列・名前表・ディスパッチ表・コードの所在まで特定できた。「そこに情報があるか」自体はもう問いではない。
- 解析可能性: 静的解析の成果は製品にそのまま主張できる(§3.4)。ロードベースも確定した(§3.3)。

### 6.2 残る障害

- 手元の Ghidra(12.1.3)の言語モジュール一覧に ARC が無いことを確認した。このままでは主 FW の Ghidra プロジェクト化ができない。
- capstone 6.0.0a7 は ARC デコードを持つが ARCv2 寄りで、ARCompact 世代のコードでは同期ずれが大きい(§3.2 の留保)。

### 6.3 次の打ち手(第2段)

1. ARCompact 対応の逆アセンブル環境の整備: Ghidra 向け ARC 言語モジュールの導入可否の検証、または ARC に対応する他ツールの導入。関数先頭のアライメントとベクタ表を種に、命令境界の同期を取る手順を確立する。
2. エントリポイントの列挙: ベクタ表のジャンプ先と §4.2 のディスパッチ表を起点に、drmctrl 系の処理と `gen_kauth` / `setexchgkey` の参照元を特定する。
3. トークン解決の追跡: `drmctrl_open_secured_strm` の書式を持つ関数群と、SECUREDTS セッション確立のコードを読み、トークン(ホストから渡る制御語)が FW 内でどう解釈され、チップ内部状態(キーストア、OTP 由来の材料)とどう結び付くかを追う。
4. 製品版の復号・鍵の探索は行わない(§3.4 の帰結として不要であり、鍵はホスト側資料に無い)。

## 7. 再現手順の要点

- 配列の抽出: AV ドライバソースの C 配列(16 進リテラルの列)をバイナリ化し、宣言サイズと一致を確認する。Intel HEX の変換は `objcopy` を使う(§2 の失敗記録)。
- 同一性の検証: 製品モジュール内の配列との全長バイト照合、および §3.4 のブロック対応の全数照合(平文・暗号化の双方について、ブロック辞書の衝突ゼロを確認する)。
- 本書の数値は全て手元の作業環境で再計算可能な形で残した(イメージのハッシュは §2)。
