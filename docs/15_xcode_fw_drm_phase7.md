# 15. XCode ファームウェア DRM モジュール解析 第7段: 伝送層ディスパッチ探索(陰性の範囲明記)、AKE 中核計算の実体、slot_id 写像の所在切り分け

対象: 主 FW 平文イメージ(ファイルオフセット表記、[docs/05](05_xcode_firmware_images.md) の SHA-256 `3e99b413…` と同一物)。本書のアドレスは原則ファイルオフセットで書く。Ghidra プログラムアドレスに触れる場合はその旨を明記する(ビュー2プログラム ghp7 では プログラムアドレス = ファイルオフセット + `0x100000`、ベース 0 プログラム ghp4 では両者は一致する)。

## 0. 要約

- 第6段([docs/14](14_xcode_fw_drm_phase6.md) §8)の主軸だった「パケットスロット配列の読み手の追跡」は、両ビューの復号済み命令列に対して複数の独立した署名で系統的に探索したが、**受信・振り分け本体には到達できなかった**。陰性の範囲は §2 に明記する(絶対スカラ参照 0 件、FunctionNumber 振り分けパターン該当なし、記述子のスロットポインタフィールドを読むコードなし、等)。SCRAMBLER(mhcmd 37)/ SET_KEYSTORE_KEY(42)/ READ_FROM_OTP(45)のハンドラ本体と `control_words` の処理は未到達のまま。
- **gen_kauth の「中核計算」の実体は、ARC コード内のソフトウェア暗号ではなく、ハードウェア RSA/ECC アクセラレータのドライバだった**(§3)。ファイル `0x1FED1C` は薄いラッパで、実体(ファイル `0x1FED8C`)はエンジンレジスタへオペランドをコピーし、コマンドワードを書いて完了イベントを待ち、結果を読み戻す。AKE 素材の起源は一部追えた: gen_kauth 入力の一つ(文脈 +0x10C74、0x28 バイト)は**受信した AKE メッセージからコピーされる相手方素材**であり、別の一つ(文脈 +0x110E0)はプロトコルステップ内で**ソフトウェア bignum 演算により計算**される。文脈初期化側(セッション生成時に +0x10C20 / +0x10C30 等へ何が書かれるか)は未追跡で、OTP・鍵ストア・証明書のいずれに接続するかは未判定のまま(§3.3)。
- slot_id の写像(第6段の残件)については、**OPEN_STREAM ペイロード変換 ファイル `0xB6344` は slot_id フィールドを一切読まない**ことを実読で確定した(陰性の確定、§4.1)。ストリーム open のルータ(ファイル `0x22FC54`)は要求オブジェクトを素通しで open 本体へ渡し、open 本体は鍵指定ペアを要求の **+0x38/+0x3C(復号)と +0x40/+0x44(暗号)** から取る(§4.3)。slot_id(+0xD14 / +0xD24)の消費者は診断出力関数以外では未同定で、ペアへの変換点も未同定 = 未判定として残る。
- (a)/(b) の境界と READ_FROM_OTP の index 境界は、本段では判定材料(ハンドラ実読)に到達せず**未判定のまま**(§5)。

## 1. 方法

- 解析は作業領域 `2026-11-13-fw-drm/phase7/` で行った。Ghidra プロジェクトは第6段の ghp6 のコピー ghp7(ビュー2プログラム、ベース `0x100000`)を主とし、ベース 0 プログラム ghp4(phase4 のプロジェクト)でも同じ検索を実施した。
- 新規スクリプト(phase7/scripts/):
  - `RecvHunt7.java`: 同定済み関数を対象に「通信領域アンカ `0xAFE7FC` のスカラ参照を含み、[レジスタ+0xC] の読み(FunctionNumber 相当)があり、伝送層番号集合 {8, 25, 33, 37, 39, 40, 41, 42, 43, 44, 45, 46, 50, 51, 52} のうち 2 つ以上と比較している」関数を抽出する。
  - `Hunt3.java`: 同定済み・孤立コードを問わず全命令のリスティングを線形走査し、(A) [レジスタ+0xC] 読みの直後 12 命令以内に上限 51/52/53 との比較・減算がある、(B) 同じく直後にスケール付き表引きロードがある、(C) `1` の mov の直後 6 命令以内に [レジスタ+0x10] へのストアがある(PacketProcessed = 1 の署名)、の 3 パターンを抽出する。
  - `Hunt4.java`: 変位 `0xF0` / `0xF4` / `0xF8` のワードロード(通信記述子のスロットポインタフィールド読み)を抽出し、後続 8 命令を併記する。
  - 既存の `ScalarQuery5.java`(命令スカラの全数検索)、`DumpFunc5.java`、`DumpRange5.java` を併用した。
- ログは phase7/ 配下(recvhunt_ghp7.log、hunt3_ghp7.log、hunt4_ghp7.log、scalar_hunt_ghp4.log、dump_ghp7_*.log 等)。

## 2. 課題1: パケットスロット配列の読み手と伝送層ディスパッチ(到達できず、陰性の範囲を明記)

第5段で確定した通信記述子の構造(プロセッサ配列ベース `0xAFE000`、ストライド `0xF4`、パケットスロット配列 3 本の基底 `0xAFE6B4` / `0xAFE7E8` / `0xAFE91C`、ヘッダセル `0xAFEB64` / `0xAFF940` / `0xAFF944` への初期化側の書込み)を「読む側」を、以下の署名で探索した。

### 2.1 絶対スカラ参照: 両ビューとも 0 件

- 配列基底 3 点・ヘッダセル 3 点・共有ロックワード `0xAFEB04` を命令スカラとして含む命令は、ghp7・ghp4 の**どちらのプログラムの復号済み命令列にも 0 件**だった。
- 通信領域アンカ `0xAFE7FC`(= `0xAFE000` + `0x7FC`)だけは多数存在する(ghp7 で 633 件、ghp4 で 224 件)。したがって読み手は存在しても、絶対アドレスではなくアンカ + オフセット等の計算済みアドレッシングで到達しているはずである、という前提で以下のパターン探索を行った。

### 2.2 関数単位の振り分け署名: 候補 1 件、実読で棄却

- RecvHunt7 は ghp7 の同定済み関数 2,801 件を走査し、候補は **1 件のみ**(FUN プログラム `0x1C0514`、ファイル `0xC0514`、比較集合 {50, 52, 8, 25})だった。
- 実読(ダンプ 1,663 行、デコンパイル含む)の結果、これは**メディア/ストリームのパラメータ計算**であり棄却した: 文脈 +0x9F4 のコード値 {0xF, 10, 0x3C, 0x32, 0x19, 0x18, 7, 6, 5, 3, 1, 0xC, 8, 4} を文脈 +0x174 の値へ写像し、RAM `0x52F108` 基底・ストライド `0x134` の表を使う。パケット構造へのアクセスは無い。

### 2.3 全命令の線形走査(孤立コードを含む): ディスパッチの形は無し

- Hunt3 は ghp7 の全 489,011 命令(ghp4 でも実施)を走査した。
  - パターン A(FunctionNumber 読み + 上限判定): 実質 **0 件**(ghp7 の 1 件は [sp,0xC] のスタック読みに由来する誤検出、ghp4 は 0 件)。
  - パターン B(FunctionNumber 読み + 表引き): ghp7 で 48 件。出力の大半は [sp,0xC] のスタック読みと構造体フィールドの逐次読みであり、パケット基底からの FunctionNumber 読取り + ハンドラ表引きの形は無かった。
  - パターン C(PacketProcessed = 1 の書込み署名): 13 件。実レジスタ基底のものはファイル `0x7A000`–`0x92000` に集まり、範囲ダンプで読むと拡張レジスタ群と aux レジスタ `0x80`–`0x96`(データパス設定)を扱う **DSP/メディア系ライブラリの構造体フィールド書込み**であり、パケット完了書込みではなかった(棄却)。

### 2.4 記述子のスロットポインタフィールドを読むコード: 無し

- Hunt4 の結果、変位 `0xF0` / `0xF4` / `0xF8` のワードロードは ghp7 全体で 4 件のみで、**全て [pcl, …] の PC 相対リテラル読み**だった。通信記述子の +0xF0 / +0xF4 / +0xF8(スロット配列ポインタ)をデータレジスタ基底で読むコードは、復号済み命令列に存在しない。

### 2.5 傍証の切り分け

- プロセッサ ID 取得関数(ファイル `0x2B8A64`)の呼び出し元は、ログ/報告ライブラリ領域(ファイル `0xDD200`–`0xE124A` の密集した呼び出し群)を含む非常に広い範囲に及び、受信ループの識別子にはならない。
- アンカ `0xAFE7FC` の参照件数が多い上位 5 関数(ファイル `0x16371C` ×33、`0x1D9C40` ×29、`0x19F8F8` ×21、`0x26C8F8` ×20、`0x2C7730` ×15)についてはデコンパイルを抽出し grep による一次切り分けまで行った。いずれも `*[0xAFE004]` 基底のレジスタブロックと通信ポインタセル(`0xAFEB3C`、`0xAFEB68` 等)を多用し、ロック/アンロックヘルパの呼び出しを伴う共有バッファ/メディア処理の様相で、FunctionNumber らしい比較集合は見当たらなかった。**ただし 5 関数の精読は本段では未実施**であり、これは「読み切った上での陰性」ではない。

### 2.6 結論(未到達)と残る可能性

- 結論: 受信ポーリング → FunctionNumber 振り分け → ハンドラという経路は、**両ビューの復号済み命令列(同定済み関数 + 線形リスティングとしての孤立コード)に対する上記全署名の範囲では存在しない**。37 / 42 / 45 のハンドラ本体には到達できなかった。
- 残る可能性(いずれとも判定しない):
  1. 第4段で測った「コード密領域の約 23% が孤立コード」という未復号分の中に、制御フローが復元できていない形で存在する。線形走査は命令列としては覆っているが、分岐先・関数境界が分からないため署名が成立しない場合がありうる。
  2. 記述子のプロセッサ別 MMR/ドアベル値([docs/13](13_xcode_fw_drm_phase5.md) §5.2)を介し、別プロセッサ側の実行文脈がパケットを消費する。ただし DRM 制御の主所在は主 FW 側であること([docs/05](05_xcode_firmware_images.md) の第2 FW 文字列調査: 第2 FW 側の DRM 関連文字列は僅少)と、汎用のホスト通信層と DRM ハンドラ層は分けて考える必要がある。
  3. 計算済みの間接呼出し(関数ポインタの実行時構築)のみで到達するコード。

## 3. 課題3: gen_kauth の中核計算と AKE 素材の起源

### 3.1 中核計算ファイル `0x1FED1C` の実体は HW RSA/ECC エンジンのドライバ(確定)

第6段で「中核計算」として残ったファイル `0x1FED1C` を実読した。

- ファイル `0x1FED1C` 自体は薄いラッパで、引数を並べ替えて(第 3・第 4 引数を入れ替える)ファイル `0x1FED8C` を呼ぶだけである。呼び出し元は 9 件: gen_kauth(ファイル `0x6772C` 内の呼び出し)、AKE ライブラリ内のファイル `0x16EA74` / `0x16E1DC` / `0x16E6BC` / `0x16F674` / `0x16F790` の各所とファイル `0x6024C`。
- 実体ファイル `0x1FED8C`(本体 ファイル `0x1FED8C`–`0x1FF04F`)のデコンパイル実読:
  - RAM `0x6AE3E4` をキーとするミューテックス(取得 ファイル `0x3B86A4` / 解放 ファイル `0x3B79A8`)で排他し、呼び出し回数カウンタ RAM `0x6AE468`、エラーカウンタ RAM `0x6AE46C` を持つ。
  - エンジンレジスタ基底は `*[0xAFE004]`(通信領域のセルに格納されたポインタ)。
  - 開始時にスロットクリアループ: `i < 0x40` について `[基底+0x1800] = i<<4 | 4`、`[基底+0x1804] = 0`。
  - オペランドは呼出し側バッファからエンジン内メモリへコピーされる(コピー補助 ファイル `0x2FF438`(種別 4、エンジン内オフセット 0 / `0x10` / `0x20`)と ファイル `0x2FF0D0`(種別 2 と 1、オフセット 0))。単位数は第 2 引数(バイト長)>> 5、すなわち 32 バイト単位(gen_kauth からは `0xA0` が渡り 5 単位)。
  - コマンドワード `[基底+0x1870] = 第1引数 | (第2引数 − 1) << 20` を書き、イベントオブジェクト名 `"rsa eveflag"`(ファイル `0x16FBBC` で開く)を用い、`[基底+0x1818] = 0xC`、完了待ち(ファイル `0x16FE5C`、引数 `0x7F` / `0x9C4`)、フラグ取得(ファイル `0x16FF28`)、イベントクリア(ファイル `0x16FFE0`、`0xFFFF`)、キック(ファイル `0x29E648`、引数 `0xB`)、`[基底+0x181C] = 8`、後処理(ファイル `0x17079C`)を行う。
  - **成功条件はステータスフラグのビット 3(フラグ & 8)**。成功時は出力が ファイル `0x2FF86C` で呼出し側の最後の 2 バッファへ読み戻される。失敗時はエラー文字列 `"ERR_rsa_ecc_calculate status / event close / wait timeout / event open"`(ファイル `0x2E2A98`–`0x2E2B54` 付近)を ファイル `0x3C6E84` で記録し、出力バッファをゼロ化(各 5 ワード)して 1 を返す。
- 判定: **AKE の中核計算は ARC コード内のソフトウェア暗号ではなく、ハードウェア RSA/ECC アクセラレータが実行し、FW コードはそのドライバ(オペランド搬入・コマンド発行・完了待ち・結果搬出)に徹する**。第6段の gen_kauth 実読で「入力文脈フィールド → 中核 `0x1FED1C` → 生成値 12 バイト」とした流れの「中核」は、このエンジン実行だったことになる。バルク暗号が HW で FW は制御に徹するという第1段以来の所見([docs/05](05_xcode_firmware_images.md): 暗号定数テーブルがイメージ内に不在)と整合する。

### 3.2 AKE 素材の起源(追えた範囲)

AKE のステップ関数 2 件を実読し、gen_kauth の入力フィールドがどこから来るかを追った。

- ファイル `0x67ED4`(メッセージコード 99 のステップ): gen_kauth 呼び出しの直前に、**文脈 +0x10C74 へ受信した AKE メッセージ(引数 3 + 4)から 0x28 バイトをコピー**する(+0x10C74 は第6段で同定した gen_kauth の入力フィールドの一つ)。すなわち当該入力は**相手方(接続先デバイス)から送られた素材**である。同関数はまた、文脈 +0x10C20 から 0x10 バイトと受信メッセージ 0x2B バイトを文脈 +0x1142C / +0x1143C に組み立て、文脈 +0x112FC をオペランドとして検証系のエンジン利用関数(ファイル `0x16EA20`、内部で `0x1FED1C` ラッパを使う)へ渡す。
- ファイル `0x67A10`(メッセージコード `0x7C` のステップ):
  - 文脈 +0x10C30 から ファイル `0x66C24` で値を取り出す(個数 2 および 5。第6段で +0x10C30 は 4 バイト値・2 バイト値の取得元と判明していたもの)。取り出した値(0x14 バイト)に対しソフトウェア bignum 演算群(ファイル `0x1BF0B0` / `0x1BF170` / `0x1BF9A8` / `0x1BEF68` / `0x1BF144`)を成功するまで繰り返し、結果 0x14 バイトを **文脈 +0x110E0**(gen_kauth の入力フィールドの一つ)へ格納する。すなわち +0x110E0 は**プロトコル実行中に計算される値**である。
  - 同ステップはエンジンラッパを、オペランド = 文脈 +0x11338、文脈 +0x1134C、上記の計算値、文脈 +0x11310、文脈 +0x112FC として呼び、出力 0x28 バイトを送信メッセージへコピーする。
  - 文脈 +0x10C30 から取り出した 5 バイト値は送信メッセージ(+0x4F)にも載る。+0x10C30 は「自側の値を保持し、相手へも提示する」フィールド群である。
- ファイル `0x68664`(AKE ステップ関数と見られる第 3 の関数)はダンプまでで、本段では未読(残件、§6)。

### 3.3 未追跡・未判定のままのもの

- セッション文脈オブジェクト([引数 +0x48] が指す実体)の**生成・初期化側**は未追跡である。文脈 +0x10C20 / +0x10C30 / +0x112FC / +0x11310 / +0x11338 / +0x1134C にセッション開始時点で何が書かれるか(固定 OTP 域・鍵ストア・証明書系・乱数のいずれに接続するか)は**未判定**で、「OTP 由来ではない」とも判定していない(第6段 §8 の申し送りの状態から進んでいない部分)。次段の手掛かりは、文脈オブジェクトの生成者・初期化関数の同定である(AKE ライブラリ内のセッション生成経路)。

## 4. 課題4: slot_id の写像

### 4.1 変換関数ファイル `0xB6344` は slot_id を読まない(陰性の確定)

第6段の残件は「OPEN_STREAM ペイロード変換(ファイル `0xB6344`)で `decrypt_key_slot_id`(+0xD14)/ `encrypt_key_slot_id`(+0xD24)が鍵オブジェクト指定へどう写るか」だった。本段で `0xB6344` の命令リスティング全域とデコンパイルを実読した。

- `0xB6344`(第5段で同定された Ghidra 上の関数体は ファイル `0xB6344`–`0xB65ED`)が入力構造体(引数 2)から読むオフセットは、**+0x60、+0x64、+0x6C、+0x90、+0x94、+0x9C、+0xAC、+0xB4、+0xB8、+0xBC、+0xC0、+0xC4、+0xC8、+0xD8、+0x128、+0x62C、+0x6C8、+0x898、+0xDC8、+0xE14** に限られる。
- したがって **`+0x884`(xcode_key_index)、`+0x888` / `+0x88C`(暗号/復号モード)、`+0x8A0`(securedts_mode)、`+0xD10`(numOfDecrypter)、`+0xD14`(decrypt_key_slot_id)、`+0xD24`(encrypt_key_slot_id)は一切読まれない**。第5段でこれらのフィールド名を与えた診断出力関数(ファイル `0xDC374`)が同じ引数 2 を受けて表示すること、診断書式文字列 `"decrypt_key_slot_id:%d, encrypt_key_slot_id:%d"` と `"xcode_key_index:%d"` がイメージ内に存在することは、本段でも確認した。
- `0xB6344` の書込み先は引数 1 + `0x1274C` を基点とする 0x58 バイトのサブ構造体(オフセット +0x00〜+0x54)で、多くのフィールドがバイトスワップ補助(ファイル `0x3CA4D4`)を通してコピーされ、+0x20 に `0x11111111`、+0x54 に `0x22222222` のマーカーが書かれる。ストリーム種別コード 1–5 は入力 +0x94 のフラグビット(`0xC00`→1、`0x40`→2、`0x80`→3、`0x1000000`→4、それ以外→5)から導かれてサブ構造体 +0x08 へ、第 2 の種別コードは入力 +0x60 / +0x64 のマスクと +0x62C の値集合から導かれて +0x0C へ書かれる。
- 結論: **slot_id の写像は変換関数 `0xB6344` には存在しない**。第6段の残件は、この関数については陰性で確定した。

### 4.2 ルータ ファイル `0x22FC54` は要求を素通しする(確定)

- ストリーム open のルータ(ファイル `0x22FC54`、ログ文字列 `"strm open"`)は要求オブジェクト(引数 1)のフィールドで分岐する: +0x90 == 1 なら ファイル `0x25FCAC`、+0x90 == 5 なら条件により ファイル `0x25FCAC` / `0x35BAF8` 系 / `0x152B6C` 系、+0x90 == 4 またはフラグ条件で ファイル `0x2315AC`、その他の条件で ファイル `0x240838` または ファイル `0x24B8C4`、特定のフラグ組合せで **ファイル `0x24A7E4`(secured open 本体)へ同じ要求オブジェクトをそのまま渡す**、別の組合せで ファイル `0x24C3F8`。
- つまり secured 経路では、ルータと open 本体の間に変換は介在しない。`0xB6344` を呼ぶのは 3 つの open 変種(ファイル `0x2315AC` / `0x240838` / `0x25FCAC`)側であり、それらも §4.1 の通り slot_id には触れない。

### 4.3 open 本体が実際に読む鍵指定は +0x38 / +0x40 のペア(確定)

ファイル `0x24A7E4`(open 本体)のデコンパイルを本段で実読し、第6段の要約を具体化した。

- 鍵指定ペアは要求の **+0x38 / +0x3C(復号側)** と **+0x40 / +0x44(暗号側)** から読まれる。モード(+0x88C == 3 が復号、+0x888 == 4 が暗号)で有効な側だけが実値を持ち、無効な側は (−1, −1)が渡される。ペアは準備関数(ファイル `0x6BDFC`、第 1 引数は要求 +0xD40 の値)と鍵束縛関数(ファイル `0x161B7C`、第6段 §6.2 の −1 = 無し / 0 = 自動選択 / その他 = 鍵オブジェクト直接参照、の解釈を受ける側)へ渡される。
- その他の要求フィールドの消費: +0x898 はストリーム文脈 +0x7650 へコピーされる。+0xD6C / +0xD74 / +0xD78 のブロック(個数 < 8 のとき配列コピー)。パススルー(モード 9)経路では ファイル `0x128A4C` の戻り先オブジェクト +0x380 へ要求 +0xD29 のバイトが書かれる。

### 4.4 未判定として残るもの

- slot_id(+0xD14 / +0xD24)の消費者は、診断出力関数(ファイル `0xDC374`)以外では未同定である。+0x38 / +0x40 ペアへの変換点も未同定であり、「slot_id がペアへ変換される」こと自体も含めて**未判定**とする。残る候補は要求オブジェクトの構築側(= 課題1 で未到達の受信経路)であり、課題1 の進展に従属する。

## 5. 課題5: (a)/(b) 境界と OTP index 境界(未判定のまま)

- 本段では READ_FROM_OTP(mhcmd 45)ハンドラに到達できなかったため、(a)/(b) の境界(FW 側でトークン解決に使われる内部状態の所在区分)と、READ_FROM_OTP の index 境界(ホスト実測 [docs/07](07_otp_value_level_stability.md): `0x00`–`0x81` と `0xFF` が値レベルで固定、`0x82`–`0xFE` が読み出しごとの揮発)について、FW 側からの判定材料は得られなかった。**両者とも未判定のまま**とし、理由は課題1 の未到達に帰着する。
- なお §3 の結果は「AKE の中核計算が HW エンジン実行である」ことを示すが、これは AKE についての確定であり、録画トークンの解決経路((a)/(b) の対象)へは外挿しない。
