# 20. OTP 固定セル連結鍵仮説の実測スイープ (AES-256) — 4 セル連結も実測で棄却 (範囲は 2 段スクリーニングの形まで)

[docs/18](18_otp_concat_key_sweep.md) (2 セル連結 / AES-128) と [docs/19](19_resumption_plan.md) §2.3 (3 セル連結 / AES-192) の続きとして、4 セル連結 (AES-256) を実測した記録 (2026-11-14 実施)。問いに対する結論を先に書く:

- **仮説「`.dat` の実効 AES-256 鍵は、XCode OTP の値レベル固定セル (8 バイト) のうち 4 セルをそのまま連結したもの」は、本実験の範囲ではヒット無し**だった。相異なる鍵 68,574,961 件 (アルファベット 91 種の 4 連結) の全数を、[docs/19](19_resumption_plan.md) §2.4 の 2 段スクリーニングで試行し、第 1 段 (先頭 8 パケットの同期) の通過は **0 件**、最大でも 4/8 で、度数分布は帰無分布 (ランダムな誤鍵) の期待値と精密に整合した。第 1 段の分布の最上位にいた 4 鍵は、全行評価と別サンプルでの再確認でも最高 8/336 で、構造は一切出なかった。
- ただし棄却できる範囲は [docs/18](18_otp_concat_key_sweep.md) §7 や AES-192 と一部異なる。2 段スクリーニングの構造上、全候補について全行の周期性指標を取っていないため、**「復号後に 192 バイト周期性を保つ変換を経た TS」の場合への棄却の拡張は、本実験では全空間には及ばない** (§6 に正確に限定する)。素直な保存形式 (CBC/ECB + 位相 0 の生 TS) については全数で棄却が成立する。
- なお、セル単位の連結は 5 セル = 40 バイトで AES の鍵長上限 (32 バイト) を超えるため、連結仮説の軸は 2・3・4 セルで尽きる。本実験でこの軸は打ち止めになる (変換層・鍵解決の可能性は別軸として残る)。
- 鍵候補の値そのものは本書に書かない ([docs/18](18_otp_concat_key_sweep.md) と同じ方針。候補はセルの index の組とバイト順でのみ識別する)。

## 1. 問いと位置づけ

- [docs/18](18_otp_concat_key_sweep.md) §8 と [docs/19](19_resumption_plan.md) §2 の残件だった AES-192 / 256 拡張のうち、AES-192 は [docs/19](19_resumption_plan.md) §2.3 で実施済み (ヒット無し、範囲は docs/18 §7 と同枠組み)。残る 4 セル連結 (AES-256) を本実験で実施した。
- 方式は [docs/19](19_resumption_plan.md) §2.4 の提案どおり、アルファベットから鍵を直接構成する 2 段スクリーニングである。記述ベースの列挙 (131⁴ × バイト順 16 通り ≈ 47 億件) は採らない。
- 判定の物差しは前回までと同一で、正解なら全行 s0 = 336 (IV 由来で 335) が出る。第 1 段はその先頭部分 (8 パケット) だけを先に見る絞り込みであり、通過条件の設計根拠は §3 のとおり。

## 2. 素材と同一性ゲート

素材は [docs/18](18_otp_concat_key_sweep.md) §2 と同一のもの (開発側の作業領域に保管) をそのまま使った。

- **OTP 固定域ダンプ**: 本スクリプトは起動時に同一性ゲートを必須とし、全 131 セル (index 0x00–0x81 と 0xFF) の SHA-256 が [docs/07](07_otp_value_level_stability.md) の走査 1・2・2b のダイジェストと完全一致することを確認した (本走査・追跡走査とも **不一致 0 件**。不一致があれば起動しない作り)。素材自体の相互検証 (独立採取とのバイト一致) は [docs/18](18_otp_concat_key_sweep.md) §2.1 のとおり。
- **暗号文サンプル**: スクリーニングには x3_000 の先頭断片 (ファイル先頭行) を、再確認には [docs/18](18_otp_concat_key_sweep.md) §2.2 の 6 件のうち先頭・末尾の 5 件 (x3_000 先頭/末尾、dr_000 先頭、dr_001 先頭、mob1_000 先頭) を使った。いずれも現存とハッシュ一致が [docs/19](19_resumption_plan.md) §2.1 で確認済みの素材である。
- **アルファベット**: 固定セルの相異なる値 46 種にバイト反転を加えた相異なる 8 バイトブロック 91 種 ([docs/19](19_resumption_plan.md) §2.2)。整合ゲートとして、アルファベット長の二乗が [docs/18](18_otp_concat_key_sweep.md) の相異なる鍵数 8,281 と一致することをスクリプト内で assert した。

## 3. 方式 — 2 段スクリーニング

### 3.1 第 1 段 (全数)

- 対象: x3_000 先頭行の先頭 1,536 バイト (先頭 8 パケット)。
- 各鍵について CBC (IV = 0) と ECB の両方で復号し、位相 0 の同期位置 8 件 (オフセット 0, 192, …, 1344) における 0x47 の一致数 `s0_8` を数える。
- **通過条件: どちらかのモードで `s0_8` ≥ 7** ([docs/19](19_resumption_plan.md) §2.4 の記述どおり)。
- 通過条件の根拠: 正解鍵は、正しいモードでは 8/8 になる。録画時の IV は 0 と実測されている ([docs/18](18_otp_concat_key_sweep.md) §3) が、仮に先頭ブロックが壊れる形のずれがあっても、同期位置のうち先頭ブロック内にあるのはオフセット 0 の 1 件だけなので 7/8 を保つ。一方、誤鍵が 7/8 以上になる確率は Bin(8, 1/256) の裾で 1.1064×10⁻¹⁶ (モードあたり)、両モード全試行 137,149,922 件を通じても期待通過数は約 1.5×10⁻⁸ で、実質 0 件の見込みだった。

### 3.2 第 2 段 (通過候補のみ)

- 通過候補について、全行 (0xFC00 バイト、336 パケット) の 3 指標 (s0 / allph / per、定義は [docs/18](18_otp_concat_key_sweep.md) §5) を両モードで評価し、さらに [docs/18](18_otp_concat_key_sweep.md) §6.2 と同型の再確認 (5 サンプル × 行単位 CBC / 行単位 ECB / 連続 CBC の行 s0) を行う。
- 本実施では第 1 段の通過が 0 件だったため第 2 段は発動しなかった。その代わり、第 1 段の分布の最上位候補については §5.2 の追跡走査で同等の評価を行った。

### 3.3 検証系の自己試験

本走査に先立ち、植え付けた AES-256 鍵 (固定セル 4 件の連結) で合成平文 (192 バイトごとに 0x47、残りは PRNG) を暗号化し、次を確認した。本走査・追跡走査の両方で毎回実施し、全て PASS してから走査に入っている。

- 全行の物差し ([docs/18](18_otp_concat_key_sweep.md) §5 と同一): CBC (IV = 0) で s0 = 336、ECB で s0 = 336、CBC で IV を誤ると s0 = 335。
- 第 1 段の物差し: CBC 暗号文では (CBC 8, ECB 1)、ECB 暗号文では (CBC 1, ECB 8)、誤った IV で作った CBC 暗号文では (CBC 7, ECB 0) となり、正解鍵が第 1 段の通過条件 (≥7) を正しいモードで満たすこと、IV の誤りでも 7/8 を保つことを確認した。交差モードの値 (1/8 や 0/8) は、IV = 0 の CBC と ECB で先頭ブロックだけが一致するという構造どおりである。

### 3.4 速度の実測と見積もりの再校正

- 本走査に先立つ小規模ベンチ (第 1 段 10,000 鍵、単一プロセス) で **22.9 µs/鍵**、本走査の実行内でも **25.3 µs/鍵** を実測した。[docs/19](19_resumption_plan.md) §2.4 の見積もり (約 40 µs/鍵) より速く、全空間でも 4 並列で 10 分未満の見込みが立ったため、そのまま全数を実施した。GPU 化は行っていない (理由は docs/19 §2.4 のとおり: CPU で十分に収まり、検証系の同一性を保てる)。

## 5. 結果

### 5.1 第 1 段 (全 68,574,961 鍵 × 2 モード)

**通過 (≥7) は両モードとも 0 件。** 最大値は CBC 4/8、ECB 4/8。度数と帰無期待 (Bin(8, 1/256)、モードあたり試行数 68,574,961) の対照:

| s0_8 | 帰無期待 (モードあたり) | 観測 (CBC) | 観測 (ECB) |
|---|---|---|---|
| ≥3 | 225.6 件 | 226 件 | 223 件 |
| ≥4 | 1.10 件 | 1 件 | 3 件 |
| ≥5 | 0.0035 件 | 0 件 | 0 件 |
| ≥7 (通過条件) | 7.6×10⁻⁹ 件 | 0 件 | 0 件 |

≥3 の度数が期待値とほぼ一致し、≥4 も期待のばらつきの範囲内にある。正解の鍵が含まれていれば 8/8 (ないし 7/8) で通過するはずであり、その水準の候補は 1 件も無い。

### 5.2 上位候補の再確認 (追跡走査)

第 2 段の発動が無かったため、第 1 段の最大値 (s0_8 = 4) を取った候補を全数採取し直し、全行評価と再確認を行った。再走査の度数は本走査と完全一致し (≥3: CBC 226 / ECB 223、≥4: CBC 1 / ECB 3)、採取の再現性も確認できた。s0_8 = 4 の候補は相異なる鍵で **4 件** あり、結果は次のとおり (指標の定義は [docs/18](18_otp_concat_key_sweep.md) §5):

| 候補 (index, バイト順) | 第 1 段 (CBC, ECB) | 全行 CBC (s0, allph, per) | 全行 ECB (s0, allph, per) | 再確認の行 s0 最大 |
|---|---|---|---|---|
| 12,27,0e,16 / r0110 | (1, 4) | (1, 6, 4/64) | (6, 6, 4/64) | 6 |
| 1f,1a,22,0f / r0111 | (0, 4) | (2, 6, 4/64) | (8, 8, 6/64) | 8 |
| 2f,16,0c,1f / r0010 | (0, 4) | (0, 5, 5/64) | (4, 6, 4/64) | 5 |
| 42,1d,30,19 / r0010 | (4, 1) | (5, 5, 4/64) | (2, 5, 4/64) | 6 |

全行 s0 の最大は 8/336、再確認 (5 サンプル × 行 CBC / 行 ECB / 連続 CBC) の行 s0 の最大も 8/336 で、どの候補もどのタイトル・位置でも構造を示さなかった (帰無分布のばらつきの範囲内。[docs/19](19_resumption_plan.md) §2.5 のとおり、この試行数規模では全行換算の帰無最大が 12–13 程度まで伸びうる中での 8 である)。

### 5.3 判定

**ヒット無し。** 「実効鍵 = 固定セル 4 件の連結 (AES-256)」を、次節に限定する範囲で実測により棄却する。

## 6. 棄却できる範囲・できない範囲

本実験で**実測により棄却できる**のは、次の組み合わせである:

- 実効鍵が固定セル 4 件の連結 (§2 のアルファベットの範囲: セル単位のバイト反転を含む) であり、**かつ**保存変換が AES-CBC (IV_seed = 0、行単位・連続の両連鎖 — ファイル先頭行では両解釈が一致する) または AES-ECB であり、**かつ**復号で得られる平文が位相 0 に同期を持つ生 TS である場合。
- 第 1 段はファイル先頭の 8 パケットしか見ていないが、ファイル先頭行は録画セッションの先頭であり IV = 0 で始まるため ([docs/18](18_otp_concat_key_sweep.md) §3 の前提と同一)、この絞り込みは先頭行に対する判定としては全行評価と等価である。正解鍵の取りこぼしは、自己試験 (§3.3) で両段とも検出できることを実証したうえで否定できる。

[docs/18](18_otp_concat_key_sweep.md) §7 および AES-192 ([docs/19](19_resumption_plan.md) §2.3) と**異なる点**を明記する:

- AES-128 / 192 のスイープは全候補について全行の周期性指標 (allph / per) を計算したため、棄却は「復号後に 192 バイト周期性を保つ変換 (固定 XOR マスク、位相ずれ、同期バイトの固定置換など) を経た TS」の場合まで及んだ。本実験の第 1 段は位相 0・値 0x47 の指標しか見ていないため、**その種の変換を経た場合の連結鍵は、全空間については本実験では棄却できない**。変換を経た正解鍵は第 1 段の指標では高くならないので、§5.2 で上位 4 鍵の周期性がノイズ水準だったことは、変換ケースの証拠にはならない (この 4 鍵は「生 TS の形で高かった鍵」であって、変換ケースの候補ではない)。
- この範囲を AES-128 / 192 と同水準まで広げるには、全空間への全行評価 (実測速度では 4 並列で約 8 時間、[docs/19](19_resumption_plan.md) §2.2) か、周期性ベースの第 1 段への作り替えが要る。今回は [docs/19](19_resumption_plan.md) §2.4 の提案方式をそのまま実施した結果として、この限定をここに固定する。

本実験でも**棄却できない**もの ([docs/18](18_otp_concat_key_sweep.md) §7 から引き継ぐ):

- 復号後に周期性を壊す変換が掛かる場合の、連結鍵そのもの。
- TS residue モード (20 / 21 / 26) で保存されている場合。
- 16 バイトを生の鍵として使わない鍵スケジュール・鍵解決 (ファームウェア側解決モデルを含む)。本実験も「解決結果が連結と一致する特殊形」だけを潰したものである。
- セル内のワード単位の並べ替え等の、セル単位反転以外のバイト順バリエーション。

## 7. 連結仮説の軸の終了と残件

- セル単位連結の仮説は、2 セル (AES-128、[docs/18](18_otp_concat_key_sweep.md))、3 セル (AES-192、[docs/19](19_resumption_plan.md) §2.3)、4 セル (AES-256、本書) の全てについて、素直な保存形式の範囲で実測棄却が揃った。5 セル以上は AES の鍵長を超えるため、この軸に残件はない。
- 副線自体は閉じていない。残るのは [docs/18](18_otp_concat_key_sweep.md) §7 の範囲外のもの (周期性を壊す変換層の有無の判定 — 平文が得られる本線側の成果に依存、TS residue モードのチップセッション側試行、ファームウェア側鍵解決の規則) と、本実験で新たに切り分けられた限定 (§6: 周期性を保つ変換への棄却の拡張を AES-256 の全空間へ広げる作業) である。後者は費用対効果の観点では優先度が低く、実施するかどうかは分岐判定の必要が生じた時点で判断する。
