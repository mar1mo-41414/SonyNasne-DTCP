# 04. 未確定事項と問いの棚卸し

詰まったときに立ち返るための現状整理(2026-11-12 時点の棚卸しを、2026-11-13 に本リポジトリへ移行・更新)。詳細は [docs/01](01_dtcp_firmware_analysis.md)〜[docs/03](03_playback_path_and_oracle.md)。

## 1. 欲しいもの(この調査の範囲)

- **録画回収**: 撮り溜めた録画(`.dat`)を PC で扱える形にすること。理想形は「復号に必要な鍵だけ nasne 実機から抜いて、実 TS の復号は PC の性能で」。次善がオラクル方式(実機チップ自体を復号オラクルとして使い、復号された TS を PC で抜く)。
- なお全体の大ゴールは姉妹プロジェクト側(Debian 化)にある。本書は録画回収に絞る。

## 2. 本丸の問い: 「`.dat` の実効鍵は、どこで・どう決まるのか」

これが解ければ「鍵だけ抜いて PC で復号」の可否が決まる。

### 2.1 既知

- 録画保存の実形態は SECUREDTS(復号)+ GENERIC-AES(保存側の暗号化)。バルク暗号はチップの GENERIC-AES セッション(OPEN_GENERIC、generic_mode=0x4000、req_size=0xFC00)で行われる([docs/02](02_dat_encryption_model.md) §9)。
- ホストが SCRAMBLER(cmd 0x108)で渡す control word(CW)は鍵そのものではなく**構造化トークン**である。先頭 16 バイト中 15 バイトがブート内の全録画セッションで同一で、残り 1 バイトだけがセグメントごとの +1 カウンタ。実効鍵はファームウェアがトークンとチップ内部状態から解決する([docs/02](02_dat_encryption_model.md) §10)。
- 鍵装填系コマンド SET_KEYSTORE_KEY(0x113) / RESERVE_KEYSTORE_SLOT(0x114)は、ラッパーはあるが呼び出し箇所ゼロの dead code。SECUREDLOCAL(0x32)は発行するラッパー自体が存在しない。実測でも録画時の発火はゼロ([docs/02](02_dat_encryption_model.md) §7、§9)。
- OTP は READ_FROM_OTP(GENERIC 0x116)で全 256 index がホストから読める(E1、zero 85 / nonzero 171)。ただし READ_FROM_OTP の手続きは録画コードから到達せず、当該ブートでも未発火で、録画経路との接続は静的に無い([docs/02](02_dat_encryption_model.md) §10、§11)。
- 器(GENERIC 0x4000 + SCRAMBLER)がホスト供給 CW で双方向に働くことを往復自己検証で実証したうえで、録画時 CW の全 106 セグメント総当たりでも `.dat` は復号できず、単純ミラー仮説(録画時 CW を新規セッションへそのまま再生する)は棄却した(E2)。棄却の前に器の動作を自己検証で証明してあり、根拠は積極的に押さえてある([docs/02](02_dat_encryption_model.md) §12)。
- 鍵監査ではデバイス/ファイル/プロセスの 3 面を列挙し、列挙範囲で現行モデルと矛盾する所見は無かった。ただしこれは「列挙範囲で未発見」であって不在の証明ではない([docs/02](02_dat_encryption_model.md) §13)。

## 3. オラクル側の問い: 「再生時に平文 TS がホストメモリに乗る瞬間を捕まえられるか」

### 3.1 既知(静的)

- Tp 経路では平文 TS がホストメモリにステージされる設計である([docs/03](03_playback_path_and_oracle.md) §2)。TpStreamSourceImpl が 0xFC00 バイトの TS バッファを内蔵し、tpkeydec で開封した 16 バイト鍵をホスト内オブジェクトに保持し、バルク AES のみチップの GENERIC-AES セッションへ委任する。
- 採取ツール memscan を構築済み。対照走査(再生なし)で、336 パケット(= 0xFC00 バイトちょうど)のヒープバッファを Tp ステージングの最有力候補として同定し、アイドル時の dtvtuner に内容を持つ TS は無いことを確認した([docs/03](03_playback_path_and_oracle.md) §5)。
- オラクルの想定形は確定済み: 録画領域(p3)を残したまま起動できる環境で、XCode に復号させ、復号された TS を PC で抜いていく。パイプライン速度は明示的な測定ポイント(E4)。

### 3.2 未判定

- **E3 の初回実測では、再生中の候補バッファは再生中・停止直後とも全 null で、平文 TS のヒープ常駐は確認されなかった**([docs/03](03_playback_path_and_oracle.md) §7)。棄却の範囲は限定される(スナップショットの限界、rw-s は対象外、経路差の可能性)。
- 次の走査対象は **rw-s(デバイス共有マッピング、AV ドライバの 64MB 共有マッピングを含む)**。仮説として、平文 TS は Linux 側のメモリではなく XCode 側のメモリ(256MB)に載っている可能性も残す。
- 静的推定どおりにステージングバッファへ平文が乗るか自体(実再生では未確認のまま)。
- パイプライン速度(E4)。採取側の基礎値(memscan で 1 パス約 44MB を 1–2 秒、約 22–44MB/s)のみある。
- TpStreamSource へ TS を供給する上流側の接続形態(静的追跡が未完)。

### 3.3 前提条件の切り分け到達点(E3 の前提だった「再生できる観測環境」)

- 純正の公式環境ではリモート再生が成功する(実再生で確認)。
- 観測ビルドでは、版数表示だけを公式に合わせたビルドでも同型に失敗した。到達性の問題は全宛先の実測で否定済み。版数検証は機体内フロントエンドに存在せず、アプリ/サーバ側の版数ゲートも対照実験で棄却した。
- よって原因は観測ビルドの実行時差分と確定し、パイロット環境(無改造デーモン + ssh のみ)で再生が成功したことで、**原因はラッパー/観測シム層**と決着した。内訳(ラッパー形態かシムか)は未分離。

## 5. 副線の方針(捨てない)

「鍵だけ抜いて PC で復号」の副線は捨てない(プロジェクト方針として再確認済み)。

- 外部(SNS)で「復号した」という主張があっても、方法の開示がなければ証拠として扱わない(再現も反証もできない)。
- 同時に、その主張の存在も、こちらの未発見も、「復号できない」という反証にはならない。見落としの可能性が残る以上、この道は捨てない。
- 根拠は過去の経験則: 別の暗号化の解析で、復号鍵の所在について否定的な断定をして外した経緯があり、掘り続けた結果、見落としていた場所に鍵があった。**否定的な結論は、否定理由を肯定できる材料(積極的な証拠)が準備されて初めて受け入れる**、というのがこのプロジェクトの受け入れ基準である([AGENTS.md](../AGENTS.md) §2.2)。
- したがって鍵監査([docs/02](02_dat_encryption_model.md) §13)はこの副線を閉じるものではない。副線の分岐判定として残るのは §2.2 の未判定、特に同一ブート内リプレイと OTP の意味論である。なお OTP 固定セルの連結が実効鍵という形は、2 セル (AES-128) と 3 セル (AES-192) がホスト側 AES の全数スイープで実測棄却済み (周期性を保つ変換の範囲まで。[docs/18](18_otp_concat_key_sweep.md)、[docs/19](19_resumption_plan.md) §2.3) で、4 セル (AES-256) も 2 段スクリーニングで実測棄却済みである (ただしスクリーニング方式の構造上、周期性を保つ変換への棄却の拡張は全空間には及ばない。[docs/20](20_otp_concat_key_sweep_aes256.md))。セル単位の連結は鍵長の都合で 4 セルが上限であり、この軸は尽きた。周期性を壊す変換層がある場合の連結鍵そのものは棄却できていない。

## 6. 次にやること(優先順)

1. **E3 の続き**: rw-s(デバイス共有バッファ)側の走査可否の確認と、可能なら再生中の再採取([docs/03](03_playback_path_and_oracle.md) §8)。
2. **同一ブート内リプレイ**: 同じブートで録画 → 即 CW リプレイを行い、トークンのスコープ(ブート単位か個体単位か)を判定する(§2.2)。
3. **OTP の意味論**: 分類安定性は確認済み([docs/06](06_otp_rescan_stability.md))、値レベルの安定性もハッシュだけを残すツール変種で測定済み([docs/07](07_otp_value_level_stability.md))。残るは各 index の意味を鍵装填経路側の静的追跡と突き合わせて特定することと、0x82–0xFE の揮発域の生成機序の解明。
4. **平文ファームウェアの DRM モジュール解析**: トークン → 実効鍵の解決規則への静的な接近(§4)。(第1段 = イメージの取得と形式判定、[docs/05](05_xcode_firmware_images.md)。第2段 = 逆アセンブル環境の整備と表構造・文字列参照の実測まで完了し、文字列 xref では実行コードに到達できないと判明、[docs/08](08_xcode_fw_drm_module_phase2.md)。第3段 = レジストリの実読、H2M 配送構造の確定、DRM コード所在の切り分けまで完了し、ハンドラ同定には逆アセンブラの強化が前提と判明、[docs/09](09_xcode_fw_drm_phase3.md)。第4段 = Ghidra 実読でベクタ表・コマンド番号の 2 層性・procIdx 配送先を確定し、ディスパッチ本体は +0x100000 ビューの壁に阻まれて未同定、[docs/12](12_xcode_fw_drm_phase4.md)。第5段 = +0x100000 ビューへの再マッピング解析で、ビューの混在構造と通信記述子初期化を確定し、DRM 文字列参照の解決から DRMCTRL 実行コードに到達した。中央ディスパッチと SCRAMBLER / READ_FROM_OTP ハンドラは未同定のまま、[docs/13](13_xcode_fw_drm_phase5.md)。第6段 = 名前引き機構を同定し(リソース管理フレームワークであり操作ディスパッチではなかった)、AKE 実体・SECUREDTS 経路を実読、[docs/14](14_xcode_fw_drm_phase6.md)。次段は通信記述子の受信・ポーリング側からの mhcmd ディスパッチ同定と、gen_kauth 中核計算の追跡から。第7段 = ディスパッチ探索は複数署名で陰性の範囲を明記した上で未到達、gen_kauth 中核は HW RSA/ECC エンジンと確定、AKE 素材の一部起源と slot_id 写像の所在切り分けまで進んだ、[docs/15](15_xcode_fw_drm_phase7.md)。次段は未復号の孤立コードの復号促進と AKE 文脈の初期化側の追跡から。)第8段 = 登録サイト census は陰性、第2 FW はロードベース `0xB00000` を一次資料で確定して本格解析しメディア処理用イメージと同定、タスク表と proc4 受信タスク入口まで到達した。静的経路は到達限界の所見を整理し、申し送りとして実験系(同一ブート内リプレイ、オラクル)を主軸に据えた、[docs/16](16_xcode_fw_drm_phase8.md)。)第9段 = 第2 FW の proc4 要求処理ループ本体の実読を完了し(振り分け構造・ワーカー/転送器・OS プリミティブを同定)、proc6 の設定初期化は書込み主体(各プロセッサ自身のブート初期化関数)を同定した、[docs/22](22_xcode_fw_drm_phase9.md)。)
5. E2 の未実施トライアル(mode 20/21/26、IVDR probe、OPEN_LOCAL 生 ioctl)。スコープ判定の後で優先順位を付け直す。
