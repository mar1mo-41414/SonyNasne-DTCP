## 1. 現在地の再確認 (2026-11-14)

### 1.1 棚上げ後に起きた前提の変化

棚上げ (2026-11-13 夜) の前後で、トラック C の前提に関わる機体側の状態が大きく変わっている。再開時の実測・記録照合で確認した事実は次のとおり。

1. **NV (FSYS) のリセットと HDD-B の再登録 (2026-11-13)**: SPI の FSYS 領域を全 0xFF に戻した状態で公式 FW を HDD-B (公式 FW 実験・録画用) で起動したところ、公式 FW が HDD-B を再登録・初期化した。結果として録画一覧は 0 件になり、既存録画の `.dat` ファイルは小サイズのスタブに置き換わった。ただし HDD-B のユーザ領域 (p3) の解放済みブロックには旧録画データの実体が残存していることが保全ダンプの検証で確認されている (非ゼロ率 約 88%)。
2. **保全フルイメージの削除 (2026-11-14)**: HDD-B の保全フルイメージ (約 500 GB) はオーナーが容量問題で削除した。カービング対象のコピーは現存しない。実ディスク (HDD-B) 側の解放済みブロックの実体が今も残っているかは未再検証である。
3. **現行 FSYS と HDD-B の組み合わせの不一致**: 現在 SPI に入っている FSYS は 8 月系譜のもので、HDD-B を再登録した時点 (2026-11-13 夕方) の NV とは別物である (S1 終了後の読み出しで、公式系ブートによる約 1.2 KB の JFFS2 追記のみが差分と確認されている)。すなわち「現行 NV + HDD-B」の組み合わせは、HDD-B が最後に初期化されたときの組み合わせと一致しない。なお再登録時点の NV を含む SPI 全体ダンプは開発側に保存されており、組み合わせを復元する素材は残っている。
4. **HDD-B の観測系 rootfs の停止事象 (S1、2026-11-14)**: HDD-B + 公式 KNL の構成で、rootfs (wrap372 観測系) の init が初期化完了の合図 (beacon) を送信した直後に、ネットワークごと全停止する事象が観測された。2026-11-13 の NV 不整合時の停止と同型だが、HDD-B の rootfs が観測版であるため、「NV 不整合が原因」か「観測系自体の停止挙動」かは未分離のままである。
5. **現行の機体構成**: HDD-A (Debian 12 + 6.12 系) が装着され、SPI スロット A は開発用カーネル。本日 (2026-11-14) の再確認でも SSH で通常稼働を確認した (カーネル `6.12.112-nasne`、nasne-recpt1 が 8301 で待受中)。何も変更していない。

### 1.2 本丸の問いの到達点

本丸の問い「`.dat` の実効鍵はどこで・どう決まるのか」の到達点は [docs/02](02_dat_encryption_model.md) と [docs/04](04_open_questions.md) のとおりで、棚上げ以降に変化はない。要点のみ再掲する。

- 保存の実形態は SECUREDTS (復号) + GENERIC-AES (generic_mode=0x4000、req_size=0xFC00) で確定。ホストが渡す control word は鍵そのものではなく構造化トークン (先頭 16 バイト中 15 バイトがブート内の全録画セッションで同一、残り 1 バイトがセグメントごとの +1 カウンタ) で、実効鍵はファームウェアがトークンとチップ内部状態から解決する。
- E2 (往復自己検証で器の動作を証明したうえでの総当たり) で単純ミラー仮説は棄却済み。ただし E2 のリプレイは録画ブートとは別ブートで実施されており、**トークンのスコープ (ブート単位か個体単位か) は未判定**のまま残っている。同一ブート内で録画して即リプレイする検証は未実施であり、E2 の否定的結果の解釈範囲を区切る未実施実験として残る。
- OTP 固定域 (0x00–0x81 と 0xFF、値レベル固定) の意味論は、index 0xFF = INF2 チップ ID の 1 件のみ同定済み ([docs/17](17_otp_blackbox_probe.md))。残り固定セルの意味論照合 (tpkeydec の固定列や Kdev との照合等) は未実施。

## 2. トラック A: 連結鍵スイープの AES-192/256 拡張

### 2.1 素材の現存確認 (2026-11-14 実測)

保全フルイメージは削除されたが、本スイープの素材はそれとは別に回収されていた小容量の抽出物であり、現存を実測で確認した。

- **暗号文サンプル**: 2026-11-11 に手順 A (読み取り専用の物理読み) で回収した `.dat` 断片 (各 4 MiB) が開発側の作業領域に現存する。[docs/18](18_otp_concat_key_sweep.md) §2.2 に記録された 6 件 (x3_000 先頭/中央/末尾、dr_000 先頭、dr_001 先頭、mob1_000 先頭) は、**全件で SHA-256 が記録と完全一致**した。このほか dr_000 の中央・末尾と mob2_000 先頭の断片も同所に現存する。
- **OTP 固定域ダンプ**: 開発側の作業領域に現存し、全体の SHA-256 が [docs/17](17_otp_blackbox_probe.md) §4 の記録値と一致した (値は本書に書かない)。スイープ実行時には [docs/18](18_otp_concat_key_sweep.md) §2.1 と同じ同一性ゲート (全 131 セルの SHA-256 と docs/07 の走査 1・2・2b の照合、不一致 0 件) を通す。
- **検証系**: [docs/18](18_otp_concat_key_sweep.md) の実施スクリプト (screening + 再確認) が作業領域に現存し、そのまま拡張可能な形だった (§2.3)。

### 2.2 探索空間の見積もり

候補の数え方は [docs/18](18_otp_concat_key_sweep.md) §4 と同じである。鍵候補は「セルの index の組 × 各セルのバイト順 (そのまま/反転)」で記述し、鍵バイト列が重複するものは 1 回だけ試行する。重複除去後の数は、相異なる 8 バイトブロックの集合 (アルファベット) の大きさで決まる。

- 固定域 131 セルの相異なる値は 46 種類 (ゼロ値 1 種 + 0x00–0x81 の nonzero 44 種 + 0xFF の値 1 種)。バイト反転を加えた相異なるブロックは **91 種類** である。これは [docs/18](18_otp_concat_key_sweep.md) の相異なる鍵数 8,281 = 91² と整合する (本拡張のスクリプトでも、アルファベット長の二乗が 8,281 に一致することを整合ゲートとして assert した)。
- **AES-192 (3 セル連結)**: 91³ = **753,571 鍵**。
- **AES-256 (4 セル連結)**: 91⁴ = **68,574,961 鍵**。
- 記述ベースの素朴な数え方 (131³ ≈ 225 万、131⁴ ≈ 2.9 億) より小さいが、試行すべき相異なる鍵は上記のとおりである。AES-256 では記述の列挙自体 (131⁴ × バイト順 16 通り ≈ 47 億件) が現実的でなく、アルファベットから直接鍵を構成する方式が必須になる。

所要時間の見積もりは [docs/18](18_otp_concat_key_sweep.md) の実測速度に基づく。AES-128 スイープは 8,281 鍵 × 2 モード (CBC (IV=0) と ECB、各 0xFC00 バイト復号 + 3 指標) を単一プロセスで 8.9 秒で処理した (約 1.07 ms/鍵、両モード込み)。

- AES-192: 全鍵を同条件で評価すると約 810 秒 (約 14 分)。4 コア並列で数分級 (実測は §2.3 のとおり 306.1 秒)。
- AES-256: 同条件の全量評価では、docs/18 の速度をそのまま引くと約 20 時間 (単一プロセス) / 約 5 時間 (4 コア)、§2.3 の実測 (1 プロセス換算で約 1.62 ms/鍵) で引くと約 31 時間 / 約 8 時間。ただし §2.4 の 2 段スクリーニングを入れれば 1 時間未満に圧縮できる見込み。

### 2.3 AES-192 の実施 (実施済み、ヒット無し)

[docs/18](18_otp_concat_key_sweep.md) の検証系を AES-192 に拡張したスクリプトを新規に作成し、長時間ジョブとして起動した。設計は前回踏襲である。

- **同一性ゲート**: 起動時に OTP ダンプの全セルを docs/07 の 3 走査と照合 (不一致があれば起動しない)。
- **自己試験**: 植え付けた AES-192 鍵 (固定セル 3 件の連結) で合成平文を暗号化し、CBC で s0=336、ECB で s0=336、CBC で IV を誤ると s0=335 になることを確認してから本走査に入る ([docs/18](18_otp_concat_key_sweep.md) §5 と同型)。
- **走査条件**: 鍵空間 753,571 鍵 (アルファベット 91 種の 3 連結、重複除去済み)。モードは CBC (IV=0) と ECB の 2 種。対象は x3_000 先頭行 (先頭 0xFC00 バイト)。指標は s0 / allph / per の 3 種 ([docs/18](18_otp_concat_key_sweep.md) §5 と同一)。候補はセルの index とバイト順でのみ識別し、鍵の値は保存しない。並列度は 4 プロセス。
- **再確認**: 走査後、上位 20 候補について [docs/18](18_otp_concat_key_sweep.md) §6.2 と同型の再確認 (別タイトル・別位置の 5 サンプル × 行単位 CBC / 行単位 ECB / 連続 CBC) を自動で実施する。
- **起動記録**: 2026-11-14 20:31:01 JST に marnux 上で長時間ジョブとして起動 (スクリプト `sweep192.py`、SHA-256 `6d913bffe7d164c1c17299681ffb74947a7e6dca48333125ef6fb303df4bcfd2`、作業領域 `2026-11-14-otp-sweep-ext/` に配置)。起動時の同一性ゲートは不一致 0 件、アルファベットは 91 種で整合ゲート (91² = 8,281) を通過、自己試験は PASS (CBC 336 / ECB 336 / 誤 IV 335)。同日 20:36:18 JST に完了した (走査 306.1 秒、再確認を含む)。
- **結果: ヒット無し。** 最大値は s0 が CBC 9 / ECB 10、allph が両モードとも 12、per が両モードとも 0.125 (8/64)。s0 の度数は両モード合計で ≥6 が 3,361 件、≥7 が 634 件、≥8 が 107 件、≥10 が 1 件で、帰無期待 (約 3,500 / 約 650 / 約 100 / 約 2 件、§2.5) とよく整合する。再確認 (上位 20 件 × 5 サンプル × 行単位 CBC / 行単位 ECB / 連続 CBC) でも行 s0 の最大は 10 で、どの候補もどのタイトル・位置でも構造を示さなかった。
- **判定**: 「実効鍵 = 固定セル 3 件の連結 (AES-192)」も、[docs/18](18_otp_concat_key_sweep.md) §7 と同じ範囲 (連結 + CBC/ECB + 周期性を保つ変換まで) で実測により棄却する。周期性を壊す変換層・TS residue モード・ファームウェア側鍵解決は引き続き範囲外である。結果ファイルは作業領域の `sweep192_summary.json` と `sweep192_run.log`。

判定の物差しは前回と同一で、正解なら s0=336 (IV 由来で 335) が出る。試行数の増加に伴う帰無分布の最大値の期待は §2.5 に置く。

### 2.4 AES-256 の実行方式 (提案、未実施)

- **方式**: アルファベット (91 種) から 4 連結鍵を直接構成し、2 段スクリーニングで評価する。第 1 段は先頭 8 パケット (1,536 バイト) のみを復号し、CBC/ECB とも s0 (8 パケット分) が 7 以上を通過条件とする。正解鍵は IV 誤りの影響を受けても 7/8 以上を保ち (先頭ブロック内の同期位置は最大 1 件しか壊れない)、誤鍵が 7/8 以上になる確率は 1 鍵あたり約 10⁻¹⁵ 級で、全空間でも通過は実質 0 件の見込み。第 2 段は通過候補に全行 (0xFC00 バイト) の 3 指標評価と §6.2 型の再確認を行う。
- **所要見積もり**: 第 1 段は鍵あたり鍵スケジュール + 96 ブロック復号が支配的で、約 40 µs/鍵 (Python + PyCryptodome の呼び出しオーバーヘッド込みの見積もり)。全空間 68,574,961 鍵で単一プロセス約 46 分、4 コアで約 12–15 分の見込み。参考として、全行評価の実測は AES-192 で 1 プロセス換算 約 1.62 ms/鍵 (docs/18 の 1.07 ms/鍵よりやや重い) だった。第 1 段は復号量が 1/42 になるため鍵スケジュールと呼び出しの比重が上がり、40 µs/鍵は楽観側の見積もりである。実施時は先行ベンチマーク (10 万鍵規模) で実測してから全体の所要を確定する。
- **CPU か GPU か**: marnux には GPU (RTX 5060) があるが、本空間は CPU のマルチプロセスで 1 時間未満に収まる見込みであり、指標計算 (周期性スコア) まで含むカスタムカーネルの開発は見合わない。検証系の同一性を保つ (前回と同じ指標・同じ自己試験を通す) ことも CPU 実装を選ぶ理由である。
- **実施タイミング**: AES-192 の結果と実測速度を受けたうえで、本書の次段として実施する。

### 2.5 判定基準と帰無見積もり

- 判定基準は [docs/18](18_otp_concat_key_sweep.md) と同一: s0 が 336 (または 335) に達する候補の有無。達しない場合の棄却範囲も前回の枠組みを引き継ぎ、試行数に応じて帰無分布の期待最大値を併記する。
- AES-192 の試行数は 753,571 鍵 × 2 モード = 1,507,142 件で、前回 (16,562 件) の約 91 倍。s0 の帰無分布 Bin(336, 1/256) から、期待件数は s0≥6 が約 3,500 件、s0≥7 が約 650 件、s0≥8 が約 100 件、s0≥10 が約 2 件のオーダーであり、最大値が 9–11 程度に留まることは帰無と整合する。裏を返せば、今回の空間では s0≥6 の候補が数千件出るのが正常であり、個別候補の再確認は上位に限る (§2.3 の上位 20 件)。
- AES-256 は試行数がさらに約 91 倍 (約 1.37 億件) になり、帰無の最大値は s0 で 12–13 程度まで伸びる見込み。判定は引き続き 336/335 水準でのみ行う。

## 3. トラック B: 静的解析の再開入口

[docs/16](16_xcode_fw_drm_phase8.md) §6 の申し送りを、実施可能な作業単位に並べ直す。到達限界の所見 (「静的に到達可能な範囲では、伝送層ディスパッチと SCRAMBLER / READ_FROM_OTP ハンドラは存在しないか、静的参照の形を持たない」) は棄却ではなく解釈であり、本トラックはその外側に残された 2 経路を攻める。

1. **孤児コードの関数境界復元 (第 1 候補)**: 主 FW のコード密領域の約 23% は関数として同定されていない。関数境界を復元することで、署名探索に掛からなかった処理 (ディスパッチやハンドラの実体) が同定可能になる可能性がある。具体的な第一歩は、[docs/16](16_xcode_fw_drm_phase8.md) §7 の残件 1 (第 2 FW の `proc4_incoming_request_process` の要求処理ループ本体の実読) で、その前提が「スケジューラ呼び出し後段の関数境界復元」と明示されている。主 FW と第 2 FW のどちらの孤児領域から始めるかは着手時に決めるが、proc4 側は入口 (受信タスク) と読みたい本体の目星が付いている分だけ具体的である。
2. **proc6 の設定初期化追跡 (第 2 候補)**: SCRAMBLER の配送先は proc6 と確定しているが、そのパーソナリティ (実行コードの所在) は第 2 FW 内に静的に列挙できなかった。残る手は、プロセッサ別設定セルへの書込み主体、すなわちブート時初期化 (ブート FW / 起動側コード) の追跡である ([docs/16](16_xcode_fw_drm_phase8.md) §7 の残件 2)。ブート側コードの所在確認から始める。
3. **付随する継続項目**: AKE 文脈の初期化側 (セッション管理層の同定)、slot_id の消費者の同定、(a)/(b) 境界と OTP index 境界の判定はいずれも上記 1・2 の成果に従属する。

実施上の位置付け: 実機に依存しないため、トラック A のジョブ実行中にも並行して進められる。ただし [docs/16](16_xcode_fw_drm_phase8.md) §6.3 のとおり費用対効果は低下している領域であり、優先度は A・C の後ろに置く。

## 4. トラック C: 動的解析 (E3 第 2 ラウンド) の前提チェックリスト

第 2 ラウンドの問いと手順は準備済みランブックのとおり (再生中の dtvtuner の rw-s 領域、特に xcodedrv の 64 MB 共有マッピングに平文 TS が載るかを、内容の保存と TS 構造の検証で判定する)。ここでは、§1.1 の前提変化を踏まえて「今も前提が満たせるか」をチェックリストとして明記する。**本書の範囲では実施しない。**

### 4.1 機体構成の前提

- [ ] 現在の機体は「HDD-A + スロット A は開発用カーネル」で Debian が稼働中である。第 2 ラウンドの観測環境 (無改造デーモン + dropbear の pilot260) は「スロット A = 公式 KNL + HDD-B」で起動する構成であり、移行にはスロット A の書き換え (読み戻し照合つき) と HDD の差し替えが要る。実施はオーナーの在宅セッションに限る。
- [ ] 復帰経路 (Debian 構成へ戻す書き戻し) の可否を、移行前に再確認する。公式ユーザーランド上で書き戻しツールが動作するかが未検証項目として残っている (代替は CH341A 経路)。
- [ ] 作業中は見張り (nasne-watchdog) の一時停止と、終了後の再開を手順に組み込む (電源断 + 差し替えの間に自動電源サイクルが走る事故を防ぐ)。

### 4.2 再生可能な録画の用意 (最大の前提変化)

- [ ] **HDD-B の録画一覧は現在 0 件である** (§1.1-1)。第 1 ラウンドで再生対象だった旧録画は `.dat` がスタブ化しており、登録情報 (.hai) 側から辿る通常の再生は成立しない見込み。解放済みブロックの実体は「データが残っている」だけで、公式系がそれを録画として認識する材料にはならない。
- [ ] したがって第 2 ラウンドには、**公式系の構成で新規録画を 1 本作り、その場で再生できること**が前提になる。チェック項目: (a) §4.3 の構成で公式系が安定起動するか、(b) 衛星・地デジの受信が成立するか (著者環境は衛星の復調経路に別の不調が報告されており、地デジでの録画が現実解になる可能性がある)、(c) 録画 → torne mobile 等からのリモート再生が成立するか。
- [ ] 新規録画を作る場合、それはトラック C のための中間素材であり、HDD-B への新規録画は解放済みブロックの旧データを上書きし得る。既存録画の回収 (カービング) を将来行う可能性とのトレードオフを、実施前にオーナーが判断する。

### 4.3 NV と HDD-B の組み合わせ

- [ ] 現行 FSYS (8 月系譜) は HDD-B を再登録した NV とは別物である (§1.1-3)。この組み合わせで公式系を起動した場合の挙動 (再び登録のやり直しが走るか、§4.4 の停止が再現するか) は未検証。
- [ ] 選択肢として、再登録時点の NV を含む SPI ダンプ (開発側に保存済み) から組み合わせを復元する方法がある。どちらの組み合わせで臨むかは、実施前に決めて記録する。

### 4.4 wrap372 観測系の停止問題

- [ ] S1 で観測された「beacon 送信直後の全停止」が未分離のままである (§1.1-4)。HDD-B の sys1 トップには pilot260 が配置されているという 2026-11-13 時点の記録があるが、その後の公式系ブートを経て現物が同じかは未再確認であり、起動前に sys1 の現物確認が要る。
- [ ] 停止が再現した場合の切り分け材料 (停止直前のログ回収、NV の組み合わせを変えた対照) を、実施手順側に用意しておく。

### 4.5 採取の安全条件 (第 1 ラウンドの確立ルール)

- [ ] dtvtuner のスレッドグループリーダーへは ptrace アタッチしない (非リーダー・S 状態の tid のみ、D 状態は回避)。rw-s はデバイス backed 領域の読みに直結するため、小窓探査から段階的に進める。ツールの自己検証 (19/19 PASS) は 2026-11-13 時点のもので、再実施時に再確認する。
- [ ] 再生の実施 (torne mobile からのリモート視聴の開始・継続) はオーナーの操作が要る。採取には再生を数分継続する必要がある。

### 4.6 本人の物理作業が要る点 (まとめ)

1. 見張りの一時停止と再開の合図。
2. スロット A の書き換え立ち会い (復帰に CH341A が必要になる場合に備える)。
3. 電源 OFF のうえでの HDD 差し替え (A → B、実施後に B → A)。
4. 新規録画の作成と、採取中のリモート再生の開始・継続。

## 5. 実施順序の提案

1. **トラック A / AES-192**: 実施済み (§2.3)。3 セル連結の範囲は閉じた。
2. **トラック A / AES-256**: AES-192 の実測速度で §2.4 の見積もりを再校正してから実施する。追加の前提は要らない。
3. **トラック C**: §4 のチェックリストを上から潰す。4.2 (録画の用意) と 4.3・4.4 (NV の組み合わせと停止問題) は同じ実機セッションでしか検証できないため、セッションの設計 (1 回の在宅作業でどこまで進めるか) を先に固める。トークンスコープ判定実験 (§1.2、同一ブート内リプレイ) は観測ビルド構成が前提で pilot260 構成とは環境が異なるため、同じセッションで続けて行う場合は再配置と再起動を挟む別段として設計する。
4. **トラック B**: 実機に依存しないため並行実施が可能。優先度は A・C の後ろ。
