# HDD-B 実ディスクのカービング調査 (削除済み録画の dinode 残存と回収)

実施: 2026-11-14 夜 (JST)。対象: marnux に USB 接続された HDD-B 実ディスク。
方法: マウントせず、`xfs_db -r` と O_RDONLY の raw 読みのみ。

要約: 2026-11-13 の NV リセットで再登録・初期化された HDD-B の p3 (XFS) について、
ライブツリーの現況センサスと、削除済みファイルの dinode 残存調査を行った。
削除済み録画の dinode が広く無傷で残っており、**extent の追跡で旧 `.dat` を
バイト単位で回収できる**ことを、陽性対照 (ハッシュ一致) つきで実証した。
dinode 健在な 1 MB 以上の削除済みファイル 15 件 (計 3,423,186,408 バイト) を同定し、
全 extent が現在の空き領域内に収まる (再割当てされていない) ことを bno btree の
直接パースで照合した。本人の指示により、根拠の揃った 2 タイトルと `.hai` 2 件を
抽出して marnux に保存した (計 33 ファイル、約 1.5 GB、SHA-256 記録つき)。
回収した `.dat` は暗号化されたままである。復号は本線 (オラクル方式) の課題であり、
本調査の範囲外。

## 1. 対象同定と安全措置 (実施した実績)

- ディスク: `/dev/sde`、TOSHIBA MQ01ABD050、シリアル `874TPAANT` (lsblk で確認)、
  容量 500,107,862,016 バイト。記録と一致。
- パーティション: p1 256M ext3 / p2 1G ext3 / p3 498,764,636,160 バイト XFS。
  記録と一致。
- **`blockdev --setro` は実施できなかった** (事実): marnux の sudo は SSH 越しでは
  パスワード必須で対話入力ができず、直接実行は EPERM (CAP_SYS_ADMIN 不足)。
  カーネルの ro フラグ読み戻しは 0 (未設定)。
- 接続直後、デスクトップ環境 (GNOME) が sde1/sde2 を RW で自動マウントした
  (`/media/markun/sys11`、`/media/markun/sys2`)。これは本人のデスクトップ操作に
  伴うもので、ext3 ジャーナル再生が p1/p2 (システム領域) で発生した可能性は
  否定できない。両者は調査開始前に `udisksctl unmount` で解除した。
  **p3 は一度もマウントしていない。**
- 代替として実施した姿勢 (事実): 対象ディスクを一切マウントせず、読み取りは
  `xfs_db -r` と Python の O_RDONLY 読みのみ。fsck / xfs_repair / ログ再生は
  原盤に対して行っていない。なお `xfs_db -r` は起動時に
  "Flushing the data device failed, err=13" を stderr に出す (読み取り専用
  デスクリプタへの flush ioctl の失敗であり、書込みは発生しない) ことを
  透明性のため記す。

## 2. ファイルシステムの現況 (実測)

スーパーブロック: ブロックサイズ 4096、dblocks 121,768,710、
fdblocks 121,706,418、icount 576、ifree 67、AG 数 4、
内部ログは AG2 (logstart fsb 67,108,868、logblocks 59,457)。

2026-11-13 の保全イメージ時点の値との差異 (事実として記録、突合はしていない):
fdblocks はイメージ時点 119,430,283 に対し +2,276,135 ブロック (約 9.3 GB)、
icount は 1024 → 576。解釈として、保全イメージ取得後 (2026-11-14) に HDD-B が
実機で起動された経緯 (S1 フェーズ2) があり、その際の書込みで説明できる可能性は
あるが、本調査では突合していない。

空き領域 (bno btree のリーフを raw 読みで直接パースして取得。AG ごとの合計は
AGF の freeblks と完全一致し、パースの正しさを裏付けた): 空き extent は全 6 本のみ。
AG0 = 1 本 (30,441,403 ブロック)、AG1 = 2 本 (30,441,478)、AG2 = 2 本 (30,382,033)、
AG3 = 1 本 (30,441,488)。**空き領域は AG ごとにほぼ 1 本の巨大 extent に
マージされており、空き extent の境界からは個別ファイルの情報はほぼ得られない。**
攻め手は FS 構造側 (dinode) しかない、という前提が実測で確定した。

## 3. ライブツリーの現況センサス (実測)

`xfs_db` の inode 指定 + `ls` でルートから再帰走査 (マウントなし)。
総 507 エントリ (ディレクトリ 116、ファイル 391)。2026-11-13 イメージ時点の
センサス 503 件とは +4 件の差異がある (未突合)。

- `.dat` は 386 件: {51,200 バイト × 192、102,400 バイト × 2、8 バイト × 192}、
  合計 10,036,736 バイト (イメージ時点のセンサスとバイト合計まで一致)。
- `.hai` は 2 件 (各 65,536 バイト、実 extent あり)。
- その他: `.db` 1 件、`.html` 1 件、拡張子なし 1 件。

ツリー構造: `/00000015/` 直下に `10000000.dat` / `10000001.dat` (102,400 バイト)
とバケットディレクトリ 96 個 (`00`–`95`)。各バケットは 8 バイトファイル 2 件と
51,200 バイトファイル 2 件を持つ (96×4 + 2 = 386 件と一致)。

ここで調査前の前提が 1 つ訂正される (事実): **2026-11-11 時点のペイロード
サブツリー (`/00000015/00/00/0001/…` のような録画ファイル群) はライブツリーに
存在しない。386 件の `.dat` は全て再初期化後の DB スロット/メタデータ系
ファイルであり、旧録画ファイルは「小サイズに切り詰められた」のではなく
「削除された」**。削除である以上、回収の成否は dinode の残存に懸かる。

ライブ側ファイルの内容確認 (参考):
- `10000000.dat` / `10000001.dat` は相互に同一 (SHA-256
  `41f924bb7a04053c2131299901744b8d02edfb3760ff4b19bdeaa8e7c9c25d30`) で、
  開発側の `nasne_db.py` で復号でき (CRC 照合 OK)、中身は
  `<copy_count_mng><gen>00000002</gen></copy_count_mng>` (本文 113 バイト) のみ。
  再初期化後の管理ファイルであり、録画メタデータではない。
- バケットの 51,200 バイトファイルは、バケット 00 の 2 件について全長読みで
  **全ゼロ**を確認した (相互に同一、SHA-256
  `16fa66a7dc98d93f2a4c5d20baf5177f59c4c37fc62face65690c11c15fe6ff9`)。
  8 バイトファイルは 8 バイトの値を持つ (バケット 00 の例: `78d68ef8c246bed1`)。
  これらは録画サイズ情報の供給源にはならない。

## 4. 削除済み dinode の残存調査 (実測)

### 4.1 2026-11-11 ツリー (562 件) のスイープ

2026-11-11 の手順 A で得た全ツリー記録 (`p3_tree.txt`、inode・mode・サイズ・
パス) の全 562 件について、現ディスクの dinode を直接読んで照合した。

| 分類 | 件数 | 備考 |
|---|---|---|
| ライブ (現ツリーに存在) | 437 | |
| 削除済みだが dinode 無傷 | 58 | 合計 1,003,683,993 バイト |
| dinode ゼロ化 | 67 | |

「ライブ」には inode 番号が別ファイルに再利用されたものが紛れる
(例: タイトル2 の x3 録画だった ino 908 は現在はライブの 51,200 バイト
ファイルであり、旧 dinode は失われている)。

### 4.2 inode チャンク全スロット走査

ライブ + 2026-11-11 ツリーが参照する 14 チャンク (64 inode × 14) の
全スロットを走査し、非ライブで mode が残るスロット 182 件を得た
(うち一部は「チャンクのブロック自体がデータとして再利用された」誤読:
mode が異常値・サイズが負値のもの。これは dinode が上書きで破壊された
ことの傍証でもある)。

この走査で、**2026-11-11 スナップショットより後に作られた削除済み録画群**
が見つかった。特に AG2 のチャンク (ino 1074704192–1074704255) には
約 8 タイトル分のクラスタ (各タイトル = 品質ディレクトリ + `999` ファイル
1,296 バイト + ペイロード + メタデータ群) が丸ごと残っていた。

### 4.3 削除済みディレクトリの記載による構造同定

XFS のローカル形式ディレクトリはエントリを dinode 内に保持するため、
削除済みディレクトリの dinode に対して `ls` が効き、名前 → inode の
対応が復元できた (62 件の削除済みディレクトリを走査)。これにより各
ペイロードが「どの品質ディレクトリの `000.dat` で、対の `999` はどれか」
まで構造同定できた。タイトルの番組名そのものは p3 上の復元可能な範囲には
残っていない (§7)。

## 5. ゼロブロック率の解釈と、異常ペアの除外

事実: 実在の録画と同定できるファイル (タイトル1 モバイル・DR、
クラスタ B 等) のゼロ率は 0–2.26% で、ランは最大 6 本、ラン長は
512 ブロック (2 MiB) の倍数であることが多い。
これに対し ino 1074704206 (22.08%、239 ラン) と ino 1074704209
(23.85%、16 ラン) のペアは質的に異なる。

解釈 (本調査の判断): 暗号化済み TS ペイロードが 4 KiB 単位で全ゼロに
なることは通常あり得ず、この 2 件は「extent は確保されたが内容が
書き込まれなかった領域」を大量に含む。未書込み領域の成因
(録画の中断、先行確保の未充填、実験時の書込み等) は分離できていない。
「復旧できた」と言える水準 (メタデータ整合・サイズ・構造) のうち
構造面の健全性を欠くため、本人の保存指示の対象 (復旧できた録画
2 本程度) からは除外した。dinode と extent の同定自体は他候補と
同水準で成立しており、抽出そのものは可能。

なお dinode が残る/残らないの分かれ目については、解釈として:
全 inode が削除されたチャンクはゼロ化されたコアがフラッシュされずに
解放され dinode が残り、ライブな inode を含むチャンクでは削除
スロットがゼロ化されて残った (タイトル1 DR の第1セグメントの
チャンクが後者) ことと整合する。これは XFS の inode クラスタ
書戻し挙動からの解釈であり、直接の観測ではない。

## 8. この経路では失われたもの (積極的な確認つき)

- タイトル1 DR の第1セグメント `000.dat` (2,147,483,520 バイト、
  ino 1074697183): dinode がゼロ化されており回収不能。DR レンディションは
  不完全なままである。
- タイトル1 の `999` (DR 側、ino 1074697182): dinode ゼロ化。
- タイトル2 のペイロード: x3 (ino 908) は inode 番号がライブファイルに
  再利用され、モバイル側も dinode ゼロ化。いずれも dinode 経路では回収不能。
- 削除済みタイトル群の番組メタデータ (番組名・日時等): p3 上では
  `999` (暗号化形式、本調査では未解読) 以外の形では残っていない。

## 9. 残作業と次にやれること

- 同定済みで未抽出のペイロードが 10 件 (合計 1,880,507,784 バイト)
  残っている。同じ手順で抽出可能。実測の読み取り速度は約 70 MB/s
  (15 件・3.42 GB の全数読みセンサスがツール一式込みで約 49 秒)
  であり、ハッシュ計算を含めても数分オーダー。
- 小型の削除済みファイル (サムネイル・メタデータ等) も、残存スロット
  182 件の範囲で同様に抽出可能 (本調査では保存対象タイトルの分のみ実施)。
- チャンクブロック自体が再利用された箇所では dinode が破壊されており、
  その範囲のファイルは extent の手がかりがない。暗号化ペイロードは
  内容側の目印を持たないため、内容走査での再構成は本調査の範囲外。
- `999` レコードの解読は録画 DB 系の暗号 (本線) が前提。
- 回収した `.dat` の復号・再生は従来どおり本線 (オラクル方式、docs/03) の課題。
