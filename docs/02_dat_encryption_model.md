# 02. `.dat` の暗号化モデルと鍵の行方

公式ファームウェアで録画した録画本体 `.dat` が、どのような暗号化で保存され、鍵がどこでどう決まるかを追った記録(2026-11-11〜12 実施、2026-11-13 に本リポジトリへ移行・再構成)。静的解析の土台は [docs/01](01_dtcp_firmware_analysis.md)。

**現在の到達点**: 録画保存の実形態は **SECUREDTS(復号)+ GENERIC-AES セッション(モード `0x4000`)による暗号化** と実測で確定した。ホストがセッションに渡す control word は鍵そのものではなく**構造化トークン**で、実効鍵はファームウェアがトークンとチップ内部状態から解決する。**鍵そのものはホスト側のどこにも存在しない**(メモリ・ファイル・DB のいずれにも出てこない)ことが、静的解析と実測の両方で裏付けられた。

鍵の値そのものは本書にも書かない(存在・形式・所在・導出手順の構造、ゼロ/非ゼロの分類まで)。

## 1. 暗号の層構造

録画が HDD に保存され、再生されるまでに掛かりうる層を分離する。

1. **放送スクランブル(B-CAS / MULTI2)の層**: 受信した TS はスクランブル済み。公式経路では XCode 4210 側の B-CAS 処理(GENERIC チャネルの BCAS 系モード、ドライバ ioctl)でデスクランブルされる。Debian 側でも同経路は再現済み(自作の受信ツール)。これは放送波の層であって保存形式の層ではない。
2. **保存時の保護(本体 `.dat` の層)**: 従来の記録は一貫して「録画本体は DTCP-IP で保護されている」と表現してきた。ただし厳密には、DTCP-IP は本来「伝送路の保護」の規格であり、HDD 上の保存バイト列がその伝送形式そのものなのか、保存専用の別暗号なのかは分けて考える必要がある。本書の結論は §9〜§10 のとおりで、保存段の実体は汎用 AES セッションだった。
3. **伝送時(DTCP-IP)の層**: 公式の再生経路は公式アプリ経由(DLNA / DTCP-IP)のみ。コピー/ムーブは、録画 DB の `rest_copy_cnt`(ダビング10)が示すとおり DTCP-IP のコピー制御の枠内で管理される。

`.dat` の実バイト列の観測(読み取り専用の物理読み): 先頭・中央・末尾とも全域が高エントロピーで TS 同期構造は見えず、**ブロック暗号相当の暗号化が掛かっている**と判定した。ファイルは 2,147,483,520 バイト(2GiB − 128B)で分割され、実サイズは録画メタデータ(CDS の `cleartextSize`)と一致し、保存サイズは 192 バイトの倍数になる。

## 2. 鍵の所在に関する一次資料(初期の棚卸し)

本体復号の鍵がどこにあるかについて、初期時点で手元にあった事実:

- **本体裏面ラベル `DTCP <個体ごとの値>`**: 先行解析に「DTCP-IP 鍵ラベル(録画データ暗号化に関与)」と記録されていた。DTCP のデバイス証明書/鍵 ID は個体ごとに振られる性質のもので、個体固有の鍵素材が本体側にプロビジョニングされていることを示唆する。※値は個体識別情報なので書かない。その後の照合で、この値は DTCP 機器 ID そのものと確定した(§4)。
- **sysInfo 領域に DTCP 機器 ID**: `libcommlib.so` の `seiSysInfoOpen` が物理 `0x1ffef000` をマップし、`sysInfoGet*/Set*`(チップ ID、MAC、**DTCP 機器 ID**、ファーム版数等)がここを読み書きする。
- **SoC(XCode 4210)側のセキュアストリーム機構**: GPL ソース同梱の SDK ヘッダに、保護付きストリームの専用コマンド `CMD_SDEV_OPEN_SECUREDTS`(0x030)/ `CMD_SDEV_OPEN_SECUREDLOCAL`(0x032)、GENERIC モードの `DTCP 0x200`、オープンパラメータ内の `dtcp_desc[8]`、`rng_data[32]`(コメント: "reserved for DTCP only")、そして DECODE 系コマンド構造体のコメント「session_key negotiated during Diffie-Hellman exchange」が存在する。保護付きストリームの鍵交渉と処理は、ユーザーランドではなく **チップ側(ドライバ/ファームウェア)で完結する設計**であることが分かる。
- **SPI 先頭領域の OTP/RSA シンボル**: 実在するが、先行解析では「DTCP-IP/B-CAS コンテンツ保護等、別の用途で使われている可能性が高い」と整理されている(カーネルセグメントの保護には無関係と判断済み。用途そのものは未確定)。
- 対照的に、解読できた暗号群(`.dlm`、録画 DB、`.hai`、HDD 紐付けマニフェスト)は **すべてソフトウェア実装で、鍵はファームウェア内の平文埋め込みまたは定数** という共通パターンだった。本体の保護だけがこのパターンの外(チップ内閉域)にある可能性を示す材料が揃っていた。

## 3. 録画 DB と `999` ファイル — 鍵は含まれない

### 3.1 録画 DB の暗号(解読済み、ただし本体の鍵は含まれない)

- 形式: マジック `a17e4d13` + 長さ(LE32)+ CRC32(LE)+ 暗号文 + ゼロ詰め。暗号は `.dlm` と同じ **Blowfish 変種**(鍵は `.dlm` と同一)、CBC 風・IV=0・リトルエンディアン。平文は gzip(XML) に所定の XOR 変換を掛けたもの。8 バイトに満たない末尾は固定鍵ストリームと XOR。
- 復号・再暗号化とも実装済みで、96 ファイル全部が CRC OK・再暗号化でバイト一致を確認済み。パース方法は公式アプリ `dtvtuner` の I/O を LD_PRELOAD で観測して確定した。
- DB に入るのはメタデータのみである。タグ調査(主なタグ 106 種)では、コピー制御の情報(`cp_ctrl_type`、`rest_copy_cnt`、`d_cp_desc`、`dr_c_data`、`aps_c_data`、`cp_ctrl`、`c_avl_desc`、`cp_r_mode`)は存在するが、**コンテンツ鍵そのものに相当するフィールドは確認されていない**。`rest_copy_cnt=10` はダビング10の残り回数とみられる。なお `dr_c_data` 等の値の中身の解釈自体は未実施(タグ名と役割の推測まで)。
- 結論として、録画 DB の解読成果は「録画の所在・画質・サイズ・コピー制御状態の読み取り」と「DB の修復・再構成」には使えるが、**本体復号の材料(鍵)は DB からは得られていない**。

### 3.2 `999` ファイルの構造解析

品質ディレクトリ毎に置かれる `999`(1,296 バイト)を、複数タイトル・複数画質で相互比較した。**形式の差は画質単位ではなくタイトル単位**だった:

- 平文スパース形のタイトル: 固定長 1,296 バイトの構造体で、非ゼロは次の 3 フィールドのみ(いずれも LE u32):
  - `+0x00`: `.dat` 実サイズ + α(タイトルにより +104,064 / +1,024)
  - `+0x08`: 1(件数/フラグ相当)
  - `+0x20`: データ量に比例するカウンタ(モバイル画質では `.dat` サイズ / 192 と完全一致)
  - 残り 1,280 バイトは全てゼロ。**平文形の `999` には鍵素材らしきランダムデータが一切含まれていない**。
- 全面ランダム形のタイトル: 8/16 バイトブロックの重複は皆無で、平文スパース構造に対する ECB 暗号化ではない(CBC/ストリーム系か、平文自体がランダム)。既知の鍵候補(録画 DB の Blowfish 変種、後述の導出鍵候補、素材そのもの、DLM 鍵)のいずれでも、ゼロの多い構造は現れなかった。
- tpkeydec blob のヘッダ(先頭 BE32 = 64、+0x04 = 1)は、オフセットをずらしても内部に存在しない(§3.3)。

**結論: 「`999` = タイトル鍵 blob」という初期の第一候補仮説は、少なくとも平文形については否定された**(鍵が入っていない)。全面ランダム形が「暗号化された同構造」である可能性は残るが、その場合も鍵は `999` の外にある。

なお、グループ DB やバケット DB シャード(51,200 バイト固定長)にも「全面ランダムな別形式」が現れるが、この形式は録画の有無によらず使われている通常の保存形式の一種と後に確定した(抽出時のブロック対応誤りが「形式差」に見えた事例を含む)。鍵素材は含まれていない。

### 3.3 blob 照合(tpkeydec の 64 バイト blob)

回収済みの全 29 ファイル(`999` ×4、`.dat` サンプルを除く索引群、DB 群、シャード)について、tpkeydec blob のヘッダ条件(任意オフセットで BE32 = 64 かつ +0x04 バイト = 1、LE 版も)を走査した。**ヒットは 0 件**。タイトル 1 の DB XML(平文)内にも blob らしきデータはない。回収済み素材の中に、tpkeydec でアンラップできる形式の blob は存在しない。

## 4. tpkeydec の鍵導出(Kdev)のオフライン再現

[docs/01](01_dtcp_firmware_analysis.md) §5 の残件だった「sysInfo ページと SPI の対応付け」と「定数列 A・B の実体」を確定し、導出鍵 `Kdev` の導出を PC 上で再実装した。**導出に必要な個体素材 S の値と Kdev の値は書かない**(構成と出所のみ)。

**素材 S の同定**(S = sysInfo ページの 3 断片、計 16 バイト):

| 断片 | ページ内位置 | 正体 | 出所(SPI 側) |
|---|---|---|---|
| 6 バイト | `+0x130` | MAC アドレス | SPI `INFO` セグメント(0x60000)本体 `+0x24`。ページ `+0x10c` = INFO 本体先頭(hwtype)という対応で `+0x10c + 0x24 = +0x130` と一致。INFO 本体は dlm/DB と同一の Blowfish 変種で復号でき、セグメント抽出ツールで取り出せる |
| 5 バイト | `+0x3d0` | DTCP 機器 ID | `libcommlib.so` の `sysInfoGetDtcpDeviceId` がページ `+0x3d0` から 5 バイトを読むことを逆アセンブルで確認。値は SPI `INF2` セグメント(0x70000)本体 `+0x60` のチップ ID(8 バイト)の先頭 5 バイトと一致し、**本体裏面ラベルの値とも一致する**(§1・§2 の「ラベル = 機器 ID」説はこれで確定) |
| 5 バイト | `+0x3d5` | sysInfo の RandomNumber フィールド | `sysInfoGetRandomNumber` も同じページベースから `+0x3d5` の 5 バイトを読む。正体と生成元は §5 で確定(起動ごとの揮発値) |

**導出アルゴリズム**(tpkeydec.ko の ioctl ハンドラ逆アセンブルから完全復元):

1. LCG で 2 本の固定列を生成する: 状態 `s` の初期値 37、漸化式 `s ← (129·s + 105) mod 256`。反復ごとに「現状態」「1 回進めた値」を交互に取り、偶数番目の列が A、奇数番目の列が B(各 16 バイト、全個体共通・秘密ではない):
   - A = `2577c91b6dbf1163b50759abfd4fa1f3`
   - B = `0e60b20456a8fa4c9ef04294e6388adc`
2. `C[i] = (~S[i]) XOR B[i]`(ドライバ内では零初期化バッファへの 2 段 XOR として実装されている)。
3. `Kdev = AES-128-Encrypt(key=A, block=C)`(ドライバ内蔵の rijndael 実装、標準 AES)。

ただし当時、RandomNumber の候補値が確定していなかったため、候補 3 種で計算した Kdev の**正しさ自体は未検証**だった。検証には実機での tpkeydec ioctl 観測(入出力の対応付け)か、blob の実物の入手が要る(§5 で RandomNumber の生成元が確定したため、オフライン再構成の可否自体は決着した)。

## 5. RandomNumber は起動ごとの揮発値(Kdev は起動ごとに変わる)

Ghidra による呼び出し箇所の特定(対象シンボル → `.plt` スタブ宛の参照 → 呼び出し関数のデコンパイル、という手法が難読化バイナリでも効くことを実証)で確定した:

- `libcommlib.so` の `sysInfoGetRandomNumber` / `sysInfoSetRandomNumber` は、セマフォで保護して sysInfo ページ基底 +0x3d5 から / へ 5 バイトを読み書きするだけのアクセサで、永続化の処理は無い。`sysInfoSetDtcpDeviceId` も同じ形で +0x3d0 への 5 バイト書き込み。
- dtvtuner 内で `sysInfoSetRandomNumber` を呼ぶ場所は 1 箇所だけ(dtvtuner のメイン初期化関数内)。通常分岐の末尾で、`open("/dev/urandom", 0)` → `read(fd, buf, 5)` が 5 バイト読めたら `sysInfoSetRandomNumber(buf)` とする。同じ関数内では、DTCP 機器 ID のキャッシュ付きゲッタから得た 5 バイトを `sysInfoSetDtcpDeviceId` にも書いている。
- **結論: RandomNumber は dtvtuner が起動するたびに `/dev/urandom` から 5 バイト新規生成される揮発値**である。永続化先から読み出すモデル、チップ ID から派生するモデルは、どちらも否定された。
- 読み手は `libdtvrmtext.so` の輸出 API `dtvRemoteTunerRandomNumberGet` の 1 箇所のみ(機器 ID 側も `dtvRemoteTunerDtcpDeviceIdGet` が唯一の読み手)。読み手が Tp(リモート視聴)の API 面であることが裏付けられた。

**Kdev への含意**:

- 素材 S の第 3 要素が起動ごとの揮発値のため、**Kdev は dtvtuner の起動ごとに変わる**。tpkeydec の blob は「発行された起動セッション内でのみアンラップ可能」という設計と整合する(Tp のセッション鍵配送という位置づけとも一致)。
- blob のオフライン検証には、発行と同一の起動中における sysInfo ページ実値(特に RandomNumber)が必須であり、**SPI ダンプだけからの再構成は原理的に不可能**と確定した。

## 6. `.dat` 試験復号(既知のソフト鍵では開かない)

`.dat` 先頭サンプル(DR / 3 倍速 / モバイル)に対し、次の試行を行った。判定指標は復号後の 0x47 位相頻度(周期 188/192)と構造の有無:

- 鍵候補: Kdev(RandomNumber 候補 3 種)、S そのもの(同 3 種)、DLM/DB 鍵(16 バイト)を AES-128 鍵として使用。
- モード: AES ECB / CBC(IV=0) / CBC(IV = 先頭 16 バイト、2 ブロック目から復号)。録画 DB の Blowfish 変種の復号も実施。
- 結果: **全てノイズ水準**(0x47 位相頻度は最大でも 0.011 程度で、未処理の暗号文と同等)。TS 構造は現れなかった。
- 追加試行: 各タイトルの `999` を 1,296 バイト周期の XOR パッドとして `.dat` に適用(自タイトル・他タイトルとも)→ 効果なし。他の組み合わせも negative。

すなわち、入手可能な鍵候補では `.dat` は開かない。残る可能性は (1) チップ内鍵スロット(鍵がホスト側に存在しない)、(2) 未発見の鍵保存場所・導出経路、(3) 想定外の暗号モード/単位、だった(その後の §8 で (1) が裏付けられた)。

## 7. 実行主体の全数調査 — SECUREDLOCAL/鍵コマンドは発行され得ない

解析を dtvtuner 集中から広げ、「`.dat` を暗号化している実行主体は誰か。鍵はどこに存在するか」を 3 系統(GPL ソース精読 / 公式 2.60 rootfs の全バイナリ走査 / XC コマンド呼び出し箇所の全数調査)で詰め直した。再調査の動機は「暗号化は dtvtuner 以外の主体が行っている可能性を検証していない」「SoC 側がやっている説の根拠は状況証拠のみではないか」「GPL ソースの活用が不十分ではないか」という指摘に応えるためである。

### 7.1 ドライバソースが示すアーキテクチャ

SIE 公開の GPL ソースには **xcode4drv の全ソース(237 ファイル)** が含まれていた(ファーム版数別パッケージ同梱。ドライバのバージョン文字列は実機のものと同一の 6.4.0.15 で、同世代・同バージョンのソースである。バイト単位では実機のモジュールと同一ではない)。

- ユーザーランド → `ioctl(fd, 0x17241724, buf)`(`IOCTLBUFFERHEADER.command` にコマンド番号)→ ドライバ → 大半のコマンドは **H2M(Host-to-MIPS)パケット** に詰め替えられ、**XCode SoC 内蔵 MIPS ファームウェア** へ送られる。ホストドライバの仕事はコマンドの転送と DMA バッファ管理で、ストリーム暗号の実装はホスト側に存在しない。
- **鍵ストア**: `CMD2_SDEV_SET_KEYSTORE_KEY` の処理は、ユーザーが渡した `pValue[32]` を**そのまま H2M パケットにコピーしてファームウェアへ送る**。ドライバは鍵を保持も解釈もしない。パケット定義: `pValue[32]`(IN: "the CW value to be set to the keystore")、`KeyIndex`(0〜127)、`NumberOf64BitSlot`(1〜4)。キーストアは **128 スロット × 64bit のチップ内ストア**である。
- **ストリーム開始**: LOCAL 系(SECUREDLOCAL を含む)は、ユーザーパラメータの `decrypt_key_slot_id` / `encrypt_key_slot_id` を H2M パケットへコピーするだけ。**ホスト側が触るのは常に「スロット番号」であって鍵そのものではない**(SET_KEYSTORE_KEY を除く)。
- **ファームウェア実体**: ドライバソースにはファームウェアイメージ(約 6.2MB)がバイト配列で埋め込まれているが、これは非暗号化ビルドの変種で、**製品版モジュール内には平文の列は存在しない**(製品版は暗号化出力ビルド。ファームウェアの内部動作は製品個体からは静的に読めない)。
  - (2026-11-13 更新) この段落の「非暗号化ビルドの変種」「製品個体からは静的に読めない」は、[docs/05](05_xcode_firmware_images.md) の検証で更新された。製品版(暗号化出力)は平文版と**同一内容**を 16 バイトブロック単位で暗号化したものであり、平文版のアドレス・コード配置・定数は製品版にもそのまま対応する。
- **SDK ヘッダが定義するファームウェアの暗号面**:
  - `CRYPTOCTRL` / `CRYPTOCTRL2`: DES / 3DES / AES(CBC / ECB / カウンタ)/ CSS / MULTI2 / RSA の制御語(CW + IV)をスロット参照で与える構造。`CRYPTO_CTRL2_USE_SYSTEM_KEY`(0x8)=「クライアント鍵ではなくチップのシステムキーを使う」フラグが存在する。
  - `scramble_inmode` / `scramble_outmode`: BCAS / CABLECARD / DTCP / CPRM / DRM_AES 等。
  - `GENERIC_MODE_DTCP` = `0x00000200`。他に `GENERIC_MODE_BCAS`(0x400)、`GENERIC_MODE_AES`(0x4000)、`GENERIC_MODE_CPRM`(0x20000)等。
  - `param_opengeneric`: `generic_session_handle` のコメントは "session_key negotiated during aacs authentication"、`rng_data[32]` は "reserved for DTCP only"、`drmflags` / `scrambling_ctrl_flags` を持つ。GENERIC ストリームは「ファームウェアが DRM セッションを内側で処理する」ための汎用入口である。

すなわち「暗号化の実行主体」は **XCode SoC(内蔵 MIPS ファームウェア + HW 暗号エンジン、鍵はチップ内キーストア)** で、これは設計としてソースで裏付けられた。

### 7.2 rootfs 全体走査

対象: 公式 2.60 rootfs の全 868 ファイル(ELF 107 個、.so 60 個、.ko 2 個 = `xcode4drv.ko` と `tpkeydec.ko` のみ)。

- 暗号定数の走査: ヒットは OpenSSL 自身の実装(AES 逆 S-box、SHA-256 K)と、`libcommlib.so` 内の Blowfish S-box(メタデータ/DB 暗号の実装)のみ。AES 正 S-box の生表は全 rootfs に無い(OpenSSL は Te テーブル方式のため不在が通常)。**方法の限界**: 定数走査の不在は「テーブルを持たない実装」や「libcrypto の EVP 経由」の存在を否定しない。シンボル側を見ると、`/opt` のバイナリで libcrypto から AES 系を import するのはリモートアクセス用クライアント(DapClient、ネットワークプロトコル用)のみで、録画保存とは無関係。dtvtuner / webapi の libcrypto import は `EVP_sha1` のみ(DTCP トークン等のハッシュ用途)。
- デバイス参照の走査: `/dev/vixs/xcodedrv` の文字列を持つファイルは **dtvtuner、webapi、procmng の 3 実行ファイルだけ**。どのライブラリ・他デーモンも AV ドライバを開く手段を持たない。性格付けが薄かった他デーモン(リモートアクセス仲介、コンテンツ管理、電子書籍、予約サービス、WAN プロキシ、Tp コア、外付け HDD 登録管理、ファーム更新)も個別に特定し、`.dat` のデータプレーンへの関与は認められなかった。

### 7.3 XC 呼び出し箇所の全数調査

方法: Ghidra で ioctl の呼び出しを辿ると、各バイナリとも ioctl を直接呼ぶ内部関数は 1 個(可変引数トランポリン)で、その呼び出し元が SDK ラッパー関数群だった。ラッパーはスタック上にパケットを組み、コマンド番号を定数で書き込む。全ラッパーを逆コンパイルして「ラッパー → コマンド」対応を抽出した。

前提として重要な発見: **3 バイナリは同一の ViXS SDK クライアント層を静的リンクで丸ごと内蔵している**。したがってラッパーの「存在」は SDK の能力であって使用の証拠ではない。使用の判定は、実ラッパーへの計算呼び出し参照の有無で行った。

| コマンド | ラッパー | 呼び出し箇所 |
|---|---|---|
| `CMD_SDEV_OPEN_SECUREDLOCAL`(0x32) | **存在しない** | — |
| `CMD2_SDEV_SET_KEYSTORE_KEY`(0x113) | 3 バイナリとも存在 | **全バイナリで呼び出しなし**(参照は GOT と SDK の関数ポインタ表のみ) |
| `CMD2_SDEV_RESERVE_KEYSTORE_SLOT`(0x114) | 3 バイナリとも存在 | **全バイナリで呼び出しなし**(同上) |
| `CMD_SDEV_OPEN_SECUREDTS`(0x30) | 3 バイナリとも存在(コマンド番号を直書き) | dtvtuner・webapi に各 1 箇所(ディスパッチャ経由)。procmng は呼び出しなし |
| `CMD_SDEV_OPEN_LOCAL`(0x10) | 3 バイナリとも存在 | dtvtuner・webapi に各 1 箇所。procmng は呼び出しなし |
| その他の OPEN 系 | OPEN_TS = 0x0f、OPEN_GENERIC = 0x2e、OPEN_PASSTHROUGH = 0x2d、OPEN_CAPTURE = 0x1f、OPEN_DECODE = 0x105、SCRAMBLER = 0x108 | いずれも同型の直書きラッパー |

要点:

- **OPEN 系ラッパーは全てコマンド番号を直書きしており、SECUREDLOCAL 用のラッパー自体が SDK 層に無い**。パラメータで 0x32 に化ける汎用 open も存在しない。公式 FW のユーザーランドから SECUREDLOCAL を発行する経路は無い。
- SET_KEYSTORE_KEY ラッパーの中身は、呼び出し側が渡した鍵バイト列をパケットへコピーする作りで、**「ホストが鍵を知っていてチップへ渡す」設計のラッパーである**。それが 3 バイナリ全てで未使用(dead code)ということは、Sony のユーザーランドは録画に限らず**いかなる場面でもホストから鍵値を受け取っていない**ことを意味する(静的解析の範囲で)。
- 実際に使われている stream open は、dtvtuner / webapi の**単一の stream-open ディスパッチャ**に集約される。procmng は stream open を一切呼ばず、その実 ioctl は初期化級に限られる。
- 残留する不確実性(正直に記録する): Ghidra の間接呼び出し解決が API 表経由の呼び出しを取りこぼす可能性は原理的には残る。ただし他の全ラッパーについては使用箇所が均一に解決できており、鍵系ラッパーだけが系統的に漏れるとは考えにくい。また本節の結論は、後の動的観測(全観測ラウンドのログで 0x32 / 0x113 / 0x114 が 0 件だった事実)とも一致する。

### 7.4 判定

1. **前提の訂正**: 「dtvtuner(か webapi)が録画開始時に SECUREDLOCAL と鍵コマンドを発行し、それを観測すれば暗号化の有無と鍵の流れが分かる」という初期の前提は**誤りだった**。当該コマンドは発行され得ない。初期の観測設計がこの 3 点(0x32 / 0x113・0x114 / tpkeydec)を待つ形だったため全ラウンドで無記録だったのは当然であり、その無記録は「チップが暗号化していない」証拠にはならない(逆も然り)。3 点観測は**観測対象として終了**し、観測対象は OPEN_GENERIC の引数側へ移った。
2. **エンジン説はアーキテクチャとして裏付けられた**(§7.1)。暗号化は XCode SoC 内蔵ファームウェア + HW エンジンが担い、鍵はチップ内キーストアにあり、ホストはスロット番号しか触らない。したがって **`.dat` の鍵はホスト側のどこにも存在しない**(メモリ・ファイル・DB のいずれにも出てこない)というのが静的な結論である。
3. **残るモデル**: 録画の保存段で `.dat` が暗号化されることは物理検証で確定している。ホストが SECUREDLOCAL も鍵投入もしない以上、候補はファームウェア内完結の 2 つに絞られた:
   - **M1**: 録画セッションの GENERIC ストリームが `GENERIC_MODE_DTCP`(0x200)や `scrambling_ctrl_flags` の指定により、ファームウェア内側でローカル保護を適用して出力する(鍵はシステムキー / OTP 由来でファームウェア管理)。ユーザーランドのポンプは暗号文を受け取って `.dat` に書くだけ。
   - **M2**: SECUREDTS で復号された TS を、ファームウェアがローカル保存用に再暗号化して GENERIC / LOCAL 経路へ出す(同じく鍵はファームウェア管理)。
   どちらのモデルでも、鍵はホストに現れない点は共通する。
4. **目標形への含意**: 「復号に必要な鍵だけ実機から抜き、実 TS の復号は PC で行う」は、**鍵がホストに存在しない設計である以上、そのままでは到達不能**と判定を更新した。録画 DB にコンテンツ鍵フィールドが無いこと(§3.1)とも整合する。現実的な回収経路は「**実機のチップ自体を復号オラクルとして使う**」方向への組み替えが筋になる([docs/03](03_playback_path_and_oracle.md))。ただし「鍵だけ抜く」道は、分岐点(システムキーの出自)の判定次第で復活しうるため、副線として閉じない([docs/04](04_open_questions.md))。

## 8. システムキーの出自と OTP(静的解析)

副線(鍵だけ抜く)の分岐点は「システムキーが、読み取り可能な材料からの導出(KDF)なのか、OTP 封印のみなのか」である。SDK ヘッダとユーザーランドの実コードから集めた証拠:

1. **システムキーは「スロット番号」でしか参照されない**。`scramble_ctrl` には `syskey_index` フィールドがあり、変換系パラメータ構造体には `decrypt_syskey_slot_id` が even/odd 鍵スロットと並んで存在する。暗号制御語には「クライアント鍵の代わりにチップのシステムキーを使う」フラグ(`CRYPTO_CTRL2_USE_SYSTEM_KEY` = 0x8)がある。ホスト側のどこにも「システムキーの値」を運ぶフィールドは無い。
2. **OTP はファームウェア管理のストアとして実在し、ホストから値を読む公式 API がある**。第 2 コマンド群に `READ_FROM_OTP`(コマンド番号 45)が定義され、入力は stream handle と KeyIndex、出力は **8 バイトの値** である。AES-ECB 系 API の鍵選択コメントには "0 = OTP key, 1 = Pre-defined key, -1 = clear" という語彙があり、OTP 由来の鍵が暗号エンジンの選択肢として設計されている。
3. **Sony のユーザーランドはこの API を実際に使っている**。dtvtuner(webapi、procmng も同型)には完全な実装があり、AV ドライバを開き、**GENERIC セッションを RSA モード(0x8000000)で開いて**からコマンド 0x116 を発行し、成功時に 8 バイトを呼び出し側へコピーして、セッションとハンドルを閉じる。その上に、引数の KeyIndex を即値で固定したプリセットが 3 バイナリ共通で存在する: **index 0xFF** と **index 0xB**。dtvtuner では 0xFF 読みがアプリ層のアクセサ 2 つから実際に呼ばれていることを確認した。0xB 読みの直接の呼び出しは確認できていない。文書上のキーストア範囲は 0〜127 であり、**0xFF はその範囲外**である。したがってこの API のインデクス空間はキーストアとは別の OTP スロット空間(あるいは特殊セレクタを含む空間)と推定されるが、各インデクスの意味は静的に確定できなかった。
4. **導出(KDF)の痕跡は見つからなかった**。ホスト側コード・SDK ヘッダ・平文ファームウェア(GPL 同梱の非暗号化ビルド)の文字列のいずれにも、チップ ID 等の読み取り可能な材料から録画鍵(あるいはそのラップ鍵)を導出する式・定数・関数名は存在しない。本システムで唯一の「材料からの鍵導出」は tpkeydec の Kdev(§4)だが、これは Tp 配信専用であり、かつ RandomNumber が起動ごとの揮発値であるため録画の副線にはならない。DTCP のデバイス鍵が OTP 内にあること([docs/01](01_dtcp_firmware_analysis.md))も従来どおりである。

**判定**: システムキーはファームウェア管理側(OTP 封印側)にあるとする。ホストが触れるのはスロット番号と、READ_FROM_OTP 経由の一部 OTP 値のみである。ただし「OTP の一部は設計上ホスト可読であり、Sony 自身のコードがそれを使っている」ことが分かったため、可読なインデクスの範囲と中身を実機で走査すること(§11 の E1)が、そのまま副線の分岐判定実験になる。

なお平文ファームウェアの解析からは、ファームウェア内の暗号実装についても所見が得られた: 検出できた暗号定数は SHA-1 の初期値が 1 箇所のみで、AES のテーブル類・SHA-256 定数・Blowfish P 配列・DES 初期転置表はいずれも存在しない。すなわち**バルク暗号はファームウェアのソフトウェアではなく HW エンジン**が担い、ファームウェアは制御語(CW)とキースロットの指定に徹する(SHA-1 がソフトウェアなのは、DTCP の AKE が SHA-1 ベースであることと整合する)。ファームウェア側でも鍵はスロット番号として扱われ、ログ書式に鍵値そのものは出ない設計がうかがえる。ローカル保護の厳密な暗号方式・モードはファームウェア側からは未確定のままである(平文は製品版とは別ビルドであり、アドレス・コード配置・個別の定数値を製品版へ主張してはならない、という線引きを守る)。(2026-11-13 更新: この線引きは [docs/05](05_xcode_firmware_images.md) の同一性証明により解除された。平文版と製品版は同一内容である。)

## 9. 録画時の実測 — 実形態は SECUREDTS + GENERIC-AES

観測ビルド(公式ユーザーランドに観測用の手を入れたビルド)で録画 2 本(3 倍速・DR)を実行し、デーモンの ioctl 観測ログ(83 万行超)を全数解析して、録画開始時の OPEN_GENERIC の実引数を確定した。観測に先立ち、予約発火の実行主体が `tvTimerSchedule`(dtvtuner と webapi の双方に内蔵されたクラス、1 秒 tick 駆動)であること、観測系自身の欠陥(武装窓の判定とフックの戻り値)を修正して初めて録画区間を観測できるようになった経緯がある。発火連鎖の確定(再武装の直接証拠等)は観測系の検証として完了している。

### 9.1 OPEN_GENERIC の実引数

録画プロセス(dtvtuner 本体)からの OPEN_GENERIC は起動時 6 件・録画時 4 件の計 10 件で、他のプロセスからは XC コマンド自体が一切発行されていない:

| 文脈 | 件数 | generic_mode | req_size |
|---|---|---|---|
| 起動時 | 1 | `0x400`(BCAS) | `0x10000` |
| 起動時 | 3 | `0x4000`(AES) | `0xe100` / `0xfc00` ×2 |
| 起動時 | 1 | `0x200`(DTCP) | `0x10000` |
| 起動時 | 1 | `0x4000`(AES) | `0xfc00` |
| **録画 1 開始** | **2** | **`0x4000`(AES)** | **`0xfc00`** |
| **録画 2 開始** | **2** | **`0x4000`(AES)** | **`0xfc00`** |

- **M1 は棄却**: M1 が想定した「録画セッションの GENERIC が DTCP モード(0x200)の指定によりファームウェア内側でローカル保護を適用する」形は、実引数と矛盾する。DTCP モードの GENERIC open は起動時の 1 件のみで、録画セッションとは無関係である。録画の GENERIC open は 2 本とも(各 2 件ずつ)**AES モード(0x4000)、req_size 0xFC00** で揃っている。
- **実形態は SECUREDTS + GENERIC-AES**: OPEN_SECUREDTS(0x30)は全ログで 5 件のみで、すべて録画開始時にある(起動時には 1 件も無い)。つまり録画セッションは「SECUREDTS で放送 TS を復号して取り込み、GENERIC-AES セッションで保存用に暗号化する」構成である。req_size 0xFC00 は Tp 経路のステージングバッファ([docs/03](03_playback_path_and_oracle.md)、TpStreamSourceImpl の 0xFC00 バイトバッファ + GENERIC-AES 委任)と同寸であり、製品内の AES セッション利用の型が録画でも使われている。M2 の骨格(復号済み TS を保存用に再暗号化する)には沿うが、再暗号化の器は DTCP 専用モードではなく汎用 AES セッションである、というのが実測による M1/M2 の決着である。
- OPEN_LOCAL(0x10)は全ログ 0 件で、M2 の別形(LOCAL 経路への出力)も録画では使われていない。OPEN_TS_PASSTHROUGH(0x2d)は 96 件(起動 94 + 各録画 1)。
- **鍵の装填経路は観測範囲に現れなかった**: XC の観測範囲で発行されたコマンドに **0x113 / 0x114(鍵系)と 0x32(SECUREDLOCAL)は全ログ 0 件** で、§7 の静的結論を実測でも裏付けた。副線への含意として重要なのは、録画変換が Tp と同型の GENERIC-AES セッションである点で、鍵供給の仕組み(Tp ではホスト側オブジェクトが開封した鍵を保持する)が録画側でも同型かどうかが次の追跡対象になった(§10)。
- **ダンプ範囲の限界**: `drmflags` / `scrambling_ctrl_flags` / `rng_data` はパケットの +0x1D8 / +0x1E4 / +0x1E8 に位置するが、観測の引数ダンプは +0x13F までしか記録しないため、回収ログからは読み取れなかった(その後 §10.2 で、構築経路の静的解析により録画時は全て 0 と確定した)。

### 9.2 ポンプ(`.dat` 書込み)の帰属

- 録画ファイルの open と本体書込みは、観測したプロセスのうち **dtvtuner 本体のみ**で行われていた(録画パスへの open 3,844 件、本体書込み 9,339 件がすべて同一プロセス。他のプロセスの書込みはメタデータ断片のコピーのみ)。**ポンプは dtvtuner で確定**。
- ただしバルク書込みの syscall 経路の特定は未達(観測側の fd 表の飽和でタグ付けが追いつかず、バイト量の会計が成立しなかった)。次に観測するなら fd 表の拡張と書込み経路のタグ付けが観測系改修の要件になる。

## 10. control word は鍵ではなく構造化トークン

§9 の残件「GENERIC-AES セッションへの鍵装填経路」を静的に追跡し、§12(E2)の残仮説への決着も付けた。

### 10.1 SCRAMBLER パケットの末尾フィールドは録画時もゼロ

- SDK ヘッダの `param2_scrambler`(パケット +0xAC 始まり)で末尾部を確認した: +0x128 `unit_no`、+0x12C `TSPktSize`、+0x130 `tsPid[16]`、**+0x150 `numOfTsPid`、+0x154 `keyStoreIndexOfSrcData`、+0x158 `keyStoreIndexOfDstData`**、+0x15C `numScrambledBlocks`(OUT)。ヘッダのコメント上、keyStoreIndex 系は対応するフラグ(`SDEV2_SF_DATA_FROM_KEYSTORE` = 0x80 / `SDEV2_SF_DATA_TO_KEYSTORE` = 0x100)と併用した場合にのみ意味を持つ。録画時の実測フラグは 0x0c / 0x04 で、どちらのフラグも含まない。すなわち**仮に末尾フィールドに非ゼロ値が入っていたとしても、SDK の意味論では鍵参照として機能しない**。
- dtvtuner の SCRAMBLER パケット構築経路: バッファを組み立てる関数は 2 つだけ存在する。**実値バリアント**は、パケット全体をゼロ初期化したうえで、pDest / pSrc / フラグ / モード / 行数 / バイト数 / ピッチ / control_words[24] / IV_seed[16] / ALU_num[16] と、+0x158 だけを引数で書く。その引数は直接の呼び出し元 6 関数すべてが 0 を渡すことを逆コンパイルで確認した。**+0x110 control_words2、+0x128〜+0x154 は一切書かない(常に 0)**。もう一方の index バリアントはフラグに 0x60(CW_AS_INDEX | IV_AS_INDEX)を強制する別物で、録画時の実測フラグ(0x0c / 0x04)はこのバリアントでは生成できないため、**録画パスが使ったのは実値バリアントで確定**する。
- 結論として、録画時の末尾 3 フィールドは **numOfTsPid = 0、keyStoreIndexOfSrcData = 0、keyStoreIndexOfDstData = 0** であったことが静的に確定する。
- ログ側の裏付け: 回収済み観測ログの SCRAMBLER(cmd 0x108)全数再集計(録画セッション 4 本、計 12,081 呼出)でも、全呼出で scramble_mode = 2(AES_CBC_ENCRYPT)、フラグは 0x04(継続行)と 0x0c(セグメント先頭行)の 2 種のみ、**IV_seed = 0、ALU_num = 0、control_words2 = 0、unit_no = 0** が不変だった。静的結論と実測が一致する。
- ドライバ側の転送は逐語: GPL ドライバの SCRAMBLER 送信経路は、ホストのパケットの全フィールドをファームウェアコマンドへ 1 対 1 でコピーし、**ドライバ側で鍵フィールドを差し替えたりセッション状態から補ったりする処理は無い**。すなわちホスト→ドライバ→ファームウェアの間では、後述の E2 が再現したパケットが、録画時にファームウェアが受け取ったものと一致する。

### 10.2 セッション確立側(OPEN_GENERIC)にも鍵文脈は無い

- GENERIC セッションの構築は 2 経路とも、パケット 0x208 バイトをゼロ初期化してから、generic_mode / req_size / 共有入力バッファサイズのみを刻む。したがって §9.1 で「ダンプ範囲外のため判定不能」とした **drmflags / scrambling_ctrl_flags / rng_data も録画時は全て 0** であったことが静的に確定する。「OPEN_GENERIC の末尾フィールドがセッション鍵導出の種になる」という仮説は棄却される。
- 録画開始時の XC コマンド列は OPEN_TS_PASSTHROUGH → OPEN_GENERIC ×2 → OPEN_SECUREDTS ×3 → SCRAMBLER のみで、鍵に関わるコマンドは一切発行されない。さらに当該ブート全量の XC コマンド列でも **SET_CONTENT_KEY(0x102) / SET_KEYSTORE_KEY(0x113) / RESERVE_KEYSTORE_SLOT(0x114) / READ_FROM_OTP(0x116) は各 0 件**だった。

### 10.3 新発見: 録画パスの control_words は構造化トークン

録画セッション 4 本の control_words(24 バイト)の全数集計から、保存時の「CW」の実像が判明した:

- バイト 16–23 は全呼出・全セッションで 0。
- 先頭 16 バイトは、**15 バイトが当該ブートの全録画セッションで完全に同一**であり、残る 1 バイトだけが **CW セグメントごとに +1 ずつ増加するカウンタ** である。セグメント数と開始値だけがセッションごとに異なる(最大のセッションで 106 セグメント = §12 の総当たり対象と一致)。
- 対照として、起動時の別系統の AES セッションの CW は全 16 バイトが高エントロピーの固定値で、プロセスグローバルからコピーされる別系統の供給である。録画パスの供給様式はこれと明確に異なる。
- 解釈: セグメントごとに 1 バイトしか変化しない値は AES 鍵そのものではあり得ず、**録画パスの control_words は「鍵への参照トークン」であり、実効鍵はファームウェアがトークンとチップ内部状態から解決する**と見るのが整合的である。トークン本体(15 バイト)がブート内の全録画で共有される点も、タイトルや番組に紐づく鍵ではなく、ブート(ないしサービス)単位の文脈であることを示す。本体がブート単位か個体単位かは、観測下で録画が発火したブートが 1 回しかないため未確定である([docs/04](04_open_questions.md))。

### 10.4 OTP との接続: 無し

- §11(E1)の時点で「装填経路が OTP index を参照する形であれば、OTP 走査の分布と照合できる」としていたが、その前提はホスト側では反証された: 録画開始時にも当該ブート全量でも READ_FROM_OTP の発行は 0 件で、録画の鍵装填が OTP を読む経路は存在しない。
- dtvtuner 内の READ_OTP 発行手続きは、自身でドライバハンドルと RSA モードの GENERIC セッションを開いて 1 つの index を読み 8 バイトを返す独立したライブラリユーティリティで、参照元は限られ、録画コードからは到達せず、当該ブートでも発火していない。
- したがって **§11 の OTP 分布(nonzero の多い領域を含む)と突き合わせる対象は録画パスには存在しない**。nonzero の 171 index が何を保持するかは未解明のままだが、少なくとも録画 AES の鍵装填には使われていない。副線については、到達可能な素材が OTP にあっても、それが録画鍵に連なるという装填経路側の根拠は本節で失われた。実効鍵の解決はチップ内ファームウェア側で閉じており、ホストから観測・再現できる入力はトークンまでである。

### 10.5 判定

- **仮説 (α)(末尾フィールドが鍵参照を担う)は棄却(確定)**: 末尾フィールドは録画時も全て 0 であり(§10.1)、仮に非ゼロでも録画時のフラグでは SDK 意味論上機能しない。
- **仮説 (β)(実効鍵はセッション文脈に束縛される)は「実効鍵は CW トークンからファームウェア内部状態で解決される」という形に具体化して採用**: 実効鍵はパケット可視フィールドのどこにも存在しない。E2(§12)が失敗した理由はこの解決を再現できないためであり、自己検証で器自体はホスト供給 CW で双方向に働くこと(§12.1)とは矛盾しない(任意 CW の往復は「トークンとして受理された値同士」の往復であり、録画トークンの解決結果とは別物)。E2 の実施が録画したブートとは異なるブートだった点も、トークン本体がブート単位であれば失敗の十分条件になる(個体単位かは未確定)。

## 11. 実験 E1 — OTP は全 index がホスト可読

READ_FROM_OTP のインデクス空間を実機で走査した(実験設計は [docs/03](03_playback_path_and_oracle.md))。実行環境は公式ユーザーランド上で自前ツールを root として動かす観測環境で、カーネルスロット・sys1・SPI への書込みは無く、`.dat` へのアクセスも無い(OTP の読み出しのみ)。記録するのはインデクスごとの成否とゼロ/非ゼロの分類のみで、**応答の生値はツール内でも保持せず、記録にも素材にも残していない**。

### 11.1 READ_FROM_OTP のレイアウト(静的準備で確定)

dtvtuner の逆コンパイル(READ_OTP の発行手続き、OPEN_GENERIC、CLOSE_GENERIC)と既存ツールから確定した:

- 伝送路: `/dev/vixs/xcodedrv` への `ioctl(fd, 0x17241724, pkt)`
- パケット共通部: +0x00 = パケットサイズ、+0x04 = コマンド、+0x0C = status(送信時 2、成功時 1)、+0x94 = 2000、+0xA4/+0xA8 = ストリームハンドル
- OPEN_GENERIC: cmd 0x2e、パケット 0x208 バイト、generic_mode は +0xAC(本実験では dtvtuner と同じ RSA モード 0x8000000)、+0xB0 = 0、+0xB8 = 0
- READ_OTP: cmd 0x116、パケット 0xb8 バイト、KeyIndex は +0xAC、応答 8 バイトは +0xB0
- CLOSE_GENERIC: cmd 0x2f、パケット 0xb4 バイト

index ごとの手続き(ドライバ open → OPEN_GENERIC(RSA)→ READ_OTP → CLOSE_GENERIC → close)は dtvtuner 自身の発行手続きと同一である。走査ツールは分類(応答 8 バイトの OR が 0 か否か)だけを出力し、分類した直後に応答バッファをゼロ消去する設計にした(エラーパスでも生値が出力される経路は無い)。

### 11.2 結果: 全 256 index が成功、zero=85 / nonzero=171

| 分類 | 件数 | index 範囲 |
|---|---|---|
| zero(応答 8 バイトが全ゼロ) | 85 | 0x00、0x03–0x04、0x06、0x08、0x0A、0x0D、0x31–0x3F(15)、0x43–0x81(63) |
| nonzero | 171 | 0x01–0x02、0x05、0x07、0x09、0x0B–0x0C、0x0E–0x30(35)、0x40–0x42、0x82–0xFF(126) |

- 分布の構造: nonzero は上位 0x82–0xFF の 126 件連続が支配的で、0x0E–0x30 の 35 件連続が次ぐ。zero は 0x43–0x81 の 63 件連続と 0x31–0x3F の 15 件連続という 2 つの大きなブロックと、低位の散在 7 件で構成される。
- アンカー: Sony 自身が使う 0xFF(§8)は nonzero で予測どおり。意味の候補だった 0x0B も nonzero。先行スモークテストの対照 0x40 も nonzero で、全範囲結果と一致する。
- 但し書き: class=zero は「応答 8 バイトが全ゼロだった」という測定事実の記録であり、未書込みのスロットなのかゼロ値が格納されているのかは、この測定では区別できない。
- 副次確認: GENERIC の RSA モードセッションは 256 回すべて製品 FW 上で開閉できた。E2(直接構成の受理測定、[docs/03](03_playback_path_and_oracle.md))の前提確認も併せて済んだ。
- 実施経緯の訂正: 本実験は一度「未実施」と誤って報告されたが、結果ファイルの実在と内容(全 256 件の分類 + 集計)およびアンカー 3 点の一致から、実行が完了していたことを確認した。本節は実物に基づいて記録する。

### 11.3 含意と、その後の更新

- **第一関門は通過**: 実測では READ_FROM_OTP は index 空間 0x00–0xFF の**全て**で受理され(err=0)、171 件が非ゼロの内容を返した。副線の前提のうち「鍵に連なる素材がホストから到達可能な形で存在するか」には、少なくとも到達可能性の面で肯定的な実測が得られた。§7.4 の「鍵はホストのどこにも存在しない」という表現は、OTP 読み出し経路については「ホスト可読な素材が 171 index 分存在する」と修正される。
- **残る問題は意味論**: どの index が何を保持し、録画の GENERIC-AES セッションへの鍵装填がどの index(あるいは鍵スロット)を参照するかは、本走査では分からない。応答は index あたり 8 バイトであり、16 バイトの AES 鍵との対応付けには装填経路側の情報が要る。
- **その後の更新(§10.4)**: 装填経路の静的特定により、録画パスが OTP を読む経路は存在しないことが確定した。したがって副線の現判定は「到達可能性は実証済みだが、録画鍵に連なる装填経路側の根拠は失われた」であり、171 件の nonzero が録画鍵に連なること自体は未証明のままである(楽観しない)。
- **未実施**: 再起動間の安定性(再起動後に再走査し、分類が一致するか)は未実施。0xFF / 0xB の意味論も未確定のまま([docs/04](04_open_questions.md))。

## 12. 実験 E2 — 録画時 CW の単純ミラーは棄却

問いは「保存済み `.dat` を、新規に開いた GENERIC セッションへ録画時の鍵素材を渡して復号できるか(チップを復号オラクルとして使えるか)」。実験はすべて `.dat` のコピーに対して行い、原本は読み取りのみ(事後に原本のハッシュが実験前の記録値と完全一致することを確認。原本・録画・sys1・SPI への書込みは無い)。鍵素材(control word)の生値は、ツールへの受け渡しを標準入力のバイナリに限定し、引数・ファイル・ログのいずれにも残していない。本節の記録にも生値は含まれない。

### 12.0 対象素材と同定

- 対象は観測ラウンドで録画したタイトル(地デジ 3 倍速)の先頭コピー(1,032,192 バイト = 0xFC00 × 16 行分ほか)。原本は 549,814,272 バイト。
- **素材の同定**: 実験ファイルは、録画時に dtvtuner が使った SCRAMBLER セッション(fd は観測時のもの)の出力そのものであることを確認した(ファイル先頭と、録画開始直後の書込み先頭 32 バイトが一致)。すなわち「チップが書き出した暗号文」と「実験に供したコピー」の同一性はバイトレベルで担保されており、コピーの取り違えや別タイトルの混入は無い。
- 録画時、GENERIC-AES セッションは 2 本開かれた(ともに mode 0x4000 / req_size 0xFC00、§9.1)。一方のセッションの SCRAMBLER(cmd 0x108)総呼出は 8,558 回で、control word は約 81〜82 呼出ごとに回転し、相異なる CW の区間(セグメント)は **106 件**だった。
- 鍵装填の経路に関する再確認: 回収済み観測ログの全量に **SET_CONTENT_KEY(0x102) / SET_KEYSTORE_KEY(0x113) / RESERVE_KEYSTORE_SLOT(0x114) の発行は皆無**(§9.1 の実測と一致)。録画セッションへの鍵の渡し方は、SCRAMBLER パケット内包(control word)か、セッション開設時の文脈のどちらか(あるいは両方)しか残っていない。

### 12.1 器の自己検証(ラウンドトリップ) — ホスト供給 CW で双方向に働く

否定的な結果を根拠にする前に、ツールと経路そのものを自己検証した:

- 合成平文(192 バイトごとに 0x47、残りは PRNG)を用意し、GENERIC セッション(mode 0x4000、req_size 0xFC00)上で mode 2(AES_CBC_ENCRYPT)により任意の CW で暗号化した。
- セッションを閉じて**別セッション**を開き直し、同じ CW で mode 6(AES_CBC_DECRYPT)にかけたところ、**64,512 / 64,512 バイトが完全一致**して平文に戻った。

すなわち、録画保存の器(GENERIC-AES 0x4000 / 0xFC00 + SCRAMBLER)は、**ホストが供給する control word を鍵として受理し、暗号化・復号の双方向に正しく働く**。§12.2 の否定的結果は「ツールが間違っている」「器がホスト供給鍵を受け付けない」という説明では片付かないことが、この自己検証で先に潰れている。

ツールの使う SCRAMBLER パケット(IOCTLSDEVSCRAMBLER2、cmd 0x108、パケット 0x160 バイト)の確定レイアウト: +0xA4 = セッションハンドル、+0xAC = pDest(u64)、+0xB4 = pSrc(u64)、+0xBC = scramble_flags(本実験では初行 0x0c / 継続行 0x04、CW_AS_INDEX 試行時は 0x20 を追加)、+0xC0 = scramble_mode(**2 = AES_CBC_ENCRYPT、5 = AES_ECB_DECRYPT、6 = AES_CBC_DECRYPT、20/21/26 = AES TS residue DECRYPT**)、+0xC4 = numOfLine(=1)、+0xC8 = scrambledBytesPerLine(=0xFC00)、+0xCC = directBytesPerLine(=0)、+0xD0/+0xD4 = source/dest Pitch、**+0xD8 = control_words[24]**(先頭 16 バイトを使用)、+0xF0 = IV_seed[16]、+0x100 = ALU_num[16]、+0x110 = control_words2[24]、+0x15C = numScrambledBlocks(OUT)。判定指標は復号出力 0xFC00 バイトに対する TS 同期構造(192 バイト周期位置の 0x47 一致数、正解なら 336/336。ランダム出力での期待値は 336/256 ≈ 1.3 で、観測される上限は 5 程度)。

### 12.2 候補マトリクスと結果 — 全滅

対象ファイル(録画時に暗号化を担ったセッションの出力)に対し、新規セッションで以下を試行した(いずれも OPEN は受理され、SCRAMBLER も成功を返した):

| # | 構成 | 結果(sync 数) | 判定 |
|---|---|---|---|
| 1 | mode 6(CBC 復号)+ 録画セッション 1 の CW#1(セグメント 1)、先頭 8 行 | 全行 **0/336**(188 周期は偶然水準、相異なるバイト値 256) | 不成立 |
| 2 | mode 6 + 並行セッションの CW#1、先頭 8 行 | 1〜5/336(偶然水準) | 不成立 |
| 3 | mode 6 + **全 106 セグメント**の CW で先頭 1 行を総当たり | 最大 **5/336**(その他は 0〜4) | **決定的に棄却** |
| 4 | CW バイト順バリアント(ワード単位 BE 化 / 16 バイト全体反転 / ワード順反転) | いずれも偶然水準 | 不成立 |
| 5 | mode 5(ECB 復号)、mode 2(CBC 暗号化 = 逆向きの可能性) | 偶然水準 | 不成立 |
| 6 | CW_AS_INDEX(フラグ 0x20、control word を鍵ストア index として解釈)index 0〜7 | 偶然水準 | 不成立 |
| 7 | GENERIC-DTCP(mode 0x200)の SEND/RECV | OPEN は受理。しかし SEND は**未処理のまま**、RECV は全試行タイムアウトでデータなし | 経路不発 |

### 12.3 判定 — 単純ミラー仮説は棄却

**「録画時の control word を新規セッションへ渡せば、保存済み `.dat` が復号できる」という単純ミラー仮説は棄却する。** 根拠は (a) ラウンドトリップ自己検証で器とツールの正しさが実証されていること、(b) 正解の CW が存在すれば 106 セグメントのどこかで 336/336 が出るはずが、最大でも偶然水準の 5/336 に留まったこと、(c) バイト順・モード・index 解釈の主要バリアントも全滅したこと、の 3 点である。録画セッションの実効鍵(あるいは復号に必要な文脈)は、SCRAMBLER パケットの control word フィールド**だけ**では再構成できない(理由は §10.3 のトークン解決で説明が付いた)。

残仮説として当時挙がったもの: (α) パケット末尾フィールドが鍵参照を担う(→ §10.1 で棄却)、(β) 実効鍵がセッション確立文脈に束縛される(→ §10.5 で具体化して採用)、(γ) DTCP 経路は素のセッションでは処理されない(GENERIC-DTCP は open は受理されるものの SEND が処理されず、DTCP-IP 配信は AKE で確立した文脈の内側でのみ復号 + 再暗号化が結合するという静的結論と整合する。DTCP モードを復号オラクルの入口にする道は、AKE 文脈の再現なしには開かない)。

### 12.4 未実施の試行

- **mode 20 / 21 / 26(AES TS residue DECRYPT)での復号試行**: SCRAMBLER のモード表には TS residue 系の復号モードが存在するが、本実験の候補には含めなかった(素材が CBC 保存と整合する §9 の観測を優先したため)。
- **IVDR(generic_mode 0x2000)セッションの probe**: open の受理可否すら未測定。
- **OPEN_LOCAL(0x10)の生 ioctl 試行**: 製品コードではラッパー経由でのみ使われ、生 ioctl の発行形式での受理測定は未実施。

## 13. 鍵監査の所見(見落としの点検)

外部で「復号に成功した」という方法開示のない主張があったことを受け、実機側の見落としを 3 面(デバイス / ファイル / プロセス)で列挙点検した:

- 列挙範囲では、現行モデル(§7〜§10)と矛盾する所見は無かった。AV ドライバを開いている他デーモンの fd は継承された未使用のものであること(誤読しやすい点)、証明書置き場のファイルは TLS 用 CA 証明書 1 件のみであること、sys1 上に鍵素材は無いこと、などを確認した。
- **表現の訂正**: この点検は「列挙した範囲で見つからなかった」のであって、**鍵の置き場が存在しないことの証明ではない**。副線([docs/04](04_open_questions.md))を閉じる材料にはしない。
