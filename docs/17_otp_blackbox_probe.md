# 17. Debian 稼働下のブラックボックス探索:OTP 固定セルの意味論照合とコマンド面応答マッピング

XCode FW の静的解析が到達限界に達した(→ [16](16_xcode_fw_drm_phase8.md) §6)ことを受け、静的解析では到達できなかった対象を、Debian 12 + Linux 6.12 が通常サービスごと稼働している実機の上から、チップへの実コマンドで測った記録。2 フェーズ構成で、フェーズ 1 は [07](07_otp_value_level_stability.md) で値レベル固定と確定した OTP セルの意味論照合、フェーズ 2 はドライバ API / 伝送層 (mhcmd) コマンドのホスト側応答マッピング。

> 結果の要約:
> - **OTP index 0xFF の応答 8 バイトは、SPI フラッシュ INF2 セグメントに格納された個体チップ ID (8 バイト) と完全一致した。** 固定域の nonzero セルで意味論が同定できたのはこの 1 件。他の 45 セルは、試した候補 6 種 × 照合形式の範囲では一致しなかった (範囲は §3.2 に明記。不在の断定はしない)。
> - フェーズ 2 の応答マップは §5.1 の表が全て。要点は (i) `SET_KEYSTORE_KEY` (mhcmd 42) は実在し、ヘッダ記載の範囲 (0–127) 外の index 200 へのダミー書き込みまで受理した、(ii) `RESERVE_KEYSTORE_SLOT` (mhcmd 44) はパラメータ 4 変種すべてで失敗した、(iii) `XC4_RSA_REQUEST` (mhcmd 43) はダミー入力に応答し、AKE 中核の HW RSA エンジンがホストから到達可能と実測できた、(iv) `GET_RANDOM_BYTE` (mhcmd 41) は実働し、(v) `GET_HARDWARE_CAPS` はドライバに実装が無く無効コマンド応答だった。
> - 実験中、実機の通常サービス (チューナー受信サービス等) への干渉は無かった。

## 1. 目的と安全上の前提

### 1.1 目的

- フェーズ 1: [07](07_otp_value_level_stability.md) で「値レベルで固定」と確定した 45 個の nonzero セル (0x00–0x81 内) と 0xFF について、既知の個体識別系の値と一致するものがあるかをメモリ内照合で調べ、セルの意味論を同定する。
- フェーズ 2: 静的解析 (docs/08–16) で FW 側ハンドラに到達できなかったコマンドについて、ホスト側の応答 (成否・エラーコード・応答フィールド) を実測し、「ハンドラが存在するか」「ドライバ/FW の検証がどう働くか」の地図を作る。

### 1.2 安全上の前提 (実施前に静的に確認した事項)

- 進め方は docs/06・07 の前例に倣い、通常サービス稼働中のまま、自前の GENERIC セッション (RSA モード) を開閉してその中で測る。サービスは止めない。
- 使うコマンドは GPL ソースツリーのヘッダ (`drv_if.h` / `mipshost.h`) で定義が確認でき、かつ GPL ドライバ実装 (`Os_General.c` / `txcrsa.c`) でユーザパケット構造と検証動作を実読できたものだけに限った。意味不明のコマンド番号は投げていない (無効番号への応答確認として、列挙の直後 0x11B を 1 件だけ測った。ドライバ実装の default 節が `IOCTL_RET_CMD_INVALID` を返すことを実読した上で実施)。
- **ドライバ実装の実読で判明した重要な前提**: `READ_FROM_OTP` / `SET_KEYSTORE_KEY` / `RESERVE_KEYSTORE_SLOT` のドライバ側処理は、ユーザパケットの `stream_handle` をドライバ内ストリームオブジェクトへの参照としてそのまま辿る。したがってこれらのコマンドには必ず自セッションの正規ハンドルを使い、0 や任意値を渡す探査は行わなかった (不正な参照をカーネルに踏ませる危険があるため)。
- OTP の生値は出力・保存しない (照合はツール内メモリで完結、ダイジェストのみ外に出す)。ただし固定域の生値ダンプについては §4 の方針変更があり、開発側にのみ保存した (本リポジトリには載せない)。
- SPI・HDD への書き込みは行っていない。チップ側の操作は全て揮発セッション内であり、永続状態を変えるコマンド (後述の対象外判断) は使っていない。

## 2. ツール

いずれも開発側の作業領域に保管 (本リポジトリには載せない)。実機上では静的リンクの MIPS バイナリとして実行した。

| ツール | 役割 | ソース SHA-256 |
|---|---|---|
| `otp_probe` | フェーズ 1: 固定域 (0x00–0x81 + 0xFF = 131 件) の走査・SHA-256 出力・候補照合、`dump` モード (生値を標準出力へバイナリ出力、状態とダイジェストは標準エラーへ) | `b9076ede…` |
| `cmd_probe` | フェーズ 2: コマンド毎に 1 プロセスで測定 (fwstate / getcaps / hwcaps / portaddr / rand / unknown / keystore / reservebad / setoor / rsa) | `c91be1a3…` |
| `build_candidates.py` | SPI ダンプから INF2 本体を正規手順 (`spi_segments.py` によるセグメント抽出・復号) で取り出し、候補ファイルを生成 (値はスクリプトの標準出力に出さず、構造メタデータだけを表示) | `ddd1cea4…` |

検証ゲート: 両ツールとも自己試験 (SHA-256 既知ベクタ + 照合ロジックの合成セル試験) を **x86・qemu・実機の 3 環境**で走らせ、実機で全パスしてから本測定に入った。-O2 ビルドで実機だけ照合が誤動作した件は §7 に記録する。

候補ファイルは 53 バイト (SHA-256 `ceadb1cf…`)。候補の値は INF2 本体 (49,088 バイト、非ゼロは 20 バイトだけという既知の性質と一致することを生成時に確認) から機械的に切り出した。

## 3. フェーズ 1:OTP 固定セルの意味論照合

### 3.1 候補 (kind)

既存記録で得られている個体識別系の値から、6 種を候補とした。値そのものは書かない。

| kind | 候補 | 長さ | 出所 |
|---|---|---|---|
| 1 | 個体チップ ID (生バイト列) | 8 | SPI の INF2 セグメント本体 +0x60 |
| 2 | DTCP 機器 ID | 5 | kind 1 の先頭 5 バイト (裏面 DTCP ラベルと一致する値、[01](01_dtcp_firmware_analysis.md)) |
| 3 | INF2 +0x20 の ASCII 文字列の先頭 8 文字 | 8 | INF2 本体 +0x20 (12 バイトの印字可能 ASCII) |
| 4 | MAC アドレス | 6 | 実機 eth0 (ネットワーク記録で既知) |
| 5 | チップ ID の 16 進 ASCII 表現の先頭 8 文字 | 8 | kind 1 の hex 表現 (`.hai` の個体 ID 欄に使われる形式の先頭半分) |
| 6 | チップ ID 末尾 3 バイト + 0x00 0x00 | 5 | RandomNumber 候補 (a) の形式 ([02](02_dat_encryption_model.md) §15.5。後に RandomNumber は揮発値と確定し棄却された仮説の形式だが、照合範囲の明示のため含めた) |

### 3.2 照合形式 (form)

8 バイト応答との間で、次の形式を全て試した。

- form 0:8 バイトそのまま一致 (長さ 8 の候補のみ)
- form 1:8 バイト全反転
- form 2:4 バイトワード swap
- form 3:前方ゼロ埋め (候補が先頭にあり残りが全て 0)
- form 4:反転して前方ゼロ埋め
- form 5:部分列 (前方) がオフセット 0–(8−長さ) のいずれかに出現
- form 6:部分列 (反転) がいずれかのオフセットに出現

照合は nonzero セルだけを対象とした (全ゼロセルは、候補側に全ゼロのものが無いためゼロ埋め形式でも一致し得ない)。

### 3.3 結果

走査は全 131 件成功 (エラー 0)。分類は zero 85 件 / nonzero 46 件 (45 + 0xFF) で [07](07_otp_value_level_stability.md) と一致し、各セルの SHA-256 ダイジェストも全 131 件が [07](07_otp_value_level_stability.md) の scan1 と完全一致した (本ラウンドでも値レベル固定を再確認)。

一致は 1 件:

| index | 一致した候補 | 形式 | 備考 |
|---|---|---|---|
| 0xFF | kind 1 (チップ ID 生 8 バイト) | form 0 (そのまま) | kind 2 (先頭 5 バイト) も form 5 / オフセット 0 で同時に一致 (8 バイト一致の帰結) |

**すなわち OTP index 0xFF には、SPI の INF2 に格納された個体チップ ID そのものが入っている。** これは Sony 自身のコードが index 0xFF を使う ([02](02_dat_encryption_model.md) §8) ことと整合する。DTCP 機器 ID がその先頭 5 バイトであることも、OTP 経由で裏付けられた形になる。

他の 45 個の nonzero セル (0x01, 0x02, 0x05, 0x07, 0x09, 0x0B, 0x0C, 0x0E–0x30, 0x40, 0x41, 0x42) は、§3.1 の候補 6 種 × §3.2 の形式の範囲ではいずれとも一致しなかった。これは「試した範囲で一致が無かった」という記録であり、これらのセルが他の既知量 (例えば導出の中間値や断片) と無関係であることの証明ではない。次候補は §8 に挙げる。

副次観察:ダイジェストの比較から、index 0x05 と 0x09 は同一の 8 バイト値を持つ ([07](07_otp_value_level_stability.md) の公開ダイジェストからも読み取れる事実の再確認)。意味は未確定。

## 4. 固定域の生値ダンプ (開発側のみ)

実施当日の方針変更 (プロジェクトオーナーの決定、2026-11-13) により、「公開予定のリポジトリでは従来通りハッシュのみ、非公開の開発側では生値を保存してよい」となった。これを受け、固定域 131 件 (0x00–0x81 と 0xFF) の生値を新規に読み取り、**開発側 (非公開リポジトリ) にのみ**ダンプファイルとして保存した。本リポジトリからはダンプの所在とハッシュだけを参照する。

- 形式:見出しなし、index 昇順 (0x00, 0x01, …, 0x81, 0xFF) に 8 バイトずつ連結した 1,048 バイト
- ダンプ全体の SHA-256:`32dc7255182d3da4bb45839a523e7ed1a74ebd8476bf0e297ab36889508cb577`
- 検証:ダンプの各 8 バイトから再計算したダイジェストが、採取時のログ (131 件) および本ラウンドの照合走査のダイジェスト (131 件) と全件一致すること、さらに [07](07_otp_value_level_stability.md) の scan1 のダイジェストとも固定域 131 件全てが一致することを、PC 側で機械的に確認した
- 揮発域 (0x82–0xFE) は読み出すたびに値が変わり保存の意味がないため、ダンプ対象に含めていない

## 5. フェーズ 2:コマンド面の応答マッピング

### 5.1 応答マップ (全結果)

`status` はユーザパケットの return_value フィールドで、値の意味は `drv_if.h` の IOCTL 完了コード列挙による (1 = COMPLETE、2 = FAILED、3 = CMD_INVALID、4 = PARAM_INVALID)。ioctl 自体の戻り値は成功時 1、ドライバ側で弾かれた場合 −1 だった。

| コマンド | ドライバ API | mhcmd | 測定内容 | 結果 |
|---|---|---|---|---|
| GET_FW_STATE | 0x103 | — | 引数なし | status 1。fw_state = 0 (FW_ALIVE)、cpu_id = `0x02b80010`、epc = `0x0f802020` |
| SDEV_GET_CAPS | 0x0E | — | 引数なし | status 1。video_in `0x258b` / video_out `0x6dfe` / audio_in `0x8c00` / audio_out `0xff9b` |
| GET_PORT_ADDR | 0x15 | — | 引数なし | status 1。port_addr = 0 |
| GET_HARDWARE_CAPS | 0x21 | — | 引数なし | status 3 (CMD_INVALID)。**このドライバでは未実装** (GPL 実装にも case が無いことと一致) |
| 未定義番号 0x11B | — | — | 列挙直後の番号 | status 3 (CMD_INVALID)。ドライバ default 節の実読通り |
| GET_RANDOM_BYTE | 0x112 | 41 | len = 16 を 2 回 | 両回とも status 1、16 バイト全て非ゼロ、内容は毎回異なる (ダイジェストで確認)。**FW 側ハンドラ実働** |
| 〃 | 〃 | 〃 | len = 0 | status 1 (空応答として正常完了) |
| 〃 | 〃 | 〃 | len = 257 | status 4 (PARAM_INVALID)。GPL 実装通りドライバ側で弾き、FW に届いていない |
| READ_FROM_OTP | 0x116 | 45 | フェーズ 1 の全走査 | 全 131 件 status 1 (既知の通り実働) |
| RESERVE_KEYSTORE_SLOT | 0x114 | 44 | (スロット数, 要求 index) = (2, 0)、(0, 0)、(5, 0)、(2, 0x40) | **4 変種全て status 2 (FAILED)**。応答側 KeyIndex は入力のエコーのまま |
| SET_KEYSTORE_KEY | 0x113 | 42 | KeyIndex = 200、スロット数 2、値は合成ダミー 32 バイト | **status 1 (受理)**。§5.3 参照 |
| XC4_RSA_REQUEST | 0x115 | 43 | ダミー入力 (メッセージ 16 B、指数 65537、法 128 B) | status 1、outLen = 256、出力の SHA-256 = `72d6904b…`。§5.4 参照 |
| GET_MAC | 0x117 | 46 | — | **対象外**。§5.5 参照 |

### 5.2 RESERVE_KEYSTORE_SLOT の失敗について

RSA モードの GENERIC セッションの正規ハンドルを使い、パラメータを 4 変種振っても全て CMD_FAILED だった。考えられる理由は次の通りで、いずれとも判定していない。

- (a) mhcmd 44 の FW 側ハンドラが製品 FW の受信側プロセッサに存在せず、伝送層の失敗が CMD_FAILED に写っている。静的解析でハンドラに到達できなかった事実 (docs/08–16) と整合するが、SET (mhcmd 42) が受理された以上、「セキュリティ系コマンドが一律に無い」形ではない
- (b) RESERVE は GENERIC (RSA) 以外のセッション/ストリーム種別を要求する
- (c) 未試行のパラメータ意味論がある (ドライバ実装は NumberOf64BitSlot と KeyIndex の両方をそのまま FW へ転送する。KeyIndex は drv_if.h では IN、mipshost.h では OUT とコメントが食い違っており、両義に解釈して 0 と 0x40 の両方を試したが結果は同じだった)

なお、SET が受理されるため、キーストアへの書き込み経路自体は生きている。RESERVE を経ずに SET だけでスロットを使う運用が FW の想定形なのかもしれないが、未判定のまま記録する。

### 5.3 SET_KEYSTORE_KEY の範囲外受理について

ヘッダ (`mipshost.h` / `drv_if.h`) は KeyIndex の範囲を 0–127 と記す。これを検証するため、範囲外である 200 への書き込み (値は合成ダミー) が弾かれるか測ったところ、**status 1 で受理された**。すなわちこの層では 0–127 の範囲検証は働いていない (検証が別の層にある可能性、キーストアの実容量が 128 スロットより大きい可能性、index がマスクされる可能性は未分離)。書かれたのは合成ダミー値であり、キーストアはチップ内の揮発領域で、録画・再生の実データや永続状態には触れていない。以後、範囲外 index が「安全な捨て先」であるという前提は使えない (書き込みは実際に効く)。

### 5.4 XC4_RSA_REQUEST の応答について

[15](15_xcode_fw_drm_phase7.md) で「gen_kauth の中核計算は HW RSA/ECC アクセラレータのドライバ」と静的に確定していたエンジンに対し、ホスト側コマンド (mhcmd 43) がダミー入力で正常完了し、256 バイトの出力を返した。静的には到達できなかった AKE 系演算が、Debian 稼働状態のホストから到達可能であることの実測になる。ただし今回の入力は形式だけを整えたダミーであり、**出力が正しい RSA 演算結果であるかは検証していない** (outLen が法の長さ 128 ではなく 256 だった点も含め、入出力のバイト順・パディング規約の確定が先に必要)。既知ベクタでの照合は次段の候補 (§8)。

### 5.5 対象外としたコマンドと判断

- `CMD2_SDEV_GET_MAC` (0x117 / mhcmd 46):**名称に反して MAC アドレス取得ではない**。`mipshost.h` / `drv_if.h` の構造体実読により、ストリームに対する AES-CMAC 演算 (control_words と IV seed を取り、データ plane の暗号演算をする) コマンドと判明したため、読み取り系とみなして測る対象から外した。
- `CMD2_SDEV_NVMDATA` (0x11A / mhcmd 50):NVM (不揮発) データを扱う名前であり、永続状態に触れる可能性があるため対象外。
- ストリーム開設系 (OPEN_SECUREDTS 0x30、OPEN_LOCAL 0x10、OPEN_TS_PASSTHROUGH 0x2D 等) とデータ転送系:データ plane そのものであり、「応答マッピング」の範囲を超えるため対象外 (OPEN_GENERIC / CLOSE_GENERIC は docs/06・07 以来の確立した手順として使用)。
- 状態変更系 (LOAD_MIPS_CODE 5、DRIVER_CHIP_INIT 0x1E、SET_POWER_MODE 0x20、INIT 0x100 等):チップの状態を変えるため対象外。
- `TxcLoadKeystoreKeyFromOTP` について:GPL ドライバ実装 (txcrsa.c) には「OTP からキーストアへ鍵を読み込む」関数の実体があるが、**GPL ツリー内にその呼び出し元 (対応する ioctl 番号) が存在しなかった**。ホストからは単独では叩けない経路とみられる (静的所見)。

## 6. 機体への影響

全測定を通じて通常サービスは稼働継続し、チューナー受信サービスの待受ポート (8301) は各測定の前後で応答を確認した。機体の再起動・ドライバの再読み込みは行っていない。実機に置いたツールと中間ファイルは測定後に削除した。

## 7. ツールの検証で見つけた注意点 (-O2 ビルドの照合誤動作)

フェーズ 1 の照合ツールについて、-O2 でビルドした版が **実機でのみ**照合の一部形式 (form 0 / 1 / 5 / 6) を偽陰性にした。同じバイナリは qemu-mipsel では全パスし、-O0 ビルドは実機でも全パスした。SHA-256 の自己試験は全環境でパスしていたため、誤動作は小さなバイト比較ループの最適化生成コードに限られるとみられるが、**特定の命令への分離はできていない** (実機 CPU と qemu の実行差異の詳細は未追跡)。対策として、本測定のツールは -O0 でビルドし、自己試験を実機上で全パスすることを本測定開始の条件にした。この教訓は、実機で走る小さな測定ツール全般に当てはまる:エミュレータでの合格は実機での合格を保証しない。

## 8. 未確定事項と次段への申し送り

- 固定セルの残り 45 件の意味論:次候補として、(i) tpkeydec の導出で使う固定列 A / B ([02](02_dat_encryption_model.md) §15.5、全機共通で秘密情報ではない) の断片との照合、(ii) Kdev (16 バイト) の前半/後半 8 バイトとの照合 (Kdev は素材 S にブート揮発の RandomNumber を含むため、**今回のブートで採取した S から導出した Kdev と同一ブート内で照合する**場合にのみ意味がある)、(iii) セル同士の関係 (0x05 と 0x09 が同値である件を含む) の構造分析、が挙げられる。いずれも未実施。
- RESERVE の失敗理由の分離:別種セッション (AES モードの GENERIC 等) での再試行が候補。ただし SET が単独で受理される以上、優先度は低い。
- RSA 演算の正しさ:既知の小さなベクタ (短い法・指数での冪剰余) を作り、PC 側の多倍長演算結果と照合すれば、入出力規約 (バイト順・outLen の意味) まで確定できる。AKE の素材起源追跡 ([16](16_xcode_fw_drm_phase8.md) の申し送り) と接続する候補。
- キーストアの実容量と index の写像:SET の受理範囲を二分探索的に測ることは可能だが、実在スロットへのダミー書き込みが増えるため、実施は慎重に判断する (今回は index 200 の 1 件のみ)。
