# 18. OTP 固定セル連結鍵仮説の実測スイープ — 2 セル連結は実測で棄却(範囲明記)

副線(鍵だけ抜いて PC で復号)の分岐判定として実施した実測実験の記録(2026-11-13 実施)。問いに対する結論を先に書く:

- **仮説「`.dat` の実効 AES-128 鍵は、XCode OTP の値レベル固定セル(8 バイト)のうち 2 セルをそのまま連結したもの」は、本実験の範囲ではヒット無し**だった。候補の記述総数 77,596 件(相異なる鍵 8,281 件)を、実在の `.dat` 暗号文に対してホスト側 AES で全数試行し、正解なら 336/336 になるはずの TS 同期は最大で 7/336 に留まり、全指標が帰無分布(ランダムな誤鍵)の期待値と整合した。スクリーニングで抽出した 43 件の「やや高い」候補は、別タイトル・別位置のサンプルでの再確認でも最高 8/336 で、構造は一切出なかった。
- ただし棄却できる範囲は正確に限定される(§7)。**周期性を壊す未知の変換層が復号後に掛かる場合の連結鍵そのものは、本実験では棄却できない**。これは実施前にプロジェクトオーナーから追加された留保(「復号した後に独自形式の変換がかかる可能性もある」)を受けたもので、判定には周期性に耐性のある指標を併用したが、それでも届くのは「周期性を保つ変換まで」である。
- 鍵候補の値そのものは本書に書かない(候補はセルの index の組とバイト順バリエーションでのみ識別する)。OTP の生値ダンプは開発側(非公開)にのみ保存し、本書からは所在とハッシュだけを参照する([docs/17](17_otp_blackbox_probe.md) §4 と同じ方針)。

## 1. 問いと仮説

- [docs/07](07_otp_value_level_stability.md) で、OTP の index 0x00–0x81(130 件)と 0xFF は値レベルで固定と確定した。読むたびに値が変わる揮発域(0x82–0xFE)は、再起動を跨いで再生できる録画の鍵素材にはなり得ない(機体自身の再生が成立しなくなるため)。したがって「鍵だけ抜く」素材の候補は固定域に限られる。
- 固定域のうち nonzero は 0x00–0x81 の 45 件と 0xFF の 1 件。セルは各 8 バイトで、AES-128 の鍵長 16 バイトはちょうど 2 セル分である。
- **仮説: 実効鍵 = 固定セル 2 件の単純連結**(順序・各セルのバイト反転のバリエーションを含む)。根拠は「そうであってほしい」という以上のものではないが、検証コストが小さく、当たれば副線が一気に開け、外れれば実測による棄却の記録になる。プロジェクトの受け入れ基準([AGENTS.md](../AGENTS.md) §2.2)では、否定的結論には積極的な証拠が要る。本実験はその証拠を作る側の作業である。

## 2. 素材と同一性ゲート

### 2.1 OTP 固定域の生値

- 読み取りには [docs/17](17_otp_blackbox_probe.md) の `otp_probe` の `dump` モード(固定域 131 件 = index 0x00–0x81 と 0xFF を読み、生値を標準出力へバイナリ出力、ダイジェストは標準エラーへ)を使い、実機(通常サービス稼働中の Debian 環境)から 1 回だけ新規に読み取った。実機への接触はこの読み取り専用走査のみで、録画・再生中の処理への干渉はない。ツールは自己試験(selftest)通過後に実行し、実行前後でバイナリの SHA-256 が同一であることを確認した。採取後に実機側の一時ファイルは削除した。
- **同一性ゲート**: 採取した 131 セル全件について、各 8 バイトの SHA-256 が [docs/07](07_otp_value_level_stability.md) の走査 1・2・2b のダイジェストと完全一致した(不一致 0 件)。3 測定すべてと一致するため、素材が docs/07 の固定域そのものであることが値レベルで担保されている。
- **独立採取との一致**: 本採取のダンプ全体の SHA-256 は `32dc7255182d3da4bb45839a523e7ed1a74ebd8476bf0e297ab36889508cb577` で、[docs/17](17_otp_blackbox_probe.md) §4 が記録したダンプ(別の実施で採取・保存されたもの)のハッシュとバイト単位で一致した。独立した 2 回の採取が同一の素材を与えることの相互検証にもなっている。
- ダンプ自体は開発側の作業領域にのみ置く。本リポジトリには載せない。

## 3. 変換の再現性 — ホスト側で試せる範囲

候補鍵をホスト側 AES で試す前に、`.dat` の暗号変換がホスト側で再現可能かを既存記録から確定した。

- **モード**: SCRAMBLER の scramble_mode は 2 = AES_CBC_ENCRYPT / 6 = AES_CBC_DECRYPT / 5 = AES_ECB_DECRYPT([docs/02](02_dat_encryption_model.md) §12.1 の確定レイアウト)。保存は CBC 暗号化。
- **鍵の渡り方**: E2 のラウンドトリップ自己検証では、ホストが供給した任意の control word(先頭 16 バイト)で CBC 暗号化 → 別セッションで同値により CBC 復号すると 64,512/64,512 バイト × 2 行が完全一致した。すなわち器は、渡された 16 バイトをそのまま AES-128 鍵として使う標準 AES-CBC として振る舞う。本実験の「16 バイトを生の AES 鍵として試す」前提は、この実測の範囲では正しい。
- **IV**: パケットの IV_seed[16](+0xF0)が IV を与える。E2 のツールは IV_seed = 0 で実施した。本実験に先立ち、観測ラウンド(v3.71)の ioshim ログを再点検し、録画セッション 2 本の SCRAMBLER パケット先頭 400 件について IV_seed と ALU_num(+0x100)を確認したところ、**400 件全てで両フィールドともオールゼロ**だった。録画時の IV は 0 とみなせる(少なくとも先頭 400 パケットの範囲で実測)。
- **連鎖の単位**: 行(0xFC00 バイト)ごとに IV_seed で連鎖が初期化されるのか、セッション内で連鎖が継続するのかは、既存記録だけでは分離できない。ただしファイル先頭行については両解釈が一致する(セッション開始 = IV 0)ため、スクリーニングに先頭行を使う限りこの曖昧さは影響しない。再確認段(§6.2)では両解釈とも評価した。
- **ホスト側で再現できない・試していない要素**(範囲の限定として明記):
  - TS residue 系モード(20 / 21 / 26)による保存。これは E2 でも未実施([docs/02](02_dat_encryption_model.md) §12.4)。本実験の対象外。
  - 16 バイトを生の AES 鍵として使わない鍵スケジュール全般。特に、実効鍵がファームウェアのトークン解決(トークン + チップ内部状態)で決まるという現行モデル([docs/02](02_dat_encryption_model.md) §10.5)はこちら側に属し、本実験ではその解決規則自体は試せない。試したのは「解決結果がたまたま固定セル 2 件の連結に等しい」という特殊形のみである。
  - 復号の前後に掛かる未知のデータ変換(§7 で範囲を扱う)。

## 4. 候補空間

セル値の集合の性質が候補数を大きく圧縮する。固定域 130 件(0x00–0x81)の相異なる値は **45 種類しかない**: 85 件はオールゼロ(同一値)、nonzero 45 件も 44 種類の値しか持たない(1 種類の値が 2 件のセルに重複して現れる)。0xFF は nonzero で、[docs/17](17_otp_blackbox_probe.md) で INF2 チップ ID と同定された値である。

候補は「セルの index の組 × 各セルのバイト順(そのまま / 反転)」で記述し、鍵バイト列が重複するものは 1 回だけ試行した。

| 群 | 定義 | 記述数(バイト順 4 通り込み) |
|---|---|---|
| G1a | index 連続ペア (i, i+1) と逆順、i = 0x00–0x80、zero セルを含む全固定セル | 1,032 |
| G1b | 同一セルの 2 回連結、全固定セル 130 件 | 520 |
| G2 | nonzero 45 件の全順序ペア (i ≠ j) | 7,920 |
| G3 | 全固定セル 130 件の全順序ペア (i ≠ j) | 67,080 |
| GS | 0xFF を含む順序ペア(対 130 件 + (0xFF, 0xFF))。0xFF も値レベル固定のため補足として追加 | 1,044 |
| 合計 | | 77,596 |

重複を除いた**相異なる鍵は 8,281 件**。これを CBC(IV = 0)と ECB の 2 モードで試したので、鍵 × モードの試行数は 16,562 件。

範囲外として明記するもの: 3 セル以上の連結(AES-192 / 256)、セル内のワード単位の並べ替え等のバイト順バリエーション(セル単位の反転のみ実施)、揮発域(0x82–0xFE)の値(§1 の理由で対象外)。

## 5. 判定基準と検証系の自己試験

復号出力 0xFC00 バイト(192 バイト周期で 336 パケット)について、3 つの指標を全候補で計算した:

1. **s0(標準指標)**: 位相 0(オフセット 0, 192, 384, …)での 0x47 一致数。正解なら 336/336。E2 と同じ指標で、E2 の実測ノイズ上限は 5/336。
2. **allph(全位相の同期密度)**: 192 通りの全位相について 0x47 の一致数を取り、その最大値。保存位置の位相ずれや、同期位置がずれる形の変換があっても周期性が残れば検出できる。
3. **per(値非依存の周期性)**: 先頭 64 パケットについて、(位相, バイト値)の全組の中で最も頻度の高いものの割合。固定 XOR マスク型の変換(同期バイトが 0x47 以外の固定値に化ける)でも、周期性があれば 1.0 近くまで跳ねる。オーナーの留保(復号後の独自変換の可能性)を受けて追加した指標である。

**検証系の自己試験**: 本スイープに先立ち、合成平文(192 バイトごとに 0x47、残りは PRNG)を候補鍵 1 件で暗号化したものを復号評価し、(a) CBC(IV = 0)で s0 = 336、(b) ECB で s0 = 336、(c) CBC で IV を誤ると s0 = 335(壊れるのは先頭ブロック内の同期位置 1 件のみ)となることを確認した。(c)は「IV が未知でも CBC では先頭 16 バイトしか壊れない」という性質と、指標がそれを正しく数えることの確認である。

**帰無モデル**: 誤った鍵の復号出力では s0 は二項分布 Bin(336, 1/256)(平均 1.31)に従う。試行数 16,562 件に対する期待値は、s0 ≥ 6 が約 38.7 件、s0 ≥ 7 が約 7.1 件、s0 ≥ 8 が約 1.1 件。allph ≥ 11 の期待値は約 0.5 件、per ≥ 8/64 の期待値は約 0.25 件(いずれもポアソン近似)。

## 6. 結果

### 6.1 スクリーニング(x3_000 先頭行、全候補)

| 指標 | 最大値 | 内訳 |
|---|---|---|
| s0(CBC) | 7/336 | ≥6 が 21 件(6 が 19 件、7 が 2 件)、≥8 は 0 件 |
| s0(ECB) | 7/336 | ≥6 が 22 件(6 が 20 件、7 が 2 件)、≥8 は 0 件 |
| allph(CBC) | 11/336 | ≥11 は 1 件 |
| allph(ECB) | 10/336 | ≥11 は 0 件 |
| per(CBC) | 0.109(7/64) | ≥8/64 は 0 件 |
| per(ECB) | 0.125(8/64) | ≥8/64 は 1 件 |

合計で s0 ≥ 6 の候補は 43 件で、帰無期待値 38.7 件と整合する。s0 ≥ 7 は観測 4 件(期待 7.1)、s0 ≥ 8 は観測 0 件(期待 1.1)。allph・per の最大値も帰無期待のばらつきの範囲内にある。**正解の鍵が含まれていれば 336/336(ないし IV 由来で 335)が出るはずであり、その水準の候補は 1 件も無い。**

### 6.2 再確認(43 件 × 別サンプル・別位置・両連鎖解釈)

スクリーニングで s0 ≥ 6 となった 43 件全てについて、次を評価した: x3_000 / dr_000 / dr_001 / mob1_000 の各先頭 4 MiB と x3_000 の末尾 4 MiB(各 65 行)について、行単位 CBC(行ごとに IV = 0 で初期化)、連続 CBC(全体を 1 つの連鎖として復号)、ECB の 3 形態で行ごとの s0 を取り、さらに x3_000 中央断片について CBC 断片復号(先頭ブロックを捨てる)と ECB の全位相指標を取った。

- **全 43 件 × 全データセット × 全形態を通じた行 s0 の最大値は 8/336**。どの候補も、どのタイトル・位置でも構造を示さなかった。

### 6.3 判定

ヒット無し。観測された最大値の分布は帰無モデルと整合し、「高い値が出た候補が再確認で伸びる」という正解らしい振る舞いは一切無い。

## 7. 棄却できる範囲・できない範囲

本実験で**実測により棄却できる**のは、次の組み合わせである:

- 実効鍵が固定セル 2 件の連結(§4 のバイト順バリエーションの範囲)であり、**かつ**保存変換が AES-CBC(IV_seed = 0、行単位・連続の両連鎖)または AES-ECB であり、**かつ**復号で得られる平文が生 TS である場合。
- さらに周期性指標(allph / per)が全候補でノイズ水準だったことから、**復号後に 192 バイト周期性を保つ変換(固定 XOR マスク、位相ずれ、同期バイトの固定値への置換など)を経た TS** の場合まで棄却が及ぶ。

本実験では**棄却できない**もの:

- 復号後に周期性を壊す変換(ブロック単位の攪拌、圧縮的な変換等)が掛かる場合の、連結鍵そのもの。この可能性は実施前にオーナーが留保として明示したもので、本実験の指標は原理的に届かない。
- TS residue モード(20 / 21 / 26)で保存されている場合(ホスト側 AES の対象外。チップセッションでの試行が必要で、E2 でも未実施)。
- 16 バイトを生の鍵として使わない鍵スケジュール・鍵解決(ファームウェア側解決モデル [docs/02](02_dat_encryption_model.md) §10.5 を含む)。本実験は「解決結果が連結と一致する特殊形」だけを潰した。
- 3 セル以上連結の AES-192 / 256(候補空間の定義外。計算量としては拡張可能)。

したがって本結果は副線全体を閉じるものではない。閉じたのは「固定セルの単純連結 + 素直な保存形式」という最も単純な形であり、副線の残りは §8 のとおりである。

## 8. 残件

- AES-192 / 256(3–4 セル連結)への拡張: 候補数は増えるが(3 セル順序ペア相当で最大でも 130³ ≈ 220 万件規模)、ホスト側計算で到達可能な範囲。本実験の検証系がそのまま使える。
- TS residue モードの試行はチップセッション側の実験(E2 の未実施分、[docs/02](02_dat_encryption_model.md) §12.4)と束ねて扱うのが筋である。
- 周期性を壊す変換層の有無は、平文が得られる経路(オラクル本線)で平文 TS と暗号文を対にして初めて判定できる。本実験の棄却範囲の外側は本線側の成果に依存する。
