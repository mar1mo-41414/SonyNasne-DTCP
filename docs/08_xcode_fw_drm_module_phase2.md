# 08 XCode ファームウェア DRM モジュール解析 第2段 — 逆アセンブル環境の整備と参照追跡の開始

## 要約

[docs/05](05_xcode_firmware_images.md)(第1段)で確定した平文の主ファームウェアイメージ(ARC 系、ロードベース 0)を対象に、逆アセンブル環境を整備し、エントリポイントと表構造を実測し、DRM 文字列への参照追跡を開始した回の記録。

到達点:

- 逆アセンブル環境は **capstone 6.0.0 + 自作 Python スクリプト**に確定した。Ghidra 12.1.3 には ARC のプロセッサ定義が無く、Ubuntu の binutils-arc-linux-gnu は既知の ARC コードを一切デコードできないことを対照イメージで実証した(§2)。
- ベクタ表は j limm 形式のエントリが **6 個だけ**(0x00〜0x28)であることを実測した。[docs/05](05_xcode_firmware_images.md) §3 の例示値(0x28 のエントリ → 0x2D00C4)は誤りで、実測は **0x2D0144**(§3.1、docs/05 側も訂正済み)。
- docs/05 §4 で「名前表」「ディスパッチ表」とみた構造の実態を更新した。名前側は XML 署名断片やログ書式が混在する**文字列プール**、ディスパッチ側(0x2ED578〜)は **(ID 0x1101〜0x1106, 同一ポインタ 0x3DCD7C) の 6 レコード**で、ポインタはゼロ初期化領域(ランタイムオブジェクト)を指す。静的なハンドラ表ではなかった(§3.3、§3.4)。
- **DRM 文字列への参照は、イメージ内コードから通常の形式では存在しない**ことを範囲明記のうえで実測した: 対象文字列アドレスは 32 ビット値として(通常リトルエンディアン/半語スワップの両形式、全バイトアライメント)イメージ全域のどこにも現れない。オフセット表の仮説も、候補ベース 6 件では密な表が見つからなかった(§4)。文字列群は「イメージ内コードが参照する rodata」ではなく、マニフェスト/名前プールとして振る舞う。
- したがって本丸である「録画時トークン(CW)がチップ内部状態とどう結び付くか」と、焦点である「FW(ARC)コード自体がトークンに変換を行うか(a)、素通しでチップ内解決か(b)」は、**FW 側ハンドラ自体が未同定のため本段では未判定**。追跡戦略は文字列 xref から、ホスト側コマンド(SCRAMBLER 0x108 / READ_FROM_OTP 0x116 / OPEN_SECUREDTS 0x30)に対応する FW 側ディスパッチ機械の同定へ移す(§5、§6)。

未確定の区切り: セッション確立のコードパス実読、(a)/(b) の境界、READ_FROM_OTP の index 境界(0x82 付近、[docs/07](07_otp_value_level_stability.md) の実測に対応する FW 側の扱い)は、いずれも次段以降。

## 1. 対象と方法

- 対象: 第1段で製品と同一内容と証明された平文の主 FW イメージ(6,216,324 バイト)。アドレスはファイルオフセット = ロードアドレス(ベース 0)。
- 実機には触れていない。手元の解析環境上のファイル解析のみ。
- 方法: 表構造はバイト列の直接解読(デコーダ非依存)、コードの読みは capstone による種エントリからの再帰辿りを基本とし、デコードの正しさが検証できた範囲でのみ主張する(理由は §2.4)。

## 2. 逆アセンブル環境の整備と選定

### 2.1 候補と検証結果

| 候補 | 結果 |
|---|---|
| Ghidra 12.1.3 | Processors 一覧に ARC が無い。主 FW をプロジェクト化できない |
| Ghidra 向けコミュニティ SLEIGH(学会発表で自作されたもの) | 存在は確認したが、出所未検証のプロセッサ定義を丸ごと導入すると解析結果の監査可能性が担保できないため、本段では導入しない。自作を含め将来の選択肢として残す |
| Ubuntu binutils-multiarch の objdump | ARC の BFD ターゲット自体が無い |
| Ubuntu binutils-arc-linux-gnu 2.42 | 使用不可と判定(証拠は §2.2) |
| radare2 5.5.0 | ARC 用プラグインが無い |
| **capstone 6.0.0** | **採用**(検証は §2.3、限界は §2.4) |

### 2.2 binutils-arc-linux-gnu を使用不可とした証拠

- 主 FW を raw binary として、また ELF 化して、さらに CPU 種別(arc700 等)を明示しても、全ワードが .word として出力されるだけで命令としてデコードされない。
- 対照として、本物の ARC 向け Linux イメージ(ブート FW 側のカーネルメモリイメージ)でも同じく一切デコードされなかった。「主 FW 側の形式の問題」ではなく、このビルドの ARC デコーダが機能していないと判断した。

### 2.3 capstone の検証(正しく読めることの確認)

- ベクタ表が j 命令の連続としてデコードでき、跳躍先が docs/05 の既知値と一致した(例: エントリ 0 → 0x113C20)。
- 0x8000 のサンク表で、レジスタ退避 → 呼び出し → 復帰の一連が首尾一貫して読めた。
- 別の ARC イメージでも、カーネル空間アドレスへの跳躍として一貫した読みが得られた。

### 2.4 capstone ARC の限界(本段の読みの前提)

- 実装が ARCv2 寄りで、一部のデコードが疑わしい(サンク表内で不自然な即値演算、あり得ない分岐先など)。
- 線形スイープは同期ずれする。任意オフセットから読むと数命令で崩壊する箇所がある(例: ベクタ [3] の先 0x100030 はデータ様の並びに読め、コードとして意味を取れない)。
- このため本段のコードに関する主張は「表の直接解読」と「デコードが検証できた範囲」に限定し、到達できなかった範囲は到達できなかったと書く。
- スキップデータモードは連続性こそ改善するが、誤デコードの混入も増えるため、意味の主張の根拠には使っていない。

## 3. エントリポイントと表構造の実測

### 3.1 ベクタ表(訂正を含む)

- ファイル先頭のベクタ表は j limm(8 バイト)エントリが **6 個だけ**続く(スロット 0x00〜0x28)。0x30 でパターンは崩れる。
- 跳躍先: [0]=0x113C20、[1]=0x113C00、[2]=0x113D5C、[3]=0x100030、[4]=0x1002B8、[5]=0x2D0144。
- limm の格納規約: ファイル上のリトルエンディアン u32 W に対し、値 = ((W & 0xFFFF) << 16) | (W >> 16)(半語スワップ)。
- **訂正**: docs/05 §3 の「0x28 のエントリ → 0x2D00C4」は、0x2C 付近のバイト列の半語読みに由来する誤り。実測は 0x2D0144。
- [5] の先 0x2D0144 は、そのオフセットからコードとしてデコードできなかった(データ様の反復が混在)。エントリの意味は未解決。

### 3.2 サンク/ラッパ表(0x8000)

- 0x8000 には 0x50 バイト刻みの小さなラッパが並ぶ。各ラッパは戻りアドレスレジスタを退避し、jl で 0x1922C0 付近の実体を呼び、復帰する形。
- この表の呼び出し先は、実関数への種として利用できた数少ない確実な入口である。

### 3.3 「名前表」の実態 — 文字列プール

- 0x2ED300〜 の領域は、綺麗なシンボル表ではなく**文字列プール**だった。XML 署名の断片、ログ書式、モジュールタグ様の短文字列と、gen_kauth(0x2ED438)、setexchgkey(0x2ED444) などの**操作名/ラベル文字列**が混在する。
- ID と名前の対応表としては使えない。名前は「エクスポート/連携用の名前プール」の様相である(解釈)。

### 3.4 ディスパッチ表候補の実態 — 共有ランタイムオブジェクトへの対応表

- 実体は 0x2ED578〜0x2ED5A7 の **8 バイトレコード ×6**: (ID, ポインタ) で、ID は **0x1101〜0x1106**、ポインタは**全て同一の 0x3DCD7C**。
- docs/05 §4.2 の ID 読み「0x00110001〜」はレコードのずらし方の差であり、上記が実測である。
- 0x3DCD7C はファイル範囲外のゼロ初期化領域にある。すなわち静的なハンドラ/ディスクリプタではなく、**実行時に作られる共有文脈オブジェクト**であり、コマンド群 0x11xx はその文脈に対応付けられている。ハンドラ関数のアドレスはこの表からは得られない。

### 3.5 0x2ED500 のレジストリ様テーブル

- 0x2ED500〜0x2ED548 に 16 バイトレコード {フラグ, コードポインタ, コードポインタ, 0} の列がある。フラグは 0x01000000 / 0x00010000 / 0x00020000 / 0x00000200 の 4 種。コードポインタ: 0x156830、0x156AD0、0x26EE7C、0x26EE04、0x228C90、0x166B7C、0x2653F0、0x16BBE8。
- ハンドラ/機能レジストリの候補だが、各レコードの意味(どの機能か)は未確定。0x156830 は関数途中から首尾一貫して読め、ベースレジスタ + オフセットの構造体アクセスが支配的だった(オブジェクト指向的な実装の様相)。

### 3.6 0x2ED458 の初期化/登録リスト様テーブル

- 8 バイトペア ×16 レコード。片側はゼロ初期化領域系のアドレス、もう片側は 0x3D2EF8 から +0xC 刻みで増えるデータアドレス。0x2ED4D8 のゼロペアで終端する。初期化/登録リストの様相で、意味は未確定。

### 3.7 関数規模の見積もりの試行と限界

- 標準プロローグの 1 形式のバイト列はコード領域に 9 件しか無く、関数の生成形が多様なため、この方法では関数総数を推定できない(この形式を使う関数の下限でしかない)。
- ポインタ様の値の連続を走査すると、値が所在オフセット + 約 0x100000 に分布する表が複数見つかった。第二のマッピング(別ビュー/別イメージ向け)の可能性を含め、解釈は未確定。
- 種エントリからの再帰辿りによる到達範囲の測定も 3 方式で試行したが、いずれも本段の主張に使える形では完了しなかった: 詳細デコード版は制限時間内に完了せず、高速版は共有コード領域での早期終了により到達関数 34 件に留まり、スキップデータ版は誤デコード由来の分岐先が増殖して収束しなかった。したがって「到達可能なコードの統計」のような形の列挙は本段では主張しない。列挙として確実なのは §3.1〜§3.6 の表構造であり、関数規模の網羅的な列挙は逆アセンブラの強化(§6)が前提になる。

## 4. DRM 参照追跡 — 文字列参照の陰性所見

### 4.1 実測(範囲を明記する)

対象: drmctrl_open_secured_strm の書式文字列(0x2E2F54)、キースロット書式文字列(0x2E6BDC、0x2E6C04、0x2E6C34)、gen_kauth(0x2ED438)、setexchgkey(0x2ED444)、DRM 文字列ブロック先頭(0x2D3070)。

- 上記アドレスの 32 ビット表現を、**通常のリトルエンディアン形式と半語スワップ形式の両方**で、**イメージ全域・全バイトアライメント**で raw 検索した。出現は **0 件**。
- 一方、データ表の中には絶対ポインタが実在する(例: 0x3D2EF8、0x15D00C が表の要素として現れる)。「イメージにポインタが一切無い」のではなく、**文字列のアドレスだけが値として物質化していない**。
- 補助仮説(オフセット表): DRM 文字列ブロック内 1441 件の文字列について、ベース候補 6 件(0x2D3070、0x2D0000、0x2E0000、0x2C0000、0x200000、0x2D3000)からのオフセット値が表として並ぶ箇所を走査した。密な表は見つからなかった。オフセット値自体は小さい整数で全域に散在するため、この補助仮説の検証力は限定的であることも併記する。

### 4.2 解釈(推測であることを明記する)

- 文字列群(ログ書式・操作名・XML 署名断片を含む大きなブロック)は、このイメージ内のコードから通常の参照を受ける rodata としては振る舞っていない。マニフェスト/文字列ファイルとモジュール連携用の名前プールをイメージに埋め込んだ形、という解釈が現在の実測と最も整合する。
- 含意: gen_kauth / setexchgkey / SECUREDTS セッション確立の**実行コードは、このイメージ内では文字列 xref からは到達できない**。実体が「実行時に供給されるロード可能モジュール」側にある可能性も含め、追跡の入口を §6 の通り組み替える。

## 5. 焦点への回答状況 — トークン変換の境界と OTP 境界

- **(a)/(b) の境界**: 未判定。理由: FW 側でホストコマンドを受けるハンドラ(SCRAMBLER 0x108 等)を同定できておらず、トークンが通過する ARC コードを読めていない。§4 の陰性所見は「文字列で同定できる範囲の DRM コードがこのイメージに無い」ことを示すが、変換処理そのものの有無については証拠にならない(変換コードが別モジュール/別経路にある可能性を排除できない)。断定はしない。
- **OTP の index 境界(0x82 付近)**: docs/07 のホスト側実測(0x00–0x81 と 0xFF は値レベルで固定、0x82–0xFE は読み出しごとに変動)に対応する FW 側の境界処理も、READ_FROM_OTP(0x116)ハンドラ未同定のため未読。ハンドラ同定時に合わせて読む項目として §6 に置く。

## 6. 残件と次の打ち手

1. **H2M コマンドディスパッチ機械の同定**: ホスト → ドライバ → FW のパケット(先頭にコマンド番号を持つ)を受ける FW 側の入口を探す。共有文脈オブジェクト 0x3DCD7C の利用元、0x2ED500 レジストリの実読が手掛かり。
2. **0x2ED500 レジストリのコードポインタ群の実読**: capstone の読める範囲で各関数の役割を付け、コマンド処理系に接続する。
3. **ロード可能モジュールの所在確認**: DRM の実行コードが主 FW 以外(他の FW イメージ、SoC 側カーネルイメージ、実行時にホストから供給されるモジュール)にある可能性を切り分ける。
4. **逆アセンブラの強化**: Ghidra 向け ARC SLEIGH の自作、または出所を監査できた定義の導入。現行 capstone の限界(§2.4)が実読の天井になっている。
5. ハンドラ同定後: (a)/(b) の境界(トークンへのバイト演算の有無)と、READ_FROM_OTP の index 境界処理(0x82)を読む。
