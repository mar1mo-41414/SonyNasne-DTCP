# 14. XCode ファームウェア DRM モジュール解析 第6段: 名前記述子機構の同定、AKE 実体と SECUREDTS 経路の実読

対象: 主 FW 平文イメージ(ファイルオフセット表記、[docs/05](05_xcode_firmware_images.md) の SHA-256 `3e99b413…` と同一物)。本書のアドレスは原則ファイルオフセットで書く。

## 0. 要約

- 第5段([docs/13](13_xcode_fw_drm_phase5.md))の「名前記述子」方式を追跡した結果、この機構は**操作名 → 関数ポインタの対応表ではなかった**。実体は「名前付きリソース(バッファ/メモリプール)の管理フレームワーク」で、対応表は RAM `0x67F0B8` の 64 エントリ × 0x20 バイトの実行時登録テーブルであり、**エントリに実体関数へのポインタは存在しない**(フィールドは種別コード・所有者ポインタ・範囲情報・名前)。したがって SCRAMBLER 等の操作実体はこの経路では原理的に辿れない。
- ファイル `0x2D34E0` の {コードポインタ, 0} × 16 表は、名前機構とは無関係と切り分けた(レイアウト・登録経路・参照有無の全てが異なる)。併せて第5段記録の 2 点を訂正した(2 語目が非 0 のエントリの存在、後述 §4)。
- AKE 実体(gen_kauth / setexchgkey)は名前機構を経由しない独立関数で、第5段で「ラッパ」としたファイル `0x6772C` / `0x683B8` が実体そのものだった。**setexchgkey では交換鍵 12 バイトがセッション文脈内の 2 つの 12 バイト列の XOR で導出される**ことをコード実読で確定した(FW コードによるバイト単位の鍵導出の実例。ただし対象は AKE の交換鍵であり、録画トークンの解決経路へは外挿しない)。
- SECUREDTS 経路を実読した。ストリーム open 本体(ファイル `0x24A7E4`)がモード(復号 = 3 / 暗号 = 4 / その他 = 9)で分岐し、復号・暗号ではファイル `0x161B7C`(drmctrl_open_secured_strm 実体)が **6 個の鍵オブジェクトスロット**から鍵オブジェクトを選んでストリーム文脈へ束縛する。要求側の鍵フィールドが 0 の場合は種別一致する未使用スロットを自動選択し、0 でなければ鍵オブジェクトへの直接参照として扱われる。
- SCRAMBLER 実体と `control_words[24]` の処理には到達できず、(a)/(b) 境界・READ_FROM_OTP の index 境界は**未判定のまま**(理由は §7)。

## 1. 方法と第5段記録の訂正(ヘルパの大きさ)

- 解析は ghp5 のコピープロジェクト ghp6(ベース `0x100000` マッピング)で行い、DumpRange5 による線形ダンプで実読した。作業ログは作業領域 `2026-11-13-fw-drm/phase6/`。
- **訂正**: 第5段で名前引きヘルパ(ファイル `0xA19A4` / `0xA0744`)を「両方とも小さく、デコンパイル失敗」と記録したのは誤りだった。実体はいずれも大きな関数である。原因は、両ヘルパが呼ぶファイル `0x2B8A64` の関数が Ghidra 上 no-return とマークされ、呼び出し側のボディ同定が途中で切れていたこと。生バイトで確認した `0x2B8A64` は 4 命令のリーフで、`lr r0,[0x4]; lsr r0,r0,0x8; extb r0,r0; j blink` ― つまり ((aux レジスタ 0x4 >> 8) & 0xFF) を返す現文脈(プロセッサ)ID 取得関数であり、正常に戻る。
- 文脈チェック関数(ファイル `0x2B4DBC`)も実読した。aux レジスタ 0xA の値のビット 1–2 が両方立つ場合に 1 を返す「特権文脈か」の判定で、ラッパと両ヘルパの共通入口条件である(戻り値が 0 の経路では、ヘルパは例外記録領域 `0x100530` 周辺へマーカー `0x0B57AC1E` と pcl を書いて通信領域の共有ワードを待つループへ入る)。

## 2. 名前記述子と 2 つのヘルパ(確定)

### 2.1 記述子のレイアウト(ScamScramble ラッパの構築コードから)

ファイル `0x1F483C` のラッパがスタック上に構築する記述子は 0x28 バイト:

| オフセット | 内容 |
|---|---|
| +0x00 | 操作名の先頭 4 バイト(文字列から読み出し) |
| +0x04 | 引数ポインタ(ラッパの引数 2 に 0x20 を加えた値) |
| +0x08 | 0 で初期化され、ヘルパ A が登録エントリの種別コードを書き戻す |
| +0x0C | 1(固定) |
| +0x10..0x23 | 操作名の残り 20 バイト(文字列 +4 から memcpy、ヘルパはファイル `0x8D690`) |
| +0x24 | 所有者ポインタ(ラッパの引数 1) |

ラッパはヘルパ A 呼び出しの前にキャッシュフラッシュ(ファイル `0x6D478`)を引数 1・2 に対して呼ぶ。もう 1 本のラッパ(ファイル `0x188A50`)は同じ形の記述子をヘルパ B へ渡し、戻り値 0 の後にキャッシュフラッシュする。両ラッパの呼び出し元はストリーム状態機械(ファイル `0x19E550` 付近の同一関数内)。

※ 記述子の詰め方は呼び出し元で一様ではない。ファイル `0x24A7E4` はヘルパ B に対して {+0x00 = ストリーム文脈ポインタ, +0x04 = サイズ 0x1000, +0x08 = 0, +0x0C = 1, +0x10 = 名前全体("DATA_PASSTHRU_BUF")、+0x24 = 結果スロット} という詰め方をする。+0x00 / +0x24 の意味は API の用途で重ねられている、が現時点の解釈であり、確定したのは各フィールドの読み書き実態(§2.2・§2.3)のみ。

### 2.2 ヘルパ A(ファイル `0xA19A4`): 検索・利用

1. 特権文脈チェック(ファイル `0x2B4DBC`)と文脈別診断記録の後、共有 RAM(通信領域 `0xAFE7FC + 0x308`)が空くまで待つ。
2. **検索ループ**: テーブル `0x67F0B8` を最大 64 件線形走査し、`entry+0x04 == desc+0x24`(所有者)かつ `entry+0x10 == desc+0x00`(名前先頭 4 バイト)で一致とする。**名前の残り(+0x10 以降)は照合しない**。
3. 全呼び出しを記録リングへ残す: リングは `0x67F908` の 32 件 × 0x30 バイトで、単調増加カウンタ `0x680B08` の下位 5 ビットで回す。記録内容は記述子の写し(名前先頭 4 バイトと +0x10.. の 3 ワード、所有者、引数側フィールド)、文脈 ID、一致したエントリ番号(不一致は 0x40)、通信領域由来の値など。
4. 不一致時: カウンタ `0x67F900` を増やしフラグ `0x67F904` = 1 を立て、通知(ファイル `0x2B81D0`)の後 1 を返す。
5. 一致時: `entry+0x00`(種別コード)を desc+0x08 へ書き戻し、desc+0x04 を 0x20 境界へ切り上げて書き戻した上で、種別ごとに別のアリーナの会計処理を行う。種別 0x7FFFFFF はアリーナ `0x67DC78`、種別 0 は `0x67CC78`、種別 1 は `0x67D078`、種別 2 は `0x67D478` を対象とし、各アリーナは 0x10 バイト × 64 件のブロック表([ブロック+0x08] == -1 が空き)を持ち、隣接ブロックとの結合判定([entry+0x08]+1 と [block+0x04] の比較等)を含む確保処理と、メモリ記述子 `0x67E078` の種別別累算フィールド(+0x10/+0x14/+0x34 等)の更新を行う。

### 2.3 ヘルパ B(ファイル `0xA0744`): 確保・登録

1. 入口で desc+0x24 を 0 クリアする(結果スロット。呼び出し元ファイル `0x24A7E4` は戻り後に desc+0x24 を確保結果として読み、0 なら失敗として扱う)。
2. メモリ記述子 `0x67E078 + 0x30` の件数と desc+0x08 を照合し、名前(desc+0x10)を記録関数(ファイル `0x1CFD24`、書式文字列はファイル `0x2DE52C`)へ出す。
3. テーブル `0x67F0B8` の登録数を数える(`entry+0x10 == -1` が終端)。64 件満杯ならエラーカウンタ `0x67F8C0` を増やしコード 0xB を `0x67F8C4` へ記録して 1 を返す。
4. desc+0x04 を 0x20 境界へ切り上げ、desc+0x08 の種別(0x7FFFFFF / 0 / 1 / 2 / 3)ごとにメモリ記述子のアリーナ残量フィールド(+0x34 / +0x10 / +0x14 / +0x18 / +0x1C)と照合する(この先の登録書き込み部は未読了。§8 の残件)。

## 3. 対応表の実体(確定)

- 登録テーブルは RAM `0x67F0B8`、64 エントリ × 0x20 バイト、イメージ内には実体を持たず実行時に登録される。エントリのレイアウトは {+0x00 種別コード、+0x04 所有者ポインタ、+0x08・+0x0C 範囲関連、+0x10 名前先頭 4 バイト(空きエントリは -1)、+0x14 名前の残り 12 バイト}。
- 裏付けとして、診断ダンプ関数(ファイル `0x124EF8` 付近、引数の文字で分岐)が本表を 'L' で、領域表 `0x67E0B8` を 'H' / 'h' / 'l' で走査・印字し、両表ともエントリ +0x14 から 12 バイトを名前として印字する作りだった。
- 領域表 `0x67E0B8`(最大 0x80 件 × 0x20 バイト)への登録関数(ファイル `0xA2684`)も実読した。登録内容は {+0x00 = 引数 +0x00、+0x04 = 引数 +0x04、+0x08 = 引数 +0x24(開始アドレス)、+0x0C = 開始 + 引数 +0x04 - 1(終端)、+0x10 = (種別 << 16) | 0xE0000000 にビット 1 を立てたフラ그、+0x14 = 引数 +0x10 からの名前 12 バイト}。
- フレームワーク初期化(ファイル `0xA2740` 付近)は、両表と 6 つのアリーナ(0x67CC78 / 0x67D078 / 0x67D478 / 0x67D878 / 0x67DC78 / 0x67F8B8)のベースアドレスを通信領域のポインタブロック(`0xAFF7F4 + 0x3D4` 〜、実アドレス 0xAFFBC8 周辺)へ公開し、報告 API(ファイル `0x2B7E20`)へ番号 0x11A–0x125 で登録し、各アリーナのブロック表 0x400 バイトを 0xFF で初期化する。
- **結論**: この機構は「名前で引く対象」がメモリ領域・アリーナ種別であってコードではない。ScamScramble のラッパ 2 本が行っているのは、スクランブル操作そのものではなく当該操作が使う名前付きリソースの検索(ヘルパ A)/確保(ヘルパ B)である、というのが現時点の解釈(呼び出し元がストリーム状態機械であること、記述子に引数ポインタとサイズ的な値が載ることからの推定を含む)。

## 4. ファイル `0x2D34E0` の表は名前機構と無関係(切り分け)

- 生バイトを再読した。16 エントリの {ベース 0 形式のコードポインタ、2 語目} で、ポインタ列は第5段の記録どおりファイル `0x156F90`〜`0x157C2C`(バッファ/ストリーム操作系、入口 `0x156F24`)を指す。**訂正**: 2 語目は原則 0 だが、[15] だけ `0xDDF8A00B` で非 0 だった(第5段の「{ポインタ, 0} × 16」はこの点で不正確)。
- 名前文字列(ScamScramble / gen_kauth / setexchgkey / AESCMAC)は、生バイト走査(リトルエンディアン・ハーフワードスワップ両形式)で文字列プール内にのみ存在し、イメージ内のどこにも複製がない。したがって「名前文字列を埋め込んだ静的な名前 → 関数対応表」は存在しない。
- 本表への参照は第5段の探索範囲(両プログラムの全デコード命令 + スカラ検索)で 0 件のままであり、§3 の実テーブルとは所在(RAM ではなくイメージ内)・レイアウト・登録経路の全てが異なる。名前機構との関係はないと切り分ける。

## 5. AKE 実体: gen_kauth / setexchgkey(確定)

両関数とも名前記述子機構を使わない。名前文字列は関数内部のイベント記録(ファイル `0x26A698`、引数は名前・コード 0x38C / 0x541・値)へ渡すログ名としてのみ現れる。

共通構造: 対象は引数から辿る大きなセッション文脈オブジェクト([param+0x48] の先、フィールド +0x10C20〜+0x115D4 を使用)。状態フラグは [param+0x368] で、0x10 = kauth 生成済み、0x20 = 交換鍵設定済み、0x40000 = 変種分岐。呼び出し回数カウンタ(ファイル `0x3EB7A8` / `0x3EB7C8` 相当の RAM 変数)が入口で増える。

### 5.1 gen_kauth(ファイル `0x6772C`)

- 文脈内フィールド群(+0x10C74 / +0x10C88 / +0x110E0 / +0x11310 / +0x112FC)を入力に中核計算(ファイル `0x1FED1C`)を呼び、生成値 12 バイトを文脈 +0x10C9C〜+0x10CA8 へ格納する。
- フラグ 0x40000 の変種では、生成値 12 バイトを 2 つ並べた 0x18 バイトをファイル `0xEFC2C` で処理し、第 2 の 12 バイトを +0x10CA8〜+0x10CB4 へ格納する。
- 文脈 +0x10C30 からファイル `0x66C24` 経由で 4 バイトおよび 2 バイトの値を取り出し、宛先フィールド群(+0x1149C / +0x114C8 / +0x114CC、変種では +0x115C8 / +0x115D4)へ配置する。文脈 +0x115C4 が 1 の場合は関連オブジェクト(+0x115C0)へ写す経路と、イベント記録へ "gen_kauth" 名で出す経路がある。
- 終端でフラグ 0x10 と 0x20 のうち 0x10 側を立て(※ [param+0x368] |= 0x10 は生成直後、|= 0x20 は [param+0x30] == 0 の経路の終端)、状態フィールド +0x114D4 へ 0xC を書く。

### 5.2 setexchgkey(ファイル `0x683B8`)

- 引数コードが 0x1D でなければエラー 6、フラグ 0x10 が立っていなければエラー 7 を結果スロットへ返す(順序として gen_kauth の後でなければ成立しない)。
- 相手方素材 12 バイトを引数(param_3 + 4)から文脈 +0x10CB4 へコピーする。
- **交換鍵の導出(確定)**: 12 バイトについて `文脈[+0x1149C + i] = 文脈[+0x10C9C + i] XOR 文脈[+0x10CB4 + i]` を計算する。すなわち gen_kauth の生成値と相手方素材の XOR が交換鍵である。変種(フラグ 0x40000)では素材のコピー先が +0x10CC0、宛先が +0x115C8 になり、XOR の第 2 項もそちら(+0x10CC0 側の並び)を使う。また引数のバイト(param_3 + 7 の指す先)を ID として +0x114C8(変種では +0x115D4)へ格納し、+0x115D4 は 0xFF でマスクされる。
- 終端でフラグ 0x20 を立て、結果スロットへ 0 を返す。

### 5.3 鍵素材の出所について(範囲明記)

- この 2 関数の範囲では、入力は全てセッション文脈内の既存フィールドと引数であり、**OTP 読み出しや鍵ストアへの直接参照は見当たらなかった**。素材の起源 ― 文脈フィールド +0x10C30 や +0x10C74 群を誰が初期化するか、中核計算ファイル `0x1FED1C` の内部 ― は未追跡であり、「OTP 由来でない」とは判定しない(§8 の残件)。

## 6. SECUREDTS 経路: open_secured_strm(確定)

### 6.1 ストリーム open 本体(ファイル `0x24A7E4`)

**訂正**: 第5段でこの関数が参照する文字列(ファイル `0x2E2F54`)を操作名 `drmctrl_open_secured_strm` とみたが、実文字列はログ書式 **"drmctrl_open_secured_strm ret = %x"** である。また関数自体のログ文字列は "strm_open host data passthru" 系で、本関数はストリーム open の汎用本体である。

処理の流れ:

1. 0x1E18C バイトのストリーム文脈を確保(確保元プールは RAM 変数経由)し、変換後要求(param_1)から多数のフィールドをコピーする。データパススルー用のバッファは名前記述子("DATA_PASSTHRU_BUF"、§2.1 の注記)でヘルパ B から確保する。
2. 暗号モードで分岐する。モードは変換後要求の +0x888(暗号モード)と +0x88C(復号モード)で、値はストリーム文脈 +0x8174 / +0x8178 へも保存される。
   - 復号 = 3 または暗号 = 4: まず準備関数(ファイル `0x6BDFC`)へ要求 +0xD40 と鍵ペア(有効な側のみ、無効な側は -1)を渡し、次に §6.2 のファイル `0x161B7C` で鍵束縛する。モードの組合せが不正(片方だけ 3/4 でもう一方が 0 でも 3/4 でもない等)ならエラー 0x104。
   - 復号・暗号とも 9: ファイル `0x128A4C`(詳細未読)へ委ね、要求 +0xD29 のバイトを束縛済みオブジェクトの +0x380 へ書く。
   - 復号数(param +0xD68)が 0x40 を超えると例外記録を書いて停止する経路がある。
3. 鍵束縛の後処理(モード 3/4 の場合): バッファ量を要求 +0xD68 / +0xD28 / +0xD30 / +0xD34 から決めてファイル `0x926CC` で確保し、復号オブジェクト([ctx+0x81D0])にはファイル `0x6BC24` と `0x6C1D4`(対象はオブジェクト +0x148、引数は要求 +0xD44 / +0xD48)、暗号オブジェクト([ctx+0x81D4])には `0x6C1D4` を適用し、最後にファイル `0x6C040` で両オブジェクトと要求 +0xD40 を結ぶ。

### 6.2 鍵束縛(ファイル `0x161B7C`、drmctrl_open_secured_strm 実体)

- 引数は (ストリーム文脈、補助構造体、復号鍵ペア param_3/param_4、暗号鍵ペア param_5/param_6)。各ペアの第 1 要素の解釈は: **-1 = なし、0 = 自動選択、それ以外 = 鍵オブジェクトへの直接参照**。
- 自動選択: RAM の 6 スロット表(ベース `0x69735C`、ストライド 0x10、{+0x00 使用フラグ、+0x04 オブジェクト} 形式)を線形走査し、復号は [obj+0x178] == 0、暗号は [obj+0x178] == 1 の未使用オブジェクトを選ぶ。空きがなければエラー(内部状態コード 0x100 / 0x200 系)。
- 選択されたオブジェクトはストリーム文脈 +0x81D0(復号)/ +0x81D4(暗号)へ束縛される。束縛前に [obj+0x174] の使用中検査を行い、束縛後はストリーム種別([ctx+0x818C] = 8 / 0x10 / 0x20)とオブジェクト能力([obj+0x148+0x10] のビット 0x20 / 0x40 / 0x80、[obj+0x148+0x0C] の必須ビット 1|2|4)の照合を行う。
- 有効化はファイル `0x5490C`(対象オブジェクト +0x148、ストリーム文脈 +0x825C 等を渡す)。能力ビット 0x200 が立つオブジェクトではファイル `0x6C8B8` を呼び、オブジェクト +0x148+0x368 からの素材をストリーム文脈 +0x7FC0 へコピーする。
- なお第5段の「drmctrl_open 本体相当」(ファイル `0x161520`)は本関数の直前に位置する同モジュールの関数で、6 つのストリーム登録スロットを持つ側である。本段では本体の完読はしていない。

### 6.3 「スロットとモードがどう決まるか」への回答

- モードは要求(OPEN_STREAM ペイロード → 変換後要求)の指定そのままで、FW 側で選び直す処理はこの経路にはない。
- 鍵は番号ではなく**鍵オブジェクト**単位で束縛される。「スロット番号」的な選択が現れるのは自動選択(フィールド 0)時の 6 スロット表の線形走査のみ。docs/13 §5.1 のペイロード側フィールド(`decrypt_key_slot_id` +0xD14 等)が変換(ファイル `0xB6344`)でこのオブジェクト指定へどう写像されるかは未再読(§8 の残件)。

## 7. 未判定のままのもの(理由)

- **SCRAMBLER 実体と `control_words[24]` の処理**: 到達できなかった。名前機構が操作ディスパッチではなかったため第5段の到達点からは辿れず、伝送層ディスパッチは未同定のまま([docs/13](13_xcode_fw_drm_phase5.md) §6 の陰性範囲が現在の到達点)。トークンが FW コードで加工されるか、そのまま HW / 他プロセッサへ渡るか ― (a)/(b) の境界 ― は実体を読むまで判定しない。§5 で AKE 交換鍵については FW コードによるバイト単位の導出(XOR)が実在することを確認したが、これは AKE についての事実であり、録画トークンの解決経路への外挿はしない。
- **READ_FROM_OTP の index 境界(ホスト実測 [docs/07](07_otp_value_level_stability.md): 0x00–0x81 と 0xFF が固定、0x82–0xFE が揮発)**: ハンドラ未到達のため未判定のまま。イメージ内に "otp" の文字列が存在しないことも含め、FW 側の判断材料はまだ無い。
