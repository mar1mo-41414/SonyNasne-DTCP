# 16. XCode ファームウェア DRM モジュール解析 第8段: 主 FW の登録サイト census、第2 FW の本格解析、静的解析の到達限界の整理

対象: 主 FW 平文イメージ(ファイルオフセット表記、[docs/05](05_xcode_firmware_images.md) の SHA-256 `3e99b413…` と同一物)と、第2 FW 平文イメージ(同じく [docs/05](05_xcode_firmware_images.md) の SHA-256 `a4ff86b2…` と同一物、本段で再抽出してハッシュ一致を確認済み)。主 FW のアドレスは原則ファイルオフセットで書き、Ghidra プログラムアドレスに触れる場合はその旨を明記する(ビュー2プログラム ghp7 では プログラムアドレス = ファイルオフセット + `0x100000`、ベース 0 プログラム ghp4 では両者は一致する)。第2 FW のアドレスはプログラムアドレス(= ロードベース `0xB00000` + ファイルオフセット)で書き、ファイルオフセットを併記する。

## 0. 要約

- **課題1(主 FW の登録サイト census)**: 「コマンドハンドラが初期化コードから関数ポインタを RAM 上の表へ書き込む形で実行時登録されている」という仮説を、材料化(即値・リテラルプール経由で関数入口の値を得る命令)の census 3 段と、静的な {コマンド番号, コードポインタ} 隣接ペアの全域走査で検証したが、**登録サイトは見つからなかった**(陰性の範囲は §2 に明記)。census の最有力候補(ビュー2側で 4 件の関数入口を材料化する関数、ファイル `0x1629F4`)は実読の結果、サイズクラス別のバッファプールアロケータだった。第6段の名前付きリソース管理フレームワークと合わせ、主 FW で「実行時登録」の形跡を持つ機構はバッファ/リソース管理系に限られる、という所見が補強された。
- **課題2(第2 FW の本格化)**: 第2 FW は主 FW と同じ **ARC 系**のイメージで、ロードベース `0xB00000` を GPL 一次資料(ホストドライバの `DEFAULT_SECOND_FW_OFFSET`)で確定した(§3.1)。Ghidra で本格解析し(2,595 関数 / 325,017 命令)、性格は**メディア処理プロセッサ(proc4)向けのイメージ**と同定した: コーデック文字列群が主体で、鍵ストア / OTP / AKE / mhcmd に関する文字列は存在せず、`scrambl` 文字列は AAC-SS スクランブラの DMA ログ 1 件のみ。主 FW と同じ共有通信領域・共有バッファマネージャを使うが、パケットスロット配列の基底への参照は無く、アクセスは自プロセッサの記述子ポインタ経由だった。タスク記述子表(6 件)を同定し、`proc4_incoming_request_process` の入口(プログラムアドレス `0xBC39A4`)の初期化部まで実読した(要求処理ループ本体は未読)。SCRAMBLER の配送先 proc6 のパーソナリティが本イメージ内にあるかは、プロセッサ別設定ポインタが実行時初期化で静的に引けず**未判定**(§3.9)。
- **課題3(AKE 文脈の初期化側)**: フィールドオフセットを命令スカラとして含む関数の全数検索は 0 件(手法の範囲での陰性)。第7段の残件だった AKE ステップ関数ファイル `0x68664` と、その呼び出し側の断片を実読したが、いずれも文脈フィールドの**消費者**であり、セッション文脈の生成・初期化側には到達しなかった(§4)。初期値の出所(OTP 固定域・鍵ストア・証明書・乱数)は未判定のまま。
- (a)/(b) の境界と READ_FROM_OTP の index 境界は、ハンドラ本体に到達できなかったため**未判定のまま**(§5)。
- **静的解析の到達限界**(§6): 第2〜8段で試した手を列挙し、残る可能性を (i) 未復号の孤立コード、(ii) 他プロセッサの実行文脈(proc6 パーソナリティ)、(iii) 実行時に構築される表・計算済み間接呼出しのみで到達する経路、の 3 つに整理した。静的に到達可能な範囲での追加の一手は費用対効果が落ちており、実験系(再生経路オラクル等)への申し送りを §6.3 に整理した。これは到達限界の所見であり、ハンドラ不在の証明ではない。

## 2. 課題1: 登録サイトの洗い出し(主 FW、見つからず・陰性の範囲を明記)

第6段で同定した名前付きリソース管理フレームワークが「実行時登録」の流儀だったことから、コマンドハンドラも同様に登録されている可能性を検証した。登録関数なら「複数の関数入口の値を、呼び出し以外の形(即値の材料化、またはリテラルプールのワード参照)で得て、ストアする」痕跡が集中するはずである。

### 2.1 census 第1段(緩い材料化、ghp4)

- 全 281,069 命令を走査し、関数ごとに「イメージ範囲内の相異なるスカラ値(オペランド即値 + データ参照先ワードの値)の数」とストア数を集計した。
- 上位は数千命令級の巨大なメディア処理関数が占め(相異なる値 153 件 / ストア 341 件が最大)、「少数の関数ポインタを集中的に材料化する登録関数」の形は現れなかった。値の範囲がイメージ基底 0 から始まるため小さい定数も大量に数えられる手法であり、この段は粗いふるいに留まる。
- 関数に属さない孤立コードは 61,743 命令(ストア 7,234 件)あり、相異なる値は 1,750 件。孤立コード側の精査は第3段で行った。

### 2.2 census 第2段(関数入口への材料化に限定、ghp4)

- 対象を「同定済み関数の入口アドレスと一致する値」の材料化(フローのターゲットであるものを除く)に限定し直した(同定済み関数 1,881 件)。
- 同定済み関数の中では、2 件以上の入口を材料化する関数は**存在しなかった**。複数件が現れたのは孤立コード側のみ(6 件)で、その値には `0x8000`(サンク表基底でありマスク定数でもある)のような定数衝突や、`0x2F92` / `0x2526CE` のような非整列値(Ghidra の関数マップ上の入口だが実体は疑わしい)が混ざっていた。
- すなわちベース 0 ビューの同定済みコードについては、「関数ポインタを材料化して集める処理」は存在しない(この定義と範囲での陰性)。

### 2.3 census 第3段(クロスビュー緩和、両ビュー)と候補の実読

- 材料化の照合に ±`0x100000` のクロスビュー形を許し、サイト単位で全数出力した。サイト総数は ghp4 で 550 件、ghp7 で 185 件。
- 関数単位の最大は ghp7 の関数(ファイル `0x1629F4`、相異なる対象 4 件、ストア 20 件)。後任がデコンパイルを実読した: 引数のサイズクラス(`0x20` / `0x40` / `0x80` / `0x100` / `0x200` / `0x10000`)でフリーリストを切り替えて走査する、**サイズクラス別バッファプールのアロケータ**だった。材料化していた「関数入口」はプール記述子内のポインタで、コマンドハンドラの登録ではない。
- ghp4 側の候補 2 件(ファイル `0x7627C`、`0x7B778`)も前任がダンプし、後任がデコンパイル冒頭を実読した: 前者は DSP 演算レジスタを使うメディア演算、後者は時刻取得を含むストリームヘッダ構築の様相で、登録処理の形跡は無かった。
- 残りのサイトの大半は、`0x8000` や `0x100030` など「関数入口でもある定数」の衝突だった(サイトの命令実体が `and` マスクやオフセット加算等)。

### 2.4 静的な {コマンド番号, コードポインタ} ペア表の走査

- 登録ではなく静的な対応表の可能性として、生イメージ全域で「伝送層番号 {8, 37, 42, 44, 45} のワードの ±8 バイト以内に、コード範囲(両ビュー形)のワードが隣接する」箇所を走査した(`pairscan8.py`、後任が再実行)。
- ヒットは 54 件。内訳は、命令列中の偶然の一致(値は非整列・奇数アドレス等)、データ領域内の一致(文字列領域 [docs/13](13_xcode_fw_drm_phase5.md) で既出の表の周辺など)が大半で、{番号, ハンドラ} 対応表と読める規則的な構造は無かった。第4段の「関数ポインタが 10 個以上連続する表は両ビューとも無し」([docs/12](12_xcode_fw_drm_phase4.md))と合わせ、静的対応表の線は両形式とも陰性である。

### 2.5 結論(課題1)

- 「初期化コードが関数ポインタを材料化して RAM 表へ書き込む」形の登録サイトは、主 FW の同定済みコード(両ビュー)には存在しない(§2.1–2.3 の範囲)。静的対応表も存在しない(§2.4、第4段)。
- 残る登録の形は「静的表からのループコピー」(表の基底だけが参照される形)だが、その表自体が §2.4 と第4段の census で陰性であり、裏付けは無い。
- 副産物として、主 FW で実行時登録・材料化の形跡を持つ機構は、第6段の名前付きリソース管理と本段のバッファプールアロケータという、**バッファ/リソース管理系に限られる**ことが重ねて確認された。

## 3. 課題2: 第2 FW イメージの本格化

### 3.1 形式とロード経路(確定)

- 第2 FW(平文 2,771,804 バイト)の ISA は **ARC 系**(主 FW と同じ): 先頭のブートスタブ 40 命令が ARCompact として coherent に復号でき、補助レジスタへの `sr` / `lr` を含む。MIPS32 は第1段と同じ物差しで棄却される(ワード列中の MIPS `jr $ra` 相当は 0 件)。ゼロワード比率 0.203、文字列(5 文字以上)は 6,603 件(うち主 FW に無いもの 4,896 件)。
- **ロードベース `0xB00000` を GPL 一次資料で確定した**: ホストドライバの commsdk ヘッダに `#define DEFAULT_SECOND_FW_OFFSET 0x00b00000 //maintained by FW` があり、ドライバ実装は第2 イメージをこのフレームバッファオフセットへダウンロードする(`Down_Load_Embedded_Second_Mips_Prog`)。主イメージのオフセットは `MIPS_FB_CODE_OFFSET = 0x00000000`。プロセッサ数の上限は `MAX_FW_PROC_NUM = 7`。
- アドレス面の傍証も一致する: ブートスタブが設定する `gp = 0xDA4B20` はベース `0xB00000` + イメージサイズ `0x2A4B5C` の直後(データ/BSS の開始位置として整合)、スタブ内のジャンプ先 `0xC93D34` や文字列参照先 `0xD05xxx` 台はいずれもイメージ範囲内に収まる。ワードレンジ census でベース `0xB00000` の自己参照帯に 8,147 ワードが入ることも確認した(トリアージ `triage8c.py`)。

### 3.2 ブートスタブとプロセッサ識別

- イメージ先頭(ファイルオフセット `0x0`–)のスタブは、補助レジスタ(IDENTITY、アドレス `0x4`)を読み、プロセッサ識別子(ビット 15–8)を **3 / 4 / 6** と比較して分岐する。共有通信ヘッダのカウンタ(識別子 3 と 6 は `+0x90`、4 は `+0x98`)をインクリメントし、想定外の識別子では `+0xA0` へ `0xBAD70000 + 識別子` を書く。
- すなわち本イメージは複数のプロセッサで起動し得る共通 OS イメージで、振る舞いをプロセッサ識別子で選ぶ構造である。ただし後述の通り、静的に列挙できたタスク集合は proc4 向けのものだけだった(§3.7、§3.9)。

### 3.3 Ghidra 解析の規模

- プロジェクト ghp8s3(ベース `0xB00000`、ARCompact 定義でインポート + 自動解析): **2,595 関数 / 325,017 命令**(`Survey8s.java` の集計)。

### 3.4 内容の性格(メディア処理)

- 文字列の主体はコーデック処理である: JPEG(APP0 マーカー、SOF、ハフマン表)、H.264(DPB / MMCO のエラーログ)、AAC(SBR ライブラリのソースパス)、DTS サンプリングレート変換、`ARC_API_BUFFER_STREAM_TYPE` など。
- キーワード census(バイト部分文字列の出現数、第2 FW / 主 FW): `keystore` 0 / 0、`otp`・`OTP` 0 / 0、`kauth` 0 / 1、`exchg` 0 / 1、`mhcmd` 0 / 0、`FunctionNumber` 0 / 0、`drm` 0 / 14。`scrambl` は 2 件で、実体は `'post_Aacsscrambler_dma pcmd->scramble_mode ='`(ファイル `0x1DF9E8`、AAC-SS スクランブラの DMA ログ)とその断片であり、TS スクランブル(SCRAMBLER)に関する文字列ではない。
- `'DTCP '`(ファイル `0x1D3478`)という文字列は存在するが、そのアドレスへの参照は、LE 形・16 ビットハーフスワップ形(= ARC の limm 格納形式)のいずれでも、ベース 0 / `0xB00000` / `0xC00000` の全形で見つからなかった(`refsearch8.py`)。対照として AAC-SS スクランブラ文字列への参照はハーフスワップ形でコード内(ファイル `0x14870E`)に確認できており、検索手法自体は有効である。したがって当該文字列は、復号済みコードからは参照されないマニフェスト的な残存とみられる(解釈)。

### 3.5 共有通信領域との関係

- 命令スカラとして共有通信領域のアドレスを含む命令は 148 件(`Survey8s.java`): 内訳は記述子配列基底 `0xAFE000`、自プロセッサの記述子ポインタセル `0xAFE004`、共有ロックワード `0xAFEB04` への参照。
- **パケットスロット配列の基底 `0xAFE6B4` / `0xAFE7E8` / `0xAFE91C` への参照は 0 件**だった。第2 FW 側のアクセスは `*[0xAFE004]`(自プロセッサの記述子ブロックへのポインタ)を起点とする形であり、主 FW 側の初期化コードが前提とする「全プロセッサ分の配列を基底 + インデックスで引く」形とは異なる。
- ロックワード `0xAFEB04` の使用者は 1 関数(§3.6)だけだった。

### 3.6 共有バッファマネージャの解放関数(プログラムアドレス `0xB9A894`、実読)

- 前任の最後の作業でダンプされた本関数を後任が実読した。処理は: ロックワード `0xAFEB04` の取得(スピン)→ 要求ブロックと一致する管理エントリの検索(記述子ポインタセル `0xAFFBCC` が指す表、ストライド `0x20`、最大 `0x40` 件)→ 型(5 種: 特殊値 `0x7FFFFFF` と 0–3)ごとのフリーリスト(ポインタセル `0xAFFBD4`–`0xAFFBE4`)を辿って解放ブロックを挿入し、隣接する空きブロックを併合 → 管理ヘッダ(ポインタセル `0xAFFBC8`)の空き容量カウンタを更新 → ロック解放。要求の履歴を 32 件のリングバッファ(アドレス `0xD8B8EC`、ストライド `0x30`)にも記録する。
- デバッグ出力の書式文字列は `"<BM F B: %d S:0x%x(%d)"` と `"MemAvbl: %x (%d) Id: %x %s"`(ファイル `0x1DFA64` / `0x1DFA80`)で、**BM = バッファマネージャ**の解放処理であることが名前からも裏付けられる。
- すなわち第7段で「ロックワード」と呼んだ `0xAFEB04` の実体は、プロセッサ間で共有されるバッファマネージャの相互排他ロックであり、第6段で主 FW 側に同定したリソース管理フレームワークと同一系譜の機構が、第2 FW 側ではプロセッサ間共有の形で実装されている。パケット受信そのものはこのロックを使っていない(使用者は本関数だけ、§3.5)。

### 3.7 タスク記述子表の同定

- 文字列 `'proc4_incoming_request_process'`(ファイル `0x1D126C`)への参照をバイトレベルで検索し、データ領域(ファイル `0x1F1E14`)にそのアドレスのワードを発見した。周辺を実読し、**タスク記述子表**と同定した: ファイル `0x1F1DC4` から `0x20` バイト × 6 件、レコードは {`+0x00`: タスク ID、`+0x04`: 入口アドレス、`+0x08`: スタックサイズ、`+0x0C`: 優先度相当の値、`+0x10`: 名前文字列へのポインタ、`+0x14`–`+0x1C`: 0}。表の基底アドレスへのポインタがファイル `0x206388`(アドレス `0xD06388`)に格納されている。同じレコード形状はイメージ全域走査でもこの表だけだった(`tasktab8.py`)。
- 内容(全 6 件):
  - ID 7: `wrapper_task`、入口 `0xC8BAA8`、スタック `0xC00`、優先度相当 `0x41`
  - ID 11: `uist_mv_conversion`、入口 `0xC8219C`、スタック `0xC00`、`0x30`
  - ID 12: `proc4_incoming_request_process`、入口 `0xBC39A4`、スタック `0xC00`、`0x30`
  - ID 14: `avc_dec_init_task`、入口 `0xB97B98`、スタック `0xC00`、`0x30`
  - ID 13: `avc_encoder_task`、入口 `0xBE6B68`、スタック `0xC00`、`0x30`
  - ID 15: `proc4_SoftGVD`、入口 `0xC99A3C`、スタック `0xC000`、`0x30`
- Ghidra の参照管理ではこれらの文字列への xref は 0 件だった(表経由の参照は静的参照として生成されていなかった)。第2 FW でも、名前文字列は表に埋め込まれて実行時に引かれる形であり、コードからの直接参照は無い。

### 3.8 `proc4_incoming_request_process` 入口(プログラムアドレス `0xBC39A4`、初期化部のみ実読)

- 後任が入口関数をダンプして実読した範囲: キューのカウンタ対(アドレス `0x1483940` / `0x1483944`)の一致を確認し(不一致なら例外記録 `0xDEADC0DE` を書いて停止する致命的エラーの形)、現行タスクの制御ブロックへマジック `0xABCD00F1` を書き(タスク取得プリミティブ プログラムアドレス `0xB05710` 経由)、その後プロセッサ別スケジューラプリミティブ(プログラムアドレス `0xB04B00`)を呼ぶ。同プリミティブは補助レジスタの識別子でプロセッサ別設定セル(アドレス `0xCF0080` = 識別子 3、`0xCF00A0` = 4、`0xCF00C0` = 6)を切り替える OS の中核処理だった。
- **要求処理ループ本体は未読**である: ループはスケジューラ呼び出しの後段にあり、Ghidra が切り出した関数の範囲(入口の初期化部)には含まれなかった。到達には関数境界の復元が要る。

### 3.9 proc6 パーソナリティの所在(未判定)

- ブートスタブ(§3.2)と OS プリミティブ(§3.8)は識別子 6 の分岐を持つため、本イメージが proc6 でも起動する可能性自体は構造としてある。
- しかしプロセッサ別設定セル(`0xCF0080` 等)が指す先はイメージ内では 0 で、実行時に初期化される。したがって proc6 用のタスク集合(別のタスク表を持つのか、§3.7 の表を共用するのか)は静的には列挙できなかった。
- **SCRAMBLER(mhcmd 37、procIdx = proc6)の処理が本イメージ内にあるかは未判定**である。少なくとも proc4 パーソナリティに関する限り、本イメージはメディア処理専用で DRM 系の実行コードの存在を示す材料は無かった(§3.4)。

## 4. 課題3: AKE セッション文脈の初期化側(到達せず)

### 4.1 フィールドオフセットの即値 census(陰性、手法の範囲)

- 第7段の申し送り(文脈フィールド `+0x10C20` / `+0x10C30` / `+0x112FC` / `+0x11310` / `+0x11338` / `+0x1134C` / `+0x1149C` / `+0x10C9C` / `+0x10CB4`)について、これらの値を命令スカラとして含む関数を ghp7 の全命令から検索した(`FieldUse8.java`)。結果は **0 件**。
- AKE コードの文脈アクセスは「文脈ポインタ + 大きいオフセット」の計算済みアドレッシングで書かれており、オフセット値が裸の即値としては現れないためである(手法の限界であり、フィールドを使用する関数の不在を意味しない)。

### 4.2 AKE ステップ関数 ファイル `0x68664` の実読(第7段 §6 の残件)

- 本関数は引数コード `0x6C` を要求する AKE プロトコルステップで(違えばエラー 6)、前提として状態フラグ(セッションオブジェクト `+0x368`)の bit0 と bit1 の両立を要求する(欠ければエラー 3)。
- 処理: 文脈(= セッションオブジェクト `+0x48` が指す先、以下同じ)+`0x10C20` の `0x10` バイトを `+0x1142C` へ複写し、中核計算(ファイル `0x16EA20`、対象長 `0x44`)へ文脈 `+0x10C44` と **`+0x112FC`** を渡す。成功すると受信メッセージから文脈 `+0x10C74`(`0x28` バイト、第7段で相手方素材の置き場と確定したフィールド)・`+0x10CCC`(4 バイト)・`+0x10CD0`(5 バイト)へ複写し、状態フラグを更新したうえで、条件により gen_kauth(ファイル `0x6772C`)を呼ぶ。
- すなわち本関数は `+0x10C20` と `+0x112FC` の**消費者**であり、初期化者ではない。

### 4.3 呼び出し側の断片(ファイル `0x16B126` を含む範囲)の実読

- 本ステップの唯一の呼び出し箇所(ファイル `0x16B126`)を含む断片も後任が実読した: ステップの復帰後、文脈 **`+0x10C30`**(`0x14` バイト)を変換関数(ファイル `0xEFC2C`、第6段で gen_kauth の派生分岐でも使われた変換)へ入力し、結果をセッションオブジェクトへ戻し、セッションオブジェクト内の 2 つの 16 バイト値の XOR を取る。
- ここでも `+0x10C30` は消費される側であり、初期値の書き込みは無かった。

### 4.4 結論(課題3)

- セッション文脈の生成・初期化側(文脈オブジェクトを誰が確保し、`+0x10C20` / `+0x10C30` / `+0x112FC` / `+0x11310` の初期値をどこから書くか)は**未同定のまま**。AKE ステップ層(ファイル `0x166000`–`0x169500` の 29 関数)は前任がデコンパイル済みで作業領域に残るが、セッション管理層はその外側(ステップを呼ぶ側のさらに上位)にあるとみられる(§4.3 の断片も管理層の末端で、確保処理を含まなかった)。

## 5. 課題5: (a)/(b) 境界と OTP index 境界(未判定のまま)

- 本段でも SCRAMBLER / READ_FROM_OTP のハンドラ本体には到達できなかったため、(a)/(b) の境界と READ_FROM_OTP の index 境界(ホスト実測 [docs/07](07_otp_value_level_stability.md): `0x00`–`0x81` と `0xFF` が値レベルで固定、`0x82`–`0xFE` が読み出しごとの揮発)について、FW 側からの判定材料は得られなかった。**両者とも未判定のまま**とし、理由はディスパッチ未到達に帰着する。
- 第2 FW 側の所見(§3)は「少なくとも proc4 パーソナリティと共有バッファマネージャには DRM 系の処理が無い」という範囲のもので、トークン解決の所在を否定する材料ではない。

## 6. 静的解析の到達限界と実験系への申し送り

### 6.1 試した手の列挙(第2〜8段)

- 文字列 xref による到達(主 FW、ベース 0 / +`0x100000` の両ビュー)。
- 静的表の探索: レジストリ(ファイル `0x2ED500`)、ディスパッチ表候補(ファイル `0x2ED578`)、関数ポインタ表の census(10 連以上)、{コマンド番号, コードポインタ} 隣接ペアの全域走査(本段 §2.4)。
- 名前引き機構の追跡(名前記述子 → 名前付きリソース管理フレームワークと同定、第6段)。
- 通信記述子の読み手の署名探索(絶対スカラ参照、FunctionNumber 振り分けパターン、記述子フィールド読み、PacketProcessed 書込み署名、両ビューの同定済み関数 + 孤立コードを含む全命令線形走査、第7段)。
- 登録サイト census(材料化の 3 段、本段 §2)。
- 第2 FW の本格解析(ISA・ロードベースの確定、タスク表と受信タスク入口の同定、共有機構の実読、本段 §3)。
- GPL 一次資料による配送構造(H2M パケット、procIdx、ロード経路)の確定(第3・4段、本段 §3.1)。

### 6.2 残る可能性(いずれとも判定しない)

1. **未復号の孤立コードの中**: 主 FW のコード密領域の約 23% は関数として同定されておらず、線形走査の署名にも掛からなかった処理が残り得る。
2. **ドアベル先の他プロセッサ実行文脈**: SCRAMBLER の配送先 proc6 のパーソナリティは、第2 FW 内にあっても静的に列挙できなかった(§3.9)。proc6 専用の別イメージやブート側で供給されるコードの存在も否定できない。
3. **実行時に構築される表・計算済み間接呼出しのみで到達する経路**: 登録の材料化も静的表も無い形は、本段までの手法では原理的に捉えられない。

### 6.3 所見と実験系への申し送り

- 所見(解釈): 「主 FW の復号済み命令列と第2 FW のタスク構造」という静的に到達可能な範囲では、伝送層ディスパッチと SCRAMBLER / READ_FROM_OTP ハンドラは存在しないか、静的参照の形を持たない。静的経路の追加の一手は §6.2 の (1) 孤立コードの関数境界復元と (2) proc6 用設定の実行時初期化の追跡に限られ、いずれも費用対効果が落ちている。**副線(鍵だけ抜いて PC で復号)の静的な接近はここで一旦区切り、本線の実験系へ重心を移すのが妥当**と考える。これは到達限界の所見であり、ハンドラが存在しないことの証明ではない([AGENTS.md](../AGENTS.md) §2.2 の基準により、棄却とは書かない)。
- 実験系への申し送り:
  1. トークンのスコープ判定(同一ブート内で録画 → 即リプレイ)は静的結果に依存せず実施でき、(a)/(b) の切り分けにも間接的に効く。
  2. OTP 揮発域(`0x82`–`0xFE`)の生成機序は、FW 側ハンドラが読めない以上、ホスト側の観測(読み出し値の相関・タイミング)で攻める方が早い可能性がある。
  3. 静的解析を再開する場合の入口は、孤立コードの関数境界復元か、ブート時の proc6 設定初期化(ブート FW / 起動側コード)の追跡である。
